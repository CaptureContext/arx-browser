# ChromiumBrowserEngine

Owns one native page per tab, asynchronous profile preparation, identity-scoped navigation streams, and weak presentation hosts. The first persisted profile retains Chromium's original `Default` directory. Every additional profile uses `Arx-<UUID>` under the app's user-data directory, with its own Chromium cookies, storage and profile services. Spaces share sessions only through their profile identity.

Concurrent opens coalesce. A live tab identity cannot change profiles; cross-profile moves stage a new tab/session and only remove the source after destination creation and before-unload approval. Cancellation and failed creation retain the source. Closing a host detaches its page without closing the session. Duplicate hosts in another window focus the existing window instead of reparenting implicitly. A SwiftUI host replacement within the identical nonnil window remaps ownership before mounting, so later teardown of its old host cannot remove the page. An unattached replacement must retry after acquiring its window. A page never leaves its window on the way to a new host: it waits for a windowless host to join the window, then moves straight across, because a page that leaves its window is hidden and Chromium then drops its compositor and shows nothing until it draws again. `stage` keeps one loaded page that isn't shown, playing media or in Picture in Picture drawing in a stage view; a page no longer wanted leaves it 300 ms later unless a host took it, and staged pages count as neither attached nor visible for capture.

The engine supplies history entries, before-unload decisions and renderer-failure events. Recovery recreates only the affected session. Reset clears the page/navigation state, not shared profile site data or cache.

`make app-smoke` verifies two isolated cookie/localStorage contexts and sharing within one context, along with page attachment, Dock reopen and renderer recovery. Real password-store use, interactive dialogs and input methods remain manual checks.

Private profiles must be prepared before opening their tabs and released only after closing them. The native context is off-the-record, not a temporary on-disk profile. Cache-clearing reload clears the owning profile HTTP cache and reloads with cache bypass, preserving cookies and sign-in.

The original Chromium Default profile is selected by the workspace’s durable legacyProfileID, never by the current first profile. prepareProfile prepares the corresponding native storage without creating a page.

A newly created pinned session navigates to `Tab.reopeningURL`, so a closed pin starts from its saved URL even when restoration metadata records another page. Already loaded sessions remain untouched by repeated opens.

Conservative session revisions advance on navigation updates and session replacement/close. Guarded automation entry points recheck the live app grant after waiting for session creation and before native dispatch, preventing stale scope or navigation versions from authorizing work. These checks introduce no native ABI.

`downloads(metadataFile:organization:)` creates and retains the application-wide queue. Supply the initial ordinary BrowserOrganization before creating browser windows; the service installs its profile and space labels synchronously before subscribing to native event replay. Configure it with each later committed organization so origin labels remain available after tab closure. Initialization only establishes origin lookup; async `configure` owns reconciliation and native profile preparation. DownloadLedger persists only ordinary records atomically, preserves captured profile/space labels, reconciles stale active records after native manager initialization, and verifies completed files before explicit Open/Reveal actions. Private records stay in a separate memory-only queue. UI observation cancellation never affects native transfers.

On each `configure` call, persisted active records whose ordinary profile is absent from the organization become interrupted, unless a live native event already confirmed that transfer this session. This also handles a profile removed while native preparation is pending. Completed history and captured origin labels remain. Later profile deletion does not cancel or relabel running transfers; All Profiles retains their ordinary download history. Private records are excluded from this reconciliation.

Configuration prepares only the profiles with a persisted transfer still in progress that Chromium hasn't reported this session, or, when the saved history couldn't be read, each profile Chromium hasn't enumerated yet (DEV-880), so Chromium resumes or interrupts it and `downloads_initialized` settles the rest; preparation is attempted for each and the first error is reported. Any other profile's Chromium downloads are observed once something loads it, and the ledger lists every profile's records meanwhile. `start` prepares its profile first. The service rejects canceled configuration before changing its origin lookup or ledger. AppDownloads cancels superseded readiness/save configuration effects; an already issued native preparation may still finish, but cancellation stops subsequent profile preparations and suppresses stale failures. An individual profile preparation error does not invalidate the client or disable controls for transfers already observed.

A navigation that becomes a download (DEV-1116) commits nothing, so a tab showing a page keeps it, with no error. Each transfer carries the tab whose page started it (`BrowserDownload.sourceTabID`, kept in memory only), and the queue reports every change of one to the engine. A tab with nothing committed, a new tab or one whose only navigation became a download, then reports the newest such transfer as `BrowserNavigation.download`, with a new session revision. The engine says whether anything committed (ABI48's document type), so a current history entry with the file's address doesn't count as a page; a site-written `about:blank` popup does. Every page this engine opens fresh starts at the `about:blank` `makePage` creates it with, which Chromium commits as an ordinary entry, so while that is still such a page's only entry the tab has nothing of its own either (`isStillAtItsStart`); a restored page or a popup Chromium opened never counts that way. A page, or the tab closing, forgets it; an older transfer's progress never replaces a newer one.

The explicit `capture` client adapts ABI5 viewport snapshots to BrowserCaptureClient. It checks the requested tab revision and live authorization before and after awaiting native work, preserves the captured document/geometry, and warns that protected media may be omitted. A process-wide busy result remains actionable while canceled native work drains. App composition explicitly injects this capability. The signed rendering fixture validates pixels, layout and invalidation; the default uncomposed dependency remains unavailable.

The explicit `media()` factory observes existing and later ordinary pages and maps native page/generation identities to their current tab/profile owners. It replays authoritative snapshots and routes only generation-checked native Return-to-Tab events. A new snapshot goes out only when its sources change, so a page opening or closing without media sends no store action (DEV-945). Commands verify the exact source revision and owning live page before native dispatch and reject removed/replaced sources after awaiting completion. Private and unknown pages never enter this client. Automatic PiP maps only the separately advertised native automatic action; application composition owns per-site opt-in and source visibility transitions. It never substitutes the manual action; MediaFeature asks for the manual entry itself when a site advertises no automatic action or Arx resigned active (DEV-848). The engine creates Chromium's video PiP window (a `NativeWidgetMacFramelessNSWindow` at the floating level) on every Space and over other apps' full-screen Spaces before it's first shown: activation independence, as Chromium's Glic window has, plus `.canJoinAllSpaces`, `.fullScreenAuxiliary` and `.canJoinAllApplications` (DEV-852). Arx used to add the behaviour after Chromium showed the window, which AppKit ignores until the window is ordered in again, and ordering it out ends Picture in Picture. `PictureInPictureWindow` is now only the check the smokes use. The signed video fixture validates playback and source invalidation; OS controls and private OS presentation require separate acceptance.

Media Return-to-Tab validation is synchronous through ABI8: the adapter resolves a current ordinary owner, then the engine rechecks its exact tab/profile/page registry and asks the runtime/native observer for the generation. An unchanged or replayed Swift snapshot cannot restore an invalidated native identity. Shutdown and deleted/private owners fail closed.

ChromiumExtensionsAdapter retains native inventory authority, maps the legacy profile exclusively to Default, and consumes exact profile/token/revision requests. The required live ordinary-profile predicate is checked before native calls and after awaits; unsupported/private profiles cannot become ordinary extension targets. Mutation completion verifies the authoritative state before issuing a new token. Ordinary app startup explicitly composes ChromiumBrowserEngine.extensions(ordinaryProfileExists:). The developer fixture verifies worker execution, storage, request rules and guarded profile-specific inventory/control; the staged options host additionally adopts the exact already-created extension session without navigating a replacement. Its capability defaults off pending matching native acceptance. Installation, updates and action popup UI remain separate capabilities.

`closeAuthorized` is optional and requires explicit `enableAuthorizedClosing` composition plus the complete ABI9 function set. Capability selection is independent of readiness so the Store can retain a client created before engine startup; execution requires a running runtime. A loaded target must retain its exact page, profile, open generation and session revision around native before-unload approval. A pending open is not a dormant target. The final live grant check, native token consumption, runtime/service ownership disposal and `didClose` publication run without suspension. Refusal preserves the session; stale documents, canceled/revoked work and unavailable capability cannot fall back to unconditional destruction. Ordinary user close retains its existing path.

Favorite site icons use exact saved-page URL database queries through `siteIcons(organization:)`. The memory cache holds at most 256 results / 4 MiB, coalesces subscribers, and runs at most eight queries concurrently. A missing icon is fetched from its site only for a view showing it on screen (`icons`); a view mounted off screen (`cachedIcons`) reads only Chromium's database, and its icon is fetched once a view showing it asks. At most four reads that may fetch run at once, so a relaunch doesn't ask dozens of sites together; database-only reads go on past the waiting ones (DEV-940 follow-up). With a `storeDirectory` (BrowserWindow passes `<profile root>/Site Icons`), a `BrowserSiteIconStore` backs the memory cache (DEV-809): a stream opens with the stored icon while Chromium is asked, a live icon replaces the stored one, and a miss keeps showing it. Before the runtime is ready a stream yields only the stored icon and ends, so nothing negative is cached. At creation the store keeps only the pages the organization's open and archived tabs point at. Profile removal immediately cancels queries and clears/finalizes subscribers; generation checks reject late results. Chromium alone fetches favicons, with the profile's cookies.

The icon client is stable when created before runtime startup. Initial profile membership is seeded synchronously, but cache construction and observation wait until a subscription made while Chromium is running. Unavailable early reads are never negatively cached. Runtime observation ending clears cached/pending images. The owned signed fixture consumes the same injected client and checks post-page-close database reads. A separate restart-only process checks persisted blue/green images for the same saved URL in two ordinary profiles, without opening pages; the runner denies all site-icon HTTP traffic. These acceptance fixtures require execution against the packaged framework.

Valid favicon changes refresh only the keys of the pages they name, within the originating profile (DEV-940): a finished load re-reads that page and its load's aliases, and every key whose cached bitmap belongs to the favicon the change reports, not every mounted row. A key keeps its favicon while it is on screen, even when the budget evicts its bitmap, and through a miss or failed read. A refresh that returns new bytes also re-reads the rows showing other bytes for the same favicon (compared by what each row shows, so an evicted row is caught and the repair ends once it matches) and unobserved answers cached with other bytes, which covers changes that came without a favicon address. A change without a favicon (a lifecycle one, recovering a lost notification) reads every page it names once more, tracked or not, cached or not; a probe overtaken by another change reads again; a key whose last read failed (timeout, busy) is read again by the next page change in its profile; a read that answers with a favicon that a later change named, or whose newer bytes a later read found, reads again unless its bytes match; a lifecycle read survives its row going away; a row already reading isn't asked to read again by a sibling's answer; a probe nobody shows reads the database only (never fetches), caches no miss (a row that mounts reads again with fetching) and writes the persistent store only once a row shows its answer; and a first read still in flight when a favicon changes is read again, since its answer may predate the change. Keys are matched through an index by GURL's canonical address (lowercase scheme and host, no default port, `/` for an empty path, dot segments resolved including `%2e` spellings, no fragment); lookups still use the exact key. A key whose canonical form is only a guess (user info, characters or escapes GURL rewrites, IPv6 literals, other numeric or internationalized hosts, any `%2e`) is re-read by every page change in its profile instead. Unobserved cached results for those pages are forgotten. Only a profile-wide change (cleared history) re-reads every key in the profile. When the bounded change stream drops an older change, a profile-wide change for its profile takes its place. Bursts coalesce into the union of their pages; an active query drains before one follow-up read, so refreshes cannot repeatedly cancel the same work. Profile generation is checked again when the queued refresh runs. The lookup queue is set-backed (FIFO, O(1) membership and removal), and the cache keeps a running byte total and an access-ordered index, so an answer's budget check and least-recently-used eviction don't scan the cache.

MCP capture supplies an ordinary profile and synchronous native document epoch to the shared adapter. Those optional constraints trigger native host visibility checks before and after capture, without changing ordinary explicit user-capture behavior. The snapshot exposes the same live visibility and document stamp for final IPC response authorization. A page in a visible non-key window remains eligible; no focus, load, scroll or attachment is performed by this read. Hidden, minimized, detached and replaced hosts fail closed. A delayed native page callback cannot make an older document epoch current.

The retained `inspection` client resolves readiness on every call, so pre-run composition works after runtime startup and fails closed after shutdown. Its factory binds the exact live ordinary tab/profile/session/native document epoch; app composition additionally checks current workspace ownership. No page is created, attached, navigated or focused. ChromiumInspectionAdapter maps the native main-document semantic snapshot into bounded browser values. Its entry and completion gates bind the exact ordinary source, live authorization and native page/document/scope registry. The 114,688-byte native output budget reserves room for MCP's duplicated text/structured envelope; exact IPC and MCP checks remain authoritative. The DOM version describes historical renderer data. Browser-side validation never claims synchronous DOM currency, and no action/reference-resolution API is exposed to MCP.

`ChromiumInteractionAdapter` maps only a scoped reference click. It reuses the trusted inspection source and passes a final synchronous authorization callback into the atomic native click API. Completion never reclassifies click-induced navigation or shutdown as proof that nothing happened. Native not-dispatched/dispatched/possibly-dispatched outcomes remain distinct; no focus, scroll or replay is added by the adapter.

Reference activation uses a stable pre-startup `interaction` client. Each call resolves the exact loaded ordinary tab/profile/session/native document again, and passes the app authorization callback into the atomic runtime activation boundary. Completion preserves native dispatch uncertainty even when the activation navigated its source.

Page waits capture the native page object, profile and generation before suspending. Navigation events are wake-ups, followed by a fresh read of cached navigation and its publication epoch against the synchronous live epoch. Primary navigation start/commit or replacement invalidates the wait; the adapter never follows a new document. An injected continuous clock bounds waits to ten seconds, at most sixteen are active per client instance, and subscriptions are removed on every terminal path.

ChromiumFormAdapter validates explicit request/reference/source identities before native admission and rechecks live source and app authorization in the final synchronous callback. It maps bounded native control failures without values and preserves known unchanged/dispatched or uncertain outcomes across later navigation/cancellation. A wrong operation ID is conservative uncertainty. Production form availability remains independent from click support.

The live retained interaction factory queries ABI form support and running state on each call, independently from click. It resolves the same exact loaded ordinary page/profile/session/native document before executing the form adapter; the native runtime retains atomic DOM/control-baseline checks and final authorization. Missing tables, stopped runtime, foreign/private or disposed sources fail before submission.

ChromiumScrollAdapter validates finite bounded input and exact target/snapshot/reference/source identity before native admission, then repeats live source and app authorization immediately before submission. Typed noScrollableContainer and invalidDelta failures are retained. Known native outcomes survive late lifecycle changes; mismatched operation identity becomes conservative uncertainty. The live factory gates availability on runtime readiness and the complete ABI14 table, resolves the same ordinary session/profile/document before admission and retains the final synchronous wrapper authorization.

Renderer link menus map only the original native page to its owning tab/profile/session. Both mapping and action-time current checks preserve private-page identity and reject closed/replaced/hidden native sessions; menu dismissal releases wrapper authority.

The ABI16 retirement adapter holds profile admission closed while dispatching durable consent-bound retirement. Existing or pending sessions reject the request before native dispatch; native independently checks pages, preparations, private ownership and downloads. A missing/error receipt leaves the target blocked until persisted intent is reconciled. Other ordinary profiles continue browsing. The native startup uses Arx-Bootstrap and parents private contexts there, so retiring the permanent Default owner cannot silently recreate Default. Production composition requires stable root-bound installation identity and packaged startup/reboot acceptance.

Profile retirement blocks admissions independently of its in-flight queue operation. A failed or lost queue receipt keeps the profile blocked but permits inspection and a retry using the same request identity and a fresh snapshot revision. Concurrent queues or another request for that profile fail closed. Native ownership checks remain independent of this service policy.

Capture Area's scrolling (DEV-1208, `scrollAuthorized`) runs a short script in Arx's translation world, an isolated world of the main frame, through `evaluateTranslationScript`: it scrolls the page's own scroller by the offset, turned from points into CSS pixels by the page's zoom, with `behavior: "instant"`, and replies how far it moved, turned back into points. The page's scripts can't see or replace it. It shares the translation world's one-script-at-a-time queue, so a translation in flight answers busy, and Capture Area then draws within the viewport. A page magnified with a trackpad pinch isn't scrolled: the script checks `visualViewport.scale` first and replies without scrolling, because the visual viewport moves content by more points than the zoom says. A busy, pinched or refused script (a `file:` page or another document that isn't HTTP(S)) fails as `.busy` or `.unavailable`, meaning the page didn't move; a failure after the script may have run (a timeout, an exception, a reply that isn't two numbers) says so with another failure. One scroll moves at most 4096 points. No engine change was needed.

The capture adapter chooses a separate document closure for full-document mode and checks its live availability before submission and delivery. Native metadata maps to a document geometry value while actual viewport DIP/device scale remain unchanged. Both user capture and authorized automation use this client; full-document native availability stays false until bounded-recording and native acceptance gates pass.

Guarded keypress availability is queried independently from ordinary form support
at entry and at final synchronous authorization. The adapter maps only validated
bounded `keyPress` requests to native kind4; absent or revoked capability cannot
borrow ordinary form availability. Native partial/dispatched receipts remain
truthful across later lifecycle changes, and contain no key or field content.

The staged unhandled-Escape adapter is opt-in until native acceptance. It maps
only the current native page to its actual focused host and captures the native
document epoch for deferred validation. Closing, navigation, rehosting, focus
loss and hidden surfaces deny stale work. It does not translate Escape into a
page command or infer that content declined it from an AppKit monitor.

Content hosting is staged off by default. An adopted child is registered under
its actual source profile, ordinary media observer and download provenance
before presentation; the adapter requires the exact mounted visible source
view and matching document epoch. Refusal removes child-only registry rows.
Debug builds keep the last request and the step that refused it, or whether the
app declined or adopted it (`lastNewContents`, a `NewContentsRecord` without the
URL), so an app smoke that clicked a link can say where it stopped (DEV-1191).
Private children retain the same off-the-record context; context release waits
for all adopted pages after the last private host requests it. The wrapper never recreates
the child URL, so opener, session storage and initial navigation remain native.

Runtime-origin options rollback releases only the exact initially offered page, observers, host and media ownership before notifying AppFeature. A reentrant user close or replacement cannot remount that child or clear a replacement session. Settlement discards the temporary offer proof after publication; native remains the sole destroyer on a failed native post-publication check.

`ChromiumFormAdapter` maps pointer kinds to `ChromiumPointerAction`. A point-addressed request carries the snapshot's own ID as its reference; a drag destination reference must belong to the same snapshot, otherwise the request is stale before native code is reached.

The developer tier (ABI34, DEV-668) maps `BrowserEngineClient.evaluateScript`, `setDeveloperLog` and `readDeveloperLog` onto `ChromiumRuntime`; private pages are refused before native code, and native log entries become typed console or network entries, failing the read if one doesn't fit.

Saved passwords (ABI35, DEV-708) map `BrowserEngineClient.savedAccounts`, `signInWithPassword`, `passwordSaveOffers` and `answerPasswordSave` onto `ChromiumRuntime`. Private pages are refused before native code. The runtime is shared, so each engine yields only its own tabs' save offers.

Settings' saved passwords (ABI36, DEV-721) map `savedPasswords`, `savePassword`, `removeSavedPassword`, `revealSavedPassword` and `importPasswords` onto `ChromiumRuntime`. Each prepares the profile first and refuses a retiring one; the configured default profile uses the engine's default key. A lent field is looked up in `BrowserPasswordFields`; a field that went away is `stale`. Import failures keep native's reason (`unreadableFile`, `badFormat`, `fileTooLarge`, `tooManyPasswords`).

Autofill (ABI52, DEV-875, DEV-893) maps `autofillEvents` to this engine's ordinary tabs only (the runtime is shared), `acceptAutofillSuggestion`, `selectAutofillSuggestion`, `dismissAutofillSuggestions` and `setAutofillAuthentication`, and `autofillView(_:)` gives the page view the app anchors the suggestions in.

Addresses and cards (ABI52, DEV-893) map `autofillListing`, `saveAutofillAddress`, `saveAutofillCard` (looking the lent number field up in `BrowserPasswordFields`), `removeAutofillData` and `setAutofillProducts`, preparing the profile first as saved passwords do.

Credential migration (ABI46, DEV-830) maps `credentialImportIsAvailable`, `importPasswordRecords`, `importCookies`, `checkCookies` and `undoCredentialImport` to `ChromiumRuntime` for an ordinary, non-retiring profile it prepares first. `ChromiumCredentialImportAdapter` converts dates to Chromium's microseconds since 1601, clamps out-of-range numbers so native rejects them rather than storing another value, clears the ancestor bit of unpartitioned keys, and splits calls into the chunks native takes (10,000 passwords, 20,000 cookies).

The focused link (ABI37, DEV-713) maps `BrowserEngineClient.focusedLink` to `ChromiumRuntime.focusedLink(on:)` for the tab's live, ordinary page. It records the tab's session revision before asking and drops the answer if the tab's page or profile changed meanwhile.

Form edits (DEV-1084) map `BrowserEngineClient.formEdits` to `ChromiumRuntime.formEdits(on:)` for the tab's page, private ones too. A tab whose page was replaced while the engine checked reads as `.unknown`.

Site settings (ABI38, DEV-716) map `siteSettings`, `changeSiteSettings` and `siteSettingsChanges` onto `ChromiumRuntime`. Each call prepares the profile first and refuses a retiring one; the configured default profile is the runtime's nil profile. Edits are validated before they reach native, and permission or setting names a newer engine adds are left out of the listing rather than guessed.

Profile data (ABI39, DEV-647) maps `countBrowsingData`, `clearBrowsingData`, `downloadSettings` and `changeDownloadSettings` onto `ChromiumRuntime`, preparing the profile first and refusing a retiring one. `ChromiumDownloads` adds `removeHistory`, which forgets transfers the sheet picked before the engine cleared, if still finished, from the `DownloadLedger` and throws if the list couldn't be saved (files stay; Chromium's own records are cleared by the engine, so they don't come back at launch).

Site data (ABI40, DEV-633) maps `siteDataIsAvailable`, `siteDataScope` and `clearSiteData` onto `ChromiumRuntime` the same way.

Docked DevTools (ABI42, DEV-733): the engine keeps each page's docked frontend view behind the page in the page's host, filling it, with the page at the bounds DevTools reports, whenever the page is mounted, staged or removed and whenever `onDeveloperToolsLayout` fires. So DevTools hides and returns with its tab, and each pane, Peek and Little Arx page has its own. Activating a pane leaves keyboard focus in its DevTools. Engine commands `.toggleDeveloperTools`, `.showDeveloperToolsPanel` and `.inspectElementMode` drive it; `dockedDeveloperToolsView(_:)` serves the smoke.

Profiles load on demand and go when idle (DEV-880). Every client call that works in a profile prepares it first; the runtime counts each preparation and each finished settings, import or download-start request as a use, and holds the profile while that request is in flight. `releaseIdleProfiles(usedByApp:gracePeriod:)` adds the engine's own uses (pages, including ones still opening, unfinished downloads and downloads Chromium hasn't listed since the profile loaded, held work, retirement in progress) to the app's, lets `ProfileRelease` pick the profiles unused for the grace period, and asks the runtime to release them. A profile's grace period starts when the last sweep saw it in use. While a profile isn't loaded, its pages show the site icon Arx stored for them, or none, instead of loading the profile for an icon; the sidebar pager keeps other spaces' tabs mounted. When the runtime reports the profile prepared (`onOrdinaryProfilePrepared`), those icons are invalidated and read from Chromium. `loadedProfiles` lists what's loaded now.

Tab unloading (DEV-873): `client.unloadTab` refuses a tab whose page is opening or mounted in a window (shown, or staged behind the shown one), then calls `ChromiumRuntime.unload` with the matching reason; the engine applies Chrome's discard rules and its own. `client.snapshot` reads `isUnloaded` live from the engine, since the page's own report arrives after a posted task, and leaves `documentRevision` nil while it's unloaded. `open` of a tab whose page is unloaded calls `restoreUnloadedPage`, so selecting it, a folder's Open or an agent's `load` loads its current entry, keeping its history. An unloaded page is never staged behind the shown one, so hovering its tab doesn't load it. `client.tabHoldsUnsavedInput` (DEV-1107) reads `ChromiumRuntime.unloadBlockers(page, .windowClosed)` for `unsavedInput`, false while the page opens or on an engine without the answered exports.

DEV-898, DEV-892 and DEV-924 add engine exports outside the ABI table, looked up with `dlsym` like per-tab volume: the process table and End Process, download pause, resume and removal, and request details. `ChromiumDownloads` reads each transfer's control bits on every change, and `removeHistory` and Move to Trash also remove the transfer from Chromium's history; the ledger ignores late notifications for a transfer removed this session.

DEV-884: site settings map the engine's `ads` rows to `SiteSettings.contentBlockingOff` and `setContentBlocking` edits to an Ads ALLOW rule or its removal; the extensions client's `setContentBlocking` calls the runtime's optional export. DEV-890: `appendLinkExtensionItems` passes the app's link `NSMenu` to the engine for a current link context.

Back/forward history (DEV-878, `TabNavigationStore.swift`): after `keepNavigationHistory(in:keeping:)`, which forgets the files of tabs neither in the workspace nor in its archive, the engine saves an ordinary tab's back/forward entries (`ChromiumRuntime.navigationState`) 2.5 s after its page last changed and again as the tab closes, one file per tab in a folder per profile (`Navigation/<profile>/<tab>.navigation` beside the workspace), written on a background queue and flushed by `closeAll()`. `cloneNavigation` saves a tab's history under a duplicate's or reopened tab's identity at once, so it survives a relaunch before the copy is shown. Opening a tab takes its file and restores it before the first load when it ends at `reopeningURL`; otherwise the tab opens afresh, so a pinned tab reset to its saved page starts clean. `forgetNavigation` removes a profile's folder for Clear History, reading it as gone at once even while the removal is queued, and its open tabs save nothing more until they close. An authorized close (MCP) reads the history before consuming the page, and `discardNavigation` removes a reset saved tab's, so it reopens at its saved page alone. Private tabs are never saved or restored.

`onPageSettled` reports each ordinary page, shown or not, when it finishes loading at a different URL or title than it last reported (loading and failed states are skipped; a closed tab starts afresh). The app keeps the tab's own URL and title with it, so a tab no window shows (an agent's, a background one, or a restored one moved along its history) doesn't keep the title or URL it had when it was last shown, and its saved history still ends at the URL the tab reopens.

Unread badges (DEV-907): every page, background ones included, reports its badge through `onUnreadBadge` when it changes: the Badging API's while set (`ChromiumRuntime.onPageBadge`, which the engine clears when the page commits a new document), else the one its title shows (`UnreadBadge(title:)`, read on each navigation update). A closed page's state goes; the app keeps its last report.

DEV-1293: the client's `setSharedHistory` tells a tab's page whether the tab's WebKit page is right behind or ahead of it, and `onSharedHistorySwipe` reports a swipe released that way, for `PageEngineRouter`.

Hosted page prompts (DEV-963): `onPagePermissionPrompt` reports a tab's prompt token, or 0 when it's withdrawn, from `ChromiumRuntime.onPagePermissionPrompt`; the client's `setPagePromptsHosted`, `pagePermissionPrompt` and `answerPagePermissionPrompt` map to `ChromiumRuntime` and `ChromiumPage`. `PageEngineRouter` sends WebKit tabs none. Dark pages (DEV-1020): `darkPagesAreAvailable` and `setDarkPages`, one `DarkPagesConfiguration` for every page (`ChromiumBrowserEngine+DarkPages.swift`). A change goes to every open page; a page gets it as it is created (`setPage`) or adopted, with its profile's off sites, before its first site loads. The engine ignores a configuration it already has. Private pages are darkened with no off sites.

Hovered links (DEV-1111, ABI60): `onLinkHover` maps `ChromiumRuntime.onLinkHover` to the tab, as a `BrowserHoveredLink` with its profile and whether it's private, and `linkStatusView(_:)` is the open page view the link status shows over.

DEV-1144: `ChromiumPageMedia.swift` maps the page media bridge to tabs (`setPageMediaBridge(origins:script:handler:)` gives `PageMediaMessage`s with the tab, and `sendPageMedia(_:to:in:)`). `onAudioMutedChange` reports a tab muted or unmuted through the engine, and `onPageRemoved` a tab whose Chromium page went, so FairPlay audio played outside Chromium follows both. DEV-1151: `setPageMediaKeepsRunning(_:document:in:)` keeps a tab's page out of Chromium's freezing while its document's media plays outside Chromium. DEV-1147: `outsideMedia` names the tracks tabs play outside Chromium (`OutsideChromiumMedia`). `ChromiumMediaAdapter` shows each as its tab's media source in place of whatever Chromium reports for that tab, under a generation with the top bit set, so none collides with Chromium's; its revision moves on with every change, so a control for an older state is stale. Its controls go to `performOutsideMedia`, never to Chromium, `isSourceCurrent` asks only whether it's still shown, and the tab's position read names it, without a position, and keeps Chromium's mute. A private tab's, or one without an ordinary page, never shows.

## Profile storage aliases (DEV-1216)

Every profile handed to the runtime goes through `Profile.ID.chromiumProfile(legacy:)` (`ChromiumProfileStorage.swift`), and every profile the runtime reports comes back through `Profile.ID.chromium(_:legacy:)`: a profile merged into iCloud's uses this Mac's alias for its storage (`BrowserCore.ProfileStorageAliases`), and the profile whose storage is Chromium's Default directory, the legacy profile's or the one aliased to it, is `nil`. Retirement records map back the same way, so retiring a profile with an alias erases the storage it uses. A merged profile's transfers in the downloads ledger move to the kept profile at the next configuration (`DownloadLedger.reassign`), since Chromium reports them under it now.
