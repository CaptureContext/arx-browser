# FairPlayBridge

FairPlay in Chromium tabs, the app's side (DEV-1144). Behind the `ARX_FAIRPLAY_IN_CHROMIUM` feature flag (on by default) for the origins in `BrowserCore.FairPlayInChromium.origins` (Spotify's web player for now).

- `FairPlayBridgeScript.source` is `Resources/FairPlayBridge.js`, which the engine's page media bridge runs in the main world of those pages at document start (`ChromiumBrowserEngine.setPageMediaBridge`). It offers the page FairPlay (`com.apple.fps.1_0`) and refuses Widevine and PlayReady, so Spotify's player, which prefers Widevine, falls back to FairPlay as in Safari. When the page sets a media element's source to an HLS `data:` playlist with an `skd://` key, the script takes the element over if the page made Arx's FairPlay keys, whether or not it gave them to that element (Spotify may play a track in a player it made anew); such an element's `mediaKeys` then reads them. A `<source>` given the playlist before it's in a media element waits for the element it's put in, which takes it over as soon as it's inserted (by any DOM call that inserts a node, or, by any other route, at the next check: on the next task, then every 250 ms for as long as a track may take to become ready), loses it if its `src` is removed first, or the page loads or plays it, even an element that holds the previous track; a clear playlist, or one the bridge then declines, gets its `src` as usual. A FairPlay playlist the script can't take (no FairPlay keys in the page, or no certificate yet) sends `failed` at once, so the app falls back rather than leave Chromium with a track it can't play. Once taken over: the playlist (in parts of 30 000 characters) and the page's server certificate go to the app, an `encrypted` event marked `fromPolyfill` (which Spotify waits for) starts the page's key session, the helper's key requests reach the page as `license-request` messages, and its licence comes back through `update`. The element's state getters, `play`, `pause`, `load`, seeking, volume and mute follow the helper; `navigator.mediaSession` metadata feeds Now Playing, and its action handlers take the media keys. An element taken over while its own player plays an ordinary source, such as an ad, is paused natively first, so only the helper is heard, and from then on none of the element's own (trusted) media events reach the page, which hears only the helper's; a capturing listener stops them before the page's listeners (DEV-1158). It's the first capture listener on every target the page listens on for a media event (the window, the element, and an outside-the-document element's ancestors), since `EventTarget.prototype.addEventListener` registers it ahead of the page's first one there. The native pause still rejects a `play()` promise of the old source that hadn't settled, as any pause does. Every replaced API is a `Proxy` of the original, so it still reads as native code. Audible playback needs the person's gesture, as Chromium's autoplay policy asks.
- `FairPlayBridge` pairs that page with Arx's FairPlay helper (`FairPlayHelperConnection.live`, the `ArxFairPlay` app in `Contents/Helpers`, started on first use). It assembles and checks the playlist (`FairPlayPlaylist`), numbers each track for the helper and maps its events back to the page's generation, and keeps one owner: a tab's document. Another tab that loads a track takes the player and the first is told to pause (`stolen`). A message from any other tab or document is dropped, and an event for a document that's gone stops the track.
- A track that fails (no key within 30 s, a playback error, a helper that couldn't start or died, or the page's own 45 s wait for it to become ready) is reported once through `onFailure`. The app then moves the tab to WebKit, where FairPlay plays natively, and keeps that site in WebKit for the rest of the run.
- `setMuted(_:tab:)` follows the tab's mute; `pageGone(_:)` stops a closed or moved tab's track; `playingTab` and `onPlayingChange` say which tab plays, since Chromium itself plays nothing there; `isPlaying(_:)` also counts a track the page asked to play while it loads or buffers, so the app never unloads that tab, but not a paused one. A failure for a document that's gone isn't reported: the tab may show another by now. A private window's track shows in Now Playing as "Arx" only (`FairPlayMetadata.privateTrack`), as Chromium names an incognito page's media by its product: no title, artist, album or artwork leaves the window. `onHolderChange` names the document that holds the helper's track, playing or paused, which the app keeps out of Chromium's freezing meanwhile, so its script still answers licence renewals and Now Playing's commands (DEV-1151). `track` and `onTrackChange` say which tab's page holds the helper's track, its number, the page's media session title and artist (only "Arx" for a private window's), and whether it plays or was asked to; the app shows it on the tab's speaker and the Media page, whose play, pause, next and previous reach the page's own player through `control(_:tab:)`, as Now Playing's commands do (DEV-1147).

Diagnostics: every step goes to `FairPlayLog` (subsystem `dev.capturecontext.arx`, category `FairPlay`), from the app and from the helper process (`ArxFairPlay`). The script sends its own steps as `trace` messages (`FairPlayTrace`), each name at most 8 times a page. To see where a track stops, filter Console on the category, or run `log stream --level info --predicate 'category == "FairPlay"'`.
