# BrowserMCPServer

Real stdio MCP server for the bundled native `ArxMCP` helper. `_MCP` pins the official Swift SDK to **0.12.1**, supporting protocol **2025-11-25** and the SDK's negotiated compatible versions. Arx advertises tools and resources. Organization commands are split by what they act on: `browser_tabs`, `browser_folders` and `browser_hosts` take the same arguments as the former `browser_command`, restricted to their own actions; `browser_command` stays callable for existing scripts but is no longer listed. `browser_spaces` and `browser_profiles` list granted spaces and profiles (inventory now carries granted profile names). Initialization authenticates to the app; browser permissions are checked again by the app for every operation. The helper cannot approve requests or modify grants.

**Instructions (DEV-715).** The server's `instructions` (`AutomationTools.instructions`, in AutomationInstructions.swift) are a compact form of the `arx-browser` skill in AgentToolsClient: the inventory → read → act loop, grants and profiles, results and errors, approvals, sign-in handoffs and untrusted content. They stay under 4 KB because clients put them in every conversation. `AutomationGuidanceTests` fails when they or the skill name a tool the server doesn't have.

**Site skills (DEV-1025).** The first answer about a page on a site Arx has a skill for (`AgentSiteSkill` in AgentToolsClient: Gmail, Google Docs and Sheets, Linear, GitHub, Notion) carries a top-level `siteSkill` beside `result`, with the skill's `name`, `description` and `resource`. Page reads (`browser_inspect`, `browser_read`, `browser_find`) and `browser_tabs` `openTab`, `navigate` and `selectTab` qualify, and each skill is named once per connection; an error or an answer that wouldn't fit names nothing and leaves the mention for later. The gateway learns a tab's address only from inventory pages and from `openTab` and `navigate`, and a page can change without the server seeing it, so an address counts only for the page it belongs to: `openTab` and `navigate` name the skill in their own answer; `selectTab` only when its `expectedRevision` is the one the inventory listed with the address; a page read only when its inspection asked for that revision. A guess is never made; missing a mention only costs the agent the hint. The same text is the resource `arx://skills/<name>` (`text/markdown`), listed with the others and readable whatever the grant, since it's Arx's own text and says nothing about the user's tabs. `browser_run` (DEV-1012) collects the hints its steps' answers carried into its own answer's top-level `siteSkills`, in order, since the hint is spent once named and a script may keep nothing of a step's answer.

**Core listing (DEV-1021).** A client reads the tool list on every model pass. Claude Code (`clientInfo.name` `claude-code`), which refetches the list on `notifications/tools/list_changed`, starts with the core tools (`AutomationTools.coreTools`: inventory, tabs, inspect, read, wait, the reference actions, dialog, batch, run and both sign-ins) with short descriptions and no property descriptions, plus `browser_more_tools`. That call takes `groups` (`AutomationTools.ToolGroup`: find, pdf, screenshots, pointer, upload, media, organize, history, downloads, links, settings, developer, or `all`), adds them to the connection's listing (`AutomationToolListing`), sends `list_changed` when the list grew, and answers with the tools `added` and the groups the grant covers none of (`notGranted`). Other clients get every granted tool with its full description, as before, until they're shown to follow `list_changed`; `ARX_MCP_TOOLS=core` or `all` in the helper's environment decides for any client. Listing stays advisory: a granted tool works whether or not it's listed, and the grant still limits every group. `make agent-evals ARGS='--tools core|all'` measures both.

**Management.** `browser_tabs` also adds, reorders and removes Favorites, updates a pin's saved URL and deletes saved entries; `browser_folders` ungroups and deletes folders; `browser_spaces` creates, renames, themes, reorders, deletes and shows spaces; `browser_profiles` creates, renames and deletes profiles; `browser_windows` lists windows showing a granted space, focuses them and opens, swaps or closes Split View panes. Spaces, profiles and windows answer `action: "list"` with read alone. Profile and space changes need the browser admin class and go through the Settings transaction (`OrganizationChange`): sessions they remove must allow closing first, and the last space can't be removed. Deleting a space can first move its contents into a same-profile `destinationID`. Profile items (the targets of profile and space management) appear in inventory only for whole-profile grants, and a created profile isn't granted until the user grants it. Deleting a profile runs the profile retirement path and needs a profile without spaces. Favorites, saved-entry and folder edits commit through the sidebar's Undo. A `moveTab` into another profile's space reopens the URL and saved metadata there through the sidebar's transfer (the source closes only after its page allows it); every other cross-profile move still returns `crossProfileTransferUnsupported`. Commands that complete through other features' effects settle by observing the expected result, polling every 100 ms for up to 5 s. `browser_windows`' `openSplit` takes optional `splitTabs` (one to three `{id, revision}` tab items) and `orientation` for a Split View of 2–4 open tabs of one space; both join the mutation binding only when set. With independent windows (DEV-1157), inventory gives each open tab the `windowID` of the window that keeps it, and windows carry `isMain`; `openTab` takes an optional `windowID`, a listed window (or the main window's ID), that keeps the new tab; it never combines with `route`, and joins the mutation binding only when set. The skill describes both (version 15).

**Browser data.** `browser_history` (history class) searches visited pages and `browser_downloads` (downloads class) lists downloads, both for whole-profile grants only; private downloads never appear. `browser_archive` lists Tab Archive entries of granted spaces or whole profiles. All three page with a cursor bound to a fingerprint of the filtered list, so a page never mixes two versions (`staleCursor`), and URLs are sanitized as in inventory. `restoreArchived` reopens an entry through the archive's own model transaction with the main window's Undo; when the original space is gone it returns `routeUnresolved` until the client names a granted `destinationID`, and the entry leaves the archive, so a retry finds nothing. `startDownload` (DEV-670) targets a profile item with an http(s) `url` and returns the new download's automation ID as `targetID` once the transfer exists; it is the mutate tier, asks every time unless the client's standing policy skips mutations (a temporary grant doesn't cover it), and can't be a batch step. Chromium chooses the destination and applies its usual prompts and safety checks. `cancelDownload` and `revealDownload` act on a download's automation ID. `browser_links` cleans tracking parameters, applies the user's Proxy Link rules, or resolves a bang through the user's search shortcuts and then the bundled !bang list, the same lookup as the command bar; it returns text only. `arx://downloads` is a subscribable resource. `browser_capture` saves to a folder the person picks (see Saving captures).

**Settings (DEV-666, DEV-706).** `browser_settings` needs the browser admin class. `read` returns one section with a revision: `preferences` (the `AutomationPreferenceKey` allowlist with each key's type, choices or range), `routing` (Air Traffic Control rules whose destinations the grant covers, `hiddenRules` for the rest, and a granted fallback), `searchShortcuts`, `keyboardShortcuts` or a whole-profile grant's `extensions`. `testRoute` reports where a URL would open without opening it; a matching rule outside the grant reports only `hiddenRule`. Every other action is a change: it takes an `operationID` and the section's revision as `expectedRevision`, follows the approval policy (mutate tier; deleting a rule or shortcut is destructive), can't be a batch step, and answers with the section's new contents. Preference values are checked against their schema; a protected setting (`developerModeEnabled`, `automation` and the rest of `AutomationPreferenceKey.protectedNames`) answers `protectedSetting` from the helper, and a value outside its schema `invalidValue`. Keyboard shortcuts keep Settings' rules: reserved chords answer `shortcutReserved`, and a chord another command uses answers `shortcutConflict` unless `replace` is true. A duplicate search keyword answers `shortcutConflict`. Extensions can be listed (with `canInstall`), enabled and disabled. `installExtension` (DEV-951) takes `profileID` and a Chrome Web Store item as `extensionID` or `url` (an item page on `chromewebstore.google.com` or the old `chrome.google.com/webstore`; `BrowserWebstoreInstallRequest.extensionID(fromStoreReference:)`); anything else answers `invalidValue`, both or neither `invalidRequest`. It is `alwaysAsks` and `asksInExtensionReview`: the Extensions sheet's install review is its approval, it can't be a batch step, and an Arx that can't install store items answers `installationUnavailable`. The result carries `installation` with `outcome` (`installed`, `declined`, `alreadyInstalled`, `failed`) and a `reason` for a failure. `sitePermissions` and `zoom` (DEV-716) are read for one whole-profile grant's `profileID`: each permission's default with its `choices` and whether it's `managed`, each site's own settings, and the default and per-host zoom factors with their range. `setSitePermission` takes `profileID`, `permission` (camera, microphone, location, notifications, popups, clipboard), an optional `origin` (normalized to `scheme://host[:port]`; omitted for the default; a listed wider pattern passes as it is, for removal) and `setting` (allow, block, ask, or null to remove the site's own). `setSiteZoom` takes `profileID`, an optional `host` (normalized; omitted for the default) and `factor` (0.25–5, or null to remove). Shapes Settings wouldn't accept answer `invalidValue` from the helper. Allowing a site anything but pop-ups always asks the user, whatever the approval policy or a temporary grant (`AutomationOperation.alwaysAsks`). `browser_spaces` › `setSpaceAppearance` and `browser_profiles` › `setProfileAppearance` take an `appearance` object (null returns a field to inheriting) and `clearAppearance`; listed spaces and profiles carry their own `appearance` override and a `resolvedAppearance`.

**Fewer round trips.** `browser_click`, `browser_replace_text`, `browser_select_value`, `browser_keypress`, `browser_scroll`, `browser_hover`, `browser_drag` and `browser_type` accept `returnSnapshot: true`. After the action the helper reads the tab's current revision and inspects it again; the result carries `snapshot` only when it is the same document the action's snapshot came from (the helper remembers the documents of snapshots it delivered on this connection), and otherwise `snapshotUnavailable` with the reason (`documentChanged`, `unknownSnapshot`, a failure code or `limitExceeded`). The action's own receipt is never dropped to make room. `browser_batch` runs up to 16 steps, each `{tool, arguments}` for an allowed tool, in order. The helper first sends the whole plan (`AutomationOperation.batch`); Arx checks every target against the grant and, when the plan's highest risk tier needs approval under the client's policy, asks once showing every step. A step that then waits for the user past the call's limit ends the call with the steps so far and `waitingForUser` (DEV-1072). The same call again, with the same arguments, goes on from that step: it collects the step's open request without asking for the batch again or repeating the steps that ran. If Arx's 120 s batch approval (`AutomationBatchPlan.approvalWindow`) has lapsed by then, the helper asks once more, for the steps left only, instead of Arx asking for each. The approval binds the exact mutation bindings, in order, to that connection and grant revision for two minutes; each step then arrives as its own request with its own operationID, authorization and receipt, and any other mutation ends the approval. The batch stops at the first failure and never retries; when the combined result is too large, page content and images give way and receipts stay. Every submitted reference action consumes its snapshot except a dispatched `browser_hover` (DEV-669), whose references stay valid while the page's DOM version is unchanged; inspect again (or use `returnSnapshot`) between other actions.

**Resources.** `arx://tabs`, `arx://tabs/{tabID}` and, with the page-content class, `arx://tabs/{tabID}/snapshot` list and read granted tabs and fresh snapshots. `resources/subscribe` follows them: while any subscription is active, the helper polls the IPC `changes` payload (granted tabs' revisions only) with each grant poll and sends `notifications/resources/updated` for changed tabs (navigation, loading, title) and `notifications/resources/list_changed` when tabs join or leave. Subscribing to an ungranted or unknown tab fails; a tab that closes or leaves the grant drops its subscriptions, and losing the read class or revocation ends them all. Download events arrive with the downloads tools.

Tool results are built with `Value(encoding:)` (ValueEncoding.swift, DEV-934) instead of the SDK's `Value(_:)`: the same `JSONEncoder` text read back with `JSONSerialization` rather than the SDK's `Value.init(from:)`, which tries each kind in turn for every node. The result is the same value (`AutomationValueEncodingTests`); a 100-item inventory page takes about 1 ms instead of about 17 ms in a Release build. Data-URL strings stay `.string`, which encodes to the same text.

The bounded stdio transport wraps SDK framing rather than using its unbounded pending-data buffer: one JSON object per line, 64 KiB input, 256 KiB output, 16 in-flight IDs, 128-byte string IDs, 32 buffered messages, 30-second output deadline, serialized writes, no batches and generic malformed-input errors. SDK cancellation reaches the authenticated IPC request. Stdout contains protocol messages only; stderr contains generic configuration/connection failures. All SDK transport logging is disabled.

Supported commands: open a background tab in an explicit space (optional focus), select an already loaded tab, navigate/reload/back/forward/stop an existing session, pin/unpin/move tabs within one profile, move a complete folder subtree into an explicit space root or folder within the same profile, create a root folder, rename a folder, and close a tab through before-unload approval. Ordinary tab closes archive metadata; pins and Favorites unload/reset to their saved destination while retaining their saved entry. Folder moves require grants for both spaces and every descendant; their revision binds the ordered subtree and its ownership. A changed subtree or destination requires fresh inventory and approval. Native sessions, saved destinations and automation provenance are preserved. Commands require explicit IDs, current inventory revisions, read + manage grants and in-app approval unless a scoped temporary grant remains valid. No implicit active-tab targeting. AppFeature serializes mutations, records operation IDs without eviction within the app session (256 attempts per client), and preserves the Sidebar Undo path for organization edits. New tabs record their creating automation client. Navigation reports `acceptedLoading`, not page completion. Cancellation is best effort and cannot roll back a command already dispatched to the browser. An operation ID is not a replay instruction: after a timeout/disconnect, inspect current state rather than repeating the mutation.

Omitted: deleting saved entries, cross-profile transfer (see below), raw DOM, other element actions, full-document screenshots, typing, raw JS/CDP, cookies, passwords, filesystem, terminal, clipboard reading and assistant-provider integrations. These are not advertised as tools. Semantic reads require the native inspection capability; missing support fails closed.

`arx setup claude|codex|cursor` connects an agent from a terminal. It puts `arx` at `~/.local/bin`, asks over a same-user distributed notification, and a person confirms in Arx, so an agent can't connect itself. The client starts with no grants. The credential stays in a 0600 file under `Library/Application Support/Arx/AgentClients`, and the agent's configuration only says `arx mcp --client NAME`. `arx remove` reverses all of it.

Or use **Settings → Advanced → Local assistants (MCP)**. Enable the server, add a client, copy its one-time configuration, then grant selected context. Access is granted in capability classes: read, screenshots, page content, interact, organize and sign-in, all off for a new client (devtools and script are reserved for later tools). Each tool declares the classes it needs (`AutomationTools.requiredCapabilities(forTool:)`), `tools/list` shows only the tools the grant covers, and Arx checks the same classes again for every request. A grant can cover a whole profile, including spaces and Favorites created later. A standing per-client approval policy (always ask, destructive actions only, never) persists across restarts; every action has a risk tier (`read`, `mutate`, `destructive`; only closing a tab is destructive today) that Arx enforces, so a client cannot lower it. Grant edits no longer disconnect: the helper polls its grant every two seconds over IPC (`grants`, which doubles as the keep-alive), sends `notifications/tools/list_changed` when it changes, and requests bound to the old grant revision fail. Revoking a client still disconnects it immediately. An opt-in, default-off focused-tab alias lets `browser_command`, `browser_capture`, `browser_inspect` and `browser_wait` take `"focused"` as targetID and expectedRevision; the helper asks Arx to resolve it (`focusedTab`) when the call runs, only within the grant, and the result's `focusedTab` reports the tab used. Saved clients from before capability classes migrate with the same effective access: page interaction migrates only when the old management toggle was also on, because clicks used to require both.

`make test-mcp` builds the same executable entry point bundled by Xcode and tests it with the official Swift SDK and independent Python SDK 1.26.0 clients against real authenticated Unix IPC. AppFeature tests cover approval, stale state, grant revocation, command serialization and Undo. Connecting a real assistant application to a signed Arx app remains a manual acceptance check.

Primary references: [Swift SDK 0.12.1](https://github.com/modelcontextprotocol/swift-sdk/releases/tag/0.12.1), [MCP stdio transport](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports), [MCP lifecycle](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle), [Python SDK 1.26.0](https://github.com/modelcontextprotocol/python-sdk/tree/v1.26.0).

Before the SDK reads a client's `initialize`, the transport removes `capabilities.experimental` (`BoundedStdioTransport.compatibleHandshake`). The specification lets each experimental capability be an object, but SDK 0.12.1 decodes them as strings only, so Codex 0.167's `"codex/auth-change": {}` made the whole handshake fail, and Codex, which marks Arx's server required, ended every turn before it started (DEV-643). Arx reads none of them. Remove this when the SDK accepts objects.

The stdio transport sets `F_SETNOSIGPIPE` on its own output descriptor. A closed reader produces a bounded disconnected error instead of terminating the helper with a signal; process-wide signal handling is unchanged.

`browser_capture` is an explicit read of a single permitted, already loaded ordinary HTTP(S) page. It requires both read and separate screenshot grants, an exact tab ID and its current inventory revision. It captures only an attached, visible, non-minimized host; a visible non-key window is eligible without changing focus. Entry, native completion and final IPC release recheck grants, current ordinary profile, session/document epochs and host visibility. A hidden, detached, closed/reopened, navigated, revoked or disconnected target cannot release a queued image. The synchronous native document epoch is read from the existing ABI9 close-generation query, before deferred navigation callbacks; it is not a DOM/action revision.

Viewport or a finite positive top-left viewport-point region produces one PNG or JPEG image content block plus matching text/structured metadata: requested inventory revision, decimal-string session/document epochs, native document ID, unique capture ID, pixel/viewport dimensions, scale, format, quality, mode/region and loading status. `scale` (0.1–1) downscales and `format: "jpeg"` with `quality` (0–1, default 0.8) re-encodes in Arx; the native PNG is otherwise delivered unchanged. The image is capped at 4 MiB; replies carrying images use a 6 MiB IPC and MCP frame, every other reply keeps the 256 KiB frame. `limitExceeded` asks for a smaller scale, JPEG or a smaller region; no other resizing, scrolling or filesystem export occurs. Unloaded/hidden pages return `notLoaded`/`notReady`; unavailable native support is `unsupported`. Protected media can be blank. Pixels include visible page content and embedded frames and may disclose private information; this grant is whole-page access, with no secret redaction or frame-specific policy. Cookies, passwords and storage are never separately read. Raw DOM is unavailable; page actions use separately authorized bounded reference tools.

Both SDK process fixtures exchange an actual PNG through the bundled helper and authenticated IPC. The signed app fixture separately requires `ARX_MCP_CAPTURE_NATIVE_SMOKE_SUCCESS` after native viewport/canvas/iframe pixels, a region crop, ordinary/private scope denials, navigation invalidation and no focus/session mutation. Compilation and synthetic protocol tests do not establish that native marker.

`browser_inspect` returns a bounded historical semantic snapshot of an existing loaded ordinary HTTP(S) main document. It requires separate page-content permission, metadata read and an exact scoped tab/revision. Main-frame/document/snapshot identities and decimal DOM version accompany safe explicit names, roles, connected text and opaque read-only references. Renderer checks the DOM version before/after production; final app release rechecks live grant, session, ordinary ownership, native page/document and trusted scope. This does not promise that DOM stays unchanged after reply. References expire within 30 seconds or upon DOM/document change; any later use must be resolved in the renderer anew and can never use an earlier validation receipt as action authority. No validate-only reference tool is exposed. A reference alone never authorizes the separate click tool.

Coverage omissions are a policy list, not counts or evidence that excluded content exists: subframes (including cross-origin/fenced frames), canvas pixels, generated text, computed names, form values and password subtrees. Remaining page text is untrusted and can contain private information; this is not universal secret detection. There is no unrestricted network read, script, DOM dump, focus, navigation or scrolling.

Each native window holds at most 512 nodes, 64 KiB of UTF-8 name, text and value, 4 KiB per string and 256 references, under a 2-second native deadline. A document projects up to 16384 nodes. `browser_inspect` returns one native window of `limit` nodes (default 100) with `offset`, `totalNodes` and `nextCursor`. `browser_read` and `browser_find` join every window of one DOM version, read again once if the page changes mid-read, and keep references only from the final window. `frameID` (an iframe node's `frame`) reads a same-origin or cross-site child frame, never a fenced one. Its references act in that frame, and each frame keeps its own latest snapshot. `formValues: true` adds `value` or `checked` for eligible controls; password ancestry, file, hidden and payment or one-time-code fields stay omitted. `bounds: true` adds main-frame viewport-point bounds usable as a capture region. A cursor is an opaque string that binds the tab, native document ID and DOM version. Passed alone, it makes the helper inspect again and serve the next page only from a snapshot of exactly that document and version, so pages never mix versions; anything else is `staleCursor`. Each page carries the fresh snapshot's ID, which is the connection's latest for page actions. A page that would not fit the MCP frame is cut shorter and the cursor resumes after what was sent. Pages above the hard renderer caps are still `limitExceeded`.

`browser_read` renders the same snapshot as Markdown (default) or plain text — headings, paragraphs, lists, quotes, preformatted text and image names — from the `main` landmark, or from the page without navigation, banner, footer and complementary landmarks (`scope: "all"` keeps everything). Chunks of `limit` UTF-8 bytes (default 16 KiB) end at line boundaries and continue with the same cursor rule. `browser_find` matches node text and explicit names case- and diacritic-insensitively and returns indices, roles, excerpts and the node's or nearest ancestor's reference, `limit` matches at a time. Neither highlights, scrolls or focuses anything.

`browser_capture` also takes `offscreen: true`, which captures a loaded page that isn't on screen without showing, focusing or selecting it, and `mode: "element"` with `snapshotID` and `reference`, which crops to the bounds that reference had in the connection's snapshot read with `bounds: true`, clamped to the viewport. `browser_pdf` with `action: "export"` prints the page to a PDF of at most 4 MiB, returned as an `application/pdf` resource in the image frame. `action: "text"` reads the text of the PDF document a tab shows, in chunks, with a cursor bound to the PDF's SHA-256 digest. Both need the page-content class. `browser_find_in_page` runs Chromium's own find: it highlights matches and moves the active one, and `stop` leaves the selection on it. It needs the interact class and follows the mutation approval policy.

`load: true` on the three reading tools loads an unloaded saved tab first: the helper sends the read-tier `load` operation (page-content class), Arx opens a detached background page for the saved URL without selecting, focusing or attaching it, and the helper waits at most 10 seconds for `loadingStopped`. A tab that already has a page is read as it is. Unloaded, loading, unsupported, expired/stale and canceled operations return bounded errors. Native registries bound pending work and retained references independently.

Browser/OS permission prompts are outside the main-document semantic snapshot and cannot be inspected, accepted or dismissed by these tools. A page-owned overlay remains untrusted document content subject to the same omissions. A renderer blocked by modal work may return a bounded timeout; a failed/loading session reports not-ready, and native renderer loss invalidates document authority. The read never dismisses a prompt, reloads a failed page or silently retries against a replacement document.

`browser_click` provides accessibility activation. It needs the read, page-content and interact classes, exact ordinary tab scope and the same mutation approval used by browser commands. A temporary grant can satisfy approval but never substitutes for an absent interaction permission. Every click may submit a form or change website state; role, label and text do not establish safety.

Requests carry an explicit tab/inventory revision, latest released snapshot ID, opaque reference and unique operation ID. The app retains at most 16 released snapshots for at most 30 seconds, one per connection/tab, only after final authority and delivery-size checks. Eviction, reconnect and grant changes invalidate them. Native latest-created snapshot checks can conservatively reject an older app-released snapshot. The renderer must validate exact document, DOM version, retained reference and eligibility in the same task that initiates the click. No prior asynchronous reference-validation receipt authorizes dispatch. The tool does not focus, load, scroll or grant transient user activation.

Outcomes are deliberately small: operation ID, `notDispatched`, `dispatched` or `possiblyDispatched`, and an optional failure code. `dispatched` means event initiation, never website success or completed navigation. Once submission begins, cancellation, timeout, revocation or connection loss may leave website effects. The authenticated pending request may receive its own minimal uncertainty acknowledgment after revocation; no page content, URL, title or new state is included. A lost reply is not permission to replay. App operation IDs are retained without eviction (256 per client, 4096 total) for the app session; exhaustion fails explicitly. A repeated ID returns the recorded disposition or uncertainty, never another click. Native scope/operation admission is bounded independently.

`browser_wait` is a read-grant-only, explicit-target `loadingStopped` observation, defaulting to 2,000 ms and capped at 10,000 ms. It never loads, focuses, mutates, retries or evaluates page content. A navigation start or commit invalidates its generation, so it cannot follow navigation through commit. `expectedRevision` is checked at entry; `observedRevision` describes the historical match and may differ after permitted loading/title updates. Stopped/error metadata does not prove HTTP success, DOM readiness, network idle or action completion. Refresh inventory before a subsequent revision-bound command.

`browser_replace_text` and `browser_select_value` add bounded whole-value replacement and exact single-select selection to the same reference/grant/approval boundary. Values are never echoed in acknowledgments. They share operation IDs and serialization with clicks and organization mutations; a repeated ID with a different kind, target or payload returns duplicate uncertainty and never borrows a prior unchanged receipt. The native validated unchanged result consumes the operation without setters/events. A repeated receipt describes the original attempt, not the control’s current value. No typing, keyboard, paste, IME, autofill, password, file, contenteditable or implicit-focused-target API is offered. The existing 64 KiB encoded request envelope also applies, so heavy JSON escaping can reject a nominally allowed UTF-8 value before admission; no truncation occurs.

browser_scroll requires explicit operationID, tab, inventory revision, latest delivered snapshot/reference, horizontal|vertical axis and a finite deltaCSSPixels within ±8192. It uses the read, page-content and interact classes and mutation approval. It requests an instant offset in the nearest current native user-scrollable container, stops at its edge without chaining and never selects by focus. Dispatched is not wheel input, snapping/lazy-load completion or website success. Unchanged consumes the shared operation ID; uncertainty forbids automatic replay. Results contain no offsets or page content. The native capability remains unavailable until the live adapter is supplied and accepted.

Inspect again before each distinct scroll action: native submission retires the
snapshot even when the resulting offset is unchanged. Keep the exact original
request only when reconciling its operation receipt; a duplicate never performs
another scroll. The owned bundled-helper fixture checks consumed-reference
rejection separately from replay and navigation invalidation.

The `fullDocument` mode follows the live native/client availability predicate and the same screenshot grant, ordinary-profile, visibility and inventory-revision checks. Its bounded result retains exact document/visible rectangles, fractional scroll, zoom, page scale and one-layout-pixel raster scale separately from viewport/device scale. Unsupported recording resources, unavailable capability and exceeded budgets release no partial image; lazy content is not triggered by traversal. The signed app gate requires actual AppFeature full-document preview/crop/recapture and bundled-helper top/middle/bottom pixels with navigation and scope denial. Acceptance status belongs in Linear.

`browser_keypress` is a separate strict schema with `key`, operationID, explicit
target/revision and latest snapshot/reference. It shares interaction grants and
mutation approval with other reference actions. It supports one permitted Unicode
scalar or Backspace/Delete/arrows/Home/End/Enter on already focused supported
plain controls; modifiers, repeat, IME, physical layout, Tab/Escape and implicit
focus are unavailable. Author listeners may still submit or navigate. Native
defaults are suppressed if listeners redirect focus/selection. Dispatched means
event delivery, possiblyDispatched preserves partial/late uncertainty, and exact
duplicates never replay. The key and field values never appear in receipts.

`browser_sign_in` requests a trusted user sign-in handoff and needs its own sign-in grant plus read. `begin` binds an explicit loaded ordinary tab, its current inventory revision and the exact top-level origin; an embedded frame's origin is a stale target. Unknown arguments, including any credential-shaped field, are rejected. The result is only the operation ID and a status: `approvalRequired`, `securingPrivacy`, `userActionRequired`, `userConfirmed` (a user assertion, not verified sign-in), `cancelled`, `expired` or `blocked`. Only the user can approve in Arx. From approval until the user ends the privacy lock, the authenticated host refuses every other request from every client with `authenticationProtected`, including inventory, inspection, captures, waits, page actions, commands and new sign-ins, and it rechecks the lock before any already-captured reply leaves the app. Status and cancel stay bound to the original client, connection and grant revision. Ending the lock disconnects every client. Only clients the user chose to keep can reconnect, with their original scope and expiry; others must be authorized again. Unattended runs refuse `begin` with `userActionRequired`.

`promotePeekToTab`, `promotePeekToLittleArx` and `promoteLittleArx`. These
inherently visible host operations require explicit `focus: true`; background host
requests (refused by the helper as an `unsupported` tool result, not a schema error), unattended (headless) runs and promoting a borrowed-tab Peek into Little Arx
return `unsupported`; promoting Little Arx into another profile returns `crossProfileTransferUnsupported`. Peek requires `sourceTabID` and its current `sourceRevision` to
identify one exact ordinary owning pane, independently of `targetID`. Without a
URL it borrows the target tab; an explicit HTTP(S) URL creates a temporary preview
in that same profile. A target already displayed in another pane is refused.
Little Arx opening targets an explicit permitted space and HTTP(S) URL.

Inventory results carry `presentations` and command results carry `presentation`
(null when absent). Inventory includes `presentations` metadata only for live handles created by this
client and current helper session. Entries contain opaque identity, kind, tab and
profile IDs, original scope target and a live revision, without URL/title/content.
Refresh inventory after initial loading and before promotion; an outdated
presentation revision returns `staleTarget`. Promotion requires
`presentationID` and `presentationRevision`; Little Arx promotion targets an
explicit permitted destination space in the same profile. Handles expire after
five minutes, are bounded to eight per client and 32 globally, and disappear on
revocation/disconnection. Expiry never closes content. A handle authorizes no
inspection, screenshot, generic interaction or arbitrary temporary-window access.

Source host, pane, profile, native document/session and grant are captured before
approval and rechecked at actual handoff commit. Existing release/close/promotion
handlers retain sole session ownership. Open receipts report `acceptedLoading`
after model publication, without claiming native attachment or website success;
promotion into a space reports `committed` only after actual durable tab
membership exists, while `promotePeekToLittleArx` reports `acceptedLoading` with
the new Little Arx presentation once that window exists. Cancellation cannot undo a completed presentation;
operation IDs still never replay. Final IPC delivery rechecks current authority
and exact operation-owned receipts, including the transient metadata projection.

## Air Traffic Control routing

`openTab` opens exactly in `targetID` and ignores the user's Air Traffic Control
rules unless the request sets `route: true`. The flag applies only to `openTab`
and never combines with `destinationID`/`destinationRevision` (`invalidRequest`).
With it, Arx resolves the URL through the same `URLRouter.decide` the incoming-link
queue and Route URL use: the first enabled matching rule wins, otherwise the
fallback applies. `targetID` stays required: it is the granted source space that
stands in for "current space" rules and the fallback. A focused private window
never supplies the current space, and private spaces are never routing targets.

Routing never widens access. The routed space needs its own grant (`denied`
otherwise). It may belong to another profile, in which case the tab is created
fresh in that profile; nothing is moved. A Little Arx destination opens a Little
Arx through the host-operation path, so it needs `focus: true` and an attended
session (`unsupported` otherwise). No rule, no fallback, or a missing profile,
profile default or space returns `routeUnresolved`. The route is resolved before
approval: the person approves the resolved space and mode, and the run is pinned
to the revision captured then. The flag is part of the mutation binding.

Command results carry `route` (null when the flag was absent): `profileID`,
`spaceID`, `mode` (`mainBrowser` or `littleArx`), `source` (`rule` or `fallback`)
and, for a rule, `ruleID` and `ruleName`.

## Cross-profile transfer

Moving or pinning a tab, moving a folder, or promoting a Little Arx into a space
of another profile returns `crossProfileTransferUnsupported`. Its error result
adds a `message` saying the user can move it to another profile in Arx; other
error results keep the bare `{kind, code}` shape. Whether automation should move
content between profiles is an open product decision.

**Pointer input (ABI27).** `browser_hover`, `browser_drag` and `browser_click` with `x`/`y`, `clickCount` or `modifiers` send real mouse events through the page's own widget, in the same renderer task as the reference check. They use the read, page-content and interact classes and mutation approval, and are parsed into `AutomationFormRequest` pointer kinds (`hover`, `pointerClick`, `drag`) so they share form receipts, bindings and batches. A target is a reference (its visible centre) or a point in viewport points of the main frame (the space of inspect `bounds` and screenshots); a point replaces the reference and is sent with the snapshot's own ID. The point must hit the reference, or for a point the snapshot's document, otherwise the result is `obscured`. Drags press, move in 1–32 steps and release on `toReference` or `toX`/`toY`; HTML drag and drop completes inside the renderer and never starts a macOS drag session. Modifiers are shift, option and command; Control is refused because it turns a click into a context menu. Selects, file and color inputs and password ancestry aren't pointer targets. Clicks and drags are real input and give the page user activation; hover doesn't consume its snapshot.

**Keyboard input (ABI28).** `browser_type` focuses an input, textarea or contenteditable reference and types 1–1024 UTF-8 bytes at the end, one guarded key at a time; a line feed is Enter and is refused for single-line inputs. `browser_keypress` keeps the legacy guarded keypress for its original keys without modifiers. With `modifiers` (shift, control, option, command) or another key (Tab, Escape, Page Up/Down, F1–F12, or any printable character) it becomes a key chord that focuses the reference first. Both parse into `AutomationFormRequest` kinds (`typeText`, `keyChord` with `keyModifiers`) and use the form approval, binding and receipt path. Typed text is never echoed, and nothing is typed while the sign-in privacy lock is on, because Arx refuses every request then.

**Form state (ABI29).** `browser_set_checked` sets a checkbox or radio to `checked` true or false; a radio can only be checked. `browser_select_value` with `values` instead of `value` sets a native multiple select's whole selection to up to 64 distinct exact option values. Both are form kinds (`setChecked` with `checked`, `selectValues` with `values`) on the existing approval, binding and receipt path, and return `unchanged` without events when nothing would change. Values are never echoed.

**Uploads (ABI30).** `browser_upload` answers the file chooser a page opened right after a pointer or keyboard action, with absolute paths, or cancels it with an empty list. It needs the new `files` capability class besides read, page content and interact. It parses into the `upload` form kind with the paths in `values`, so the paths are part of the mutation binding and never echoed. Uploads always ask the user, showing every path, whatever the client's standing or temporary approval (`AutomationOperation.alwaysAsks`), and they can't be batch steps. Missing choosers and unusable paths fail as `noFileChooser` and `fileUnavailable`, with guidance.

**Dialogs (ABI31).** `browser_dialog` reads a tab's JavaScript dialog or website permission request (`read`, with a token, type, untrusted message, a prompt's default text and a permission's origin), and answers that exact one with `accept` or `dismiss`, a token and an operationID. It parses into the new `AutomationOperation.dialog`. Accepting is the mutate tier and always asks the user, showing any prompt text; dismissing is the read tier and never asks. Dialog answers can't be batch steps, prompt text is part of the binding and is never echoed, and a dialog the user answered first makes the agent's answer `staleTarget`.

**Saving captures.** `browser_capture` with `save: true` captures as usual, then Arx shows its own save panel (the PageCapture export path) so the person picks the folder and name. The result's `save` is `{status: saved, fileName}` with only the chosen file name, or `{status: declined}` when the panel is cancelled and nothing is written. The agent can't pass a path or learn the folder. Unattended runs report `userActionRequired`, and authority is checked again after the panel closes and before the file is written.

**Media.** `browser_media` with `action: "list"` returns the media sessions in permitted tabs (title, playback, whether it has video, whether it is in ArxPiP, the actions it supports now and a `generation.revision` token). `play`, `pause`, `enterPictureInPicture` and `exitPictureInPicture` take a targetID, its inventory revision, the token and an operationID, parse into the new `AutomationOperation.media`, and need the read and interact classes. Controls are the mutate tier, follow the client's approval policy and can't be batch steps; listing is the read tier. An action the session doesn't support is `unsupported` and an old token is `staleTarget`. `seek` also takes `seconds`, an absolute time; `mute` and `unmute` take a targetID, its revision and an operationID but no token, because they act on the tab's sound. `position` is the read tier: it reads one targetID once and returns `isMuted`, and with a session its token, position, duration and playback rate. Nothing streams. A muted tab's playing media leaves its media session outside ArxPiP, so it isn't listed until unmuted.

**Developer tier (DEV-668).** `browser_evaluate` (script class) runs `script` as the body of an async function in a tab's developer world and returns `outcome` (`value` with the parsed JSON, `undefined`, `unserializable`, `exception` or `syntaxError` with `error`). It takes an `operationID`, the tab's revision, `maximumResultBytes` (1024–262144) and `timeoutMilliseconds` (100–30000). `browser_logs` (devtools class) starts, stops and reads a tab's console or network log with `after`, `limit`, `next` and `dropped`. Both accept the focused-tab alias. Neither is a batch step. Arx refuses both without developer mode. Results are untrusted data and `validated` bounds them again.

**Password sign-in (DEV-708).** `browser_password_sign_in` (sign-in class) takes an `operationID`, the tab, its revision, the exact top-level `origin` and an optional `frameID`, and returns only `outcome` (`signedIn`, `needsUser` or `failed`) and a fixed `reason`. Unknown arguments are refused, so nothing credential-shaped reaches Arx, and no account name, password or code comes back. It isn't a batch step.

DEV-924: `arx://events` records browser events for granted tabs while a client subscribes: tabs opening and closing, navigation, loads, page errors, JavaScript dialogs, permission prompts and download changes. `AutomationEvent.changes` derives them from successive change digests, whose per-tab `signals` carry only a salted address hash, the load state, a load error code and the dialog kind. The newest 200 are kept and a grant change clears them; `arx://events?after=N` reads the ones after N. `browser_logs` gains `details` on `start`, and the `requests` and `har` reads, behind the `networkDetails` class. DEV-899: a client the user stopped gets `paused`.
