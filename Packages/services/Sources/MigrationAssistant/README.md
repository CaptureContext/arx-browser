# MigrationAssistant

Service contracts and the execution engine for importing browser data. It has no views and depends only on BrowserCore and the dependencies wrapper; it never imports features or AppUI.

Arc, Google Chrome and Dia are offered, alongside files the user picks: an Arx archive or a bookmarks HTML file. Brave, Edge, Helium, Chromium, Opera, Opera GX, Vivaldi, Island, the beta, dev and canary channels of Chrome, Edge and Brave, Firefox, Zen, Safari and Chromium open tabs are offered too, though each still needs its real-browser check (DEV-651, DEV-840, DEV-896); see [Unchecked sources](#unchecked-sources). Safari also needs Full Disk Access; see [Safari](#safari). `MigrationAssistantClient.liveValue` offers whichever of them it finds on this Mac and writes through `MigrationWorkspaceBridge`, which AppFeature serves. Passwords and sign-ins have their own protected flow, outside the ordinary categories; see [Passwords and sign-ins](#passwords-and-sign-ins).

## Contracts

`MigrationAssistantClient` is the dependency used by features:

- `discover` lists sources that registered adapters can read.
- `inspect(source, categories, destination)` reads a snapshot and returns a `MigrationPreview` without writing anything: per category, the importable items, items already received and what can't be imported, plus the source's spaces.
- `execute(plan)` streams `MigrationEvent.progress` and ends with exactly one `finished(MigrationReport)`, or throws a `MigrationFailure` before any commit.
- `cancel(planID)` asks a running plan to stop at the next category boundary. The stream still ends with a `cancelled` report.

`MigrationAssistantClient.running(adapters:writer:)` builds a client from `MigrationSourceAdapter` values and a `MigrationDestinationWriter`. Tests use it with fixture adapters and an in-memory writer.

## Sources

`MigrationSource` has a stable adapter-defined ID, a kind (external browser, Arx archive, older Arx settings), a name, an optional version and the categories it can read. External browsers and Arx data use separate adapters; DEV-562 owns the Arx archive and bookmarks HTML adapters and reuses these contracts.

An adapter returns a `MigrationSnapshot`: an ID for the exact data read, a list of unvalidated `MigrationRecord`s, and issues for what the source holds that Arx can't represent. Adapters read individual files. They leave source data unchanged, never open another browser's profile as an Arx profile, and don't read its credential stores. Only the passwords and sign-ins flow does that.

- **Arc** reads `StorableSidebar.json` and the profile names in `User Data/Local State`: favorites, pinned tabs and folders, and open tabs, per profile and space. The format is Arc's own and undocumented, so an unknown file is reported as unreadable. Split views become their tabs side by side. Easels, notes and welcome tabs are reported as not imported. Each space brings its colors (DEV-897, DEV-919's mapping; `ArcSpaceTheme`): `customInfo.windowTheme`'s `primaryColorPalette.midTone` (or the first color found) becomes the space's tint and the first `baseColors` list's second and third colors its gradient stops, each through `ChromeTint(approximating:)` (hue from the color's direction in the plane Arx turns tints in, intensity from its saturation), at Arx's default angle; a `colorScheme`, `appearance` or `isDark` key, if the theme has one, sets light or dark. Arx keeps colors as hue plus intensity, so this is close, not exact. Favorites and pinned tabs bring their icons (`ChromiumFavicons`) from each profile's `Favicons` database, read from a copy: the page's own favicon or the newest one on its origin, a PNG up to 64 KiB at the smallest width of at least 32. Icons ride on `MigrationRecord.icon` and `MigrationItem.icon`, outside the snapshot ID. Since DEV-845 it also reads each profile's history and installed extensions; see [Chromium history and extensions](#chromium-history-and-extensions).
- **Chrome and Dia** read each profile's `Bookmarks` file in Chromium's format, and its history (DEV-845). Every Chromium browser other than Arc is a row of `ChromiumBrowser.all` (DEV-896): its folder in Application Support, bundle identifier and Keychain item, read by the same adapter. Helium's folder (`net.imput.helium`) and item (`Helium Storage Key`) come from its own patches in the engine checkout, and Chrome's channels share Chrome's item; the others' items are assumed from Chromium's pattern and marked unverified. Opera and Opera GX keep their one profile in the user data folder itself, so a `Default` profile without a folder of its own is read from there, and a `Local State` that lists no profiles gives that one. Each profile becomes one space, with the bookmarks bar at its top level and other bookmarks in their own folder. The Chrome reader was tested against made-up files in that format, because Chrome's folder wasn't readable when this was built, and Dia's location and format are assumed from Chromium's rather than checked against an installed copy.
- **Chromium open tabs** (`ChromiumSession`, unchecked) replay the newest complete cleartext `Sessions/Session_<timestamp>` file of each profile (one with the initial-state marker, as Chromium picks it), following Chromium 156's `session_service_commands.cc`: tabs of normal windows, in window order and then visual order, at their current page. Popups, app and DevTools windows, and closed tabs and windows are left out. Pinned tabs stay open tabs. Chromium's tab IDs change every launch, so a tab is identified by its URL and how many times that URL came before it. Files encrypted with the Keychain key (version 5, `Sessions_Encrypted`) aren't read; Chromium 156 still writes a cleartext copy beside them. Fixtures are written by the tests from the documented layout: no Chromium build that writes session files was available without screen work.
- **Firefox** (`FirefoxPlaces`, unchecked) lists profiles from `profiles.ini`, the installed app's default first, and reads each profile's `places.sqlite` from a copy (bookmarks, and since DEV-896 history: `moz_places` rows visited at least once and not hidden, web pages only, at their latest visit, newest first, left out of the snapshot ID like Chromium's): the database and its write-ahead log are copied to a temporary folder (again if either changed during the copy), the copy is opened, and the folder is removed. Each profile becomes one space: the Bookmarks Toolbar is its top level, and the Bookmarks Menu, Other Bookmarks and Mobile Bookmarks keep folders of their own. Tags and separators are skipped, and `place:` queries are reported as invalid. Open tabs come from `sessionstore-backups/recovery.jsonlz4`, or `sessionstore.jsonlz4` after a clean quit, in Mozilla's `mozLz4` container; hidden tabs are left out.
- **Zen** (`FirefoxSession`, unchecked) reads the same `places.sqlite` and maps Zen's own layout: each Zen space becomes a source space with its name and emoji icon, Essentials become the profile's favorites, pinned tabs and their nested folders become bookmarks (returning to the page they were pinned at, with the current page kept), and other tabs open tabs. Folders and tabs keep Zen's order (`prevSiblingInfo`, or the pins' positions); a folder no pinned tab recreates gets a record of its own. Glance previews and empty placeholder tabs are skipped. Zen 1.18 and later keep this in `zen-sessions.jsonlz4`; older versions kept it in the `zen_workspaces` and `zen_pins` tables, which are read when the session file has no spaces, with their other open tabs from Firefox's session file and its `zen-workspace-id` tab attribute. Zen's Firefox bookmarks get a space of their own named Bookmarks.
- **Safari** (`SafariData`, unchecked) is offered whenever `~/Library/Safari` exists and reads only with Full Disk Access; see [Safari](#safari).

Each browser source carries its app's bundle identifier and `lastUsed`, the modification date of the file its adapter reads (Arc's sidebar file, Chromium's `Local State`), read from file attributes without opening the file. Onboarding uses them to preselect the default or most recently used browser. `MigrationBrowserSources.unsupportedBrowsers()` lists browsers that aren't offered so they can be shown, never read: with unchecked sources off, Safari always, and Firefox and Zen when their support folder exists. With them on (the default) it's empty. The client exposes the list as `unsupportedBrowsers`.

### Unchecked sources

Each source needs its own check against the real browser. Firefox, Zen, Safari and Chromium open tabs haven't had theirs yet, so `adapters(includesUnchecked:)` and `unsupportedBrowsers(includesUnchecked:)` keep them apart. They're offered by default (DEV-840): the live client passes `offersUncheckedSources`, which is on unless the app's `MigrationUncheckedSources` default turns it off:

```sh
defaults write dev.capturecontext.arx MigrationUncheckedSources -bool NO
```

`ARX_MIGRATION_REAL_SOURCES=1` enables a test that reads every source on this Mac, unchecked ones included except Safari, and prints only counts. Once a source passes its check, move it out of the `includesUnchecked` branches.

Snapshot IDs hash what was read, not the file, because browsers rewrite these files for unrelated reasons.

Folders, spaces and profiles without a tab are records of their own (`MigrationItemKind`), so empty ones are recreated and spaces keep their order.

## Chromium history and extensions

DEV-845. `MigrationBrowserSources.chromiumProfileData` adds each `Local State` profile's data to the snapshot (Arc's `__ARC_SYSTEM_PROFILE` is left out, as everywhere):

- **History** (`ChromiumHistory`) reads `<profile>/History` from a private copy with its `-journal` and `-wal` (`FirefoxPlaces.withCopy`), because the browser locks the file while it runs: the `urls` table, one record per page at its latest visit, newest first. Hidden rows (subframes, redirects) and rows never visited are left out. `last_visit_time` counts microseconds from 1 January 1601 UTC. Records belong to their source profile, so they follow its mapping into that Arx profile's history, as Safari's and Arx archives' do. Arc, Chrome, Dia and the unchecked Chromium browsers offer `.history`.
- **Extensions** (`ChromiumExtensionSettings`, Arc only) come from `extensions.settings` in `Preferences` and `Secure Preferences` (the secure copy wins per key): ID, name, version and the source profile. Component extensions (locations 5 and 10) and ones installed by default or by the OEM are left out. One is from the Chrome Web Store when `from_webstore` or the `FROM_WEBSTORE` creation flag says so and it isn't unpacked or from the command line. A `__MSG_name__` name is looked up in the installed copy's `_locales` (the current language, then the default locale, then English). Each becomes a `reinstallManually` issue in `.extensions`.
- **Snapshot ID.** The browser writes its history and preferences on every visit, so they're left out of the snapshot ID, which stays the sidebar's (or the bookmarks'). Both merge by key, so newer rows at commit time do no harm, and an import isn't refused as `sourceChanged` because Arc kept running.

Extensions still commit nothing here. A Web Store extension with a source profile (`MigrationIssue.Extension.installsFromStore`) is installed afterwards by `MigrationAssistantFeature`'s `ExtensionImportFeature`, through the engine's install by ID and the user's review of each; `MigrationPreview.extensionProfiles` names their source profiles, and a plan built from the preview makes those Arx profiles even when no category brings anything there. The rest are listed to reinstall by hand.

## Safari

DEV-840. macOS protects `~/Library/Safari` and Safari's container with Full Disk Access, so the Safari source carries `requiresFullDiskAccess` and is offered whether or not Arx has it. `FullDiskAccessClient` (the `fullDiskAccess` dependency) answers whether `~/Library/Safari/Bookmarks.plist` opens now (it's opened and closed, never read) and opens System Settings at Privacy & Security › Full Disk Access (`x-apple.systempreferences:com.apple.preference.security?Privacy_AllFiles`). `FullDiskAccessStatus` is `unknown`, `denied` or `granted`; features check when Safari is selected and when Arx becomes active, and inspect only once it's granted. Without access, the snapshot throws `unreadableSource`.

`SafariData` reads, with the databases opened from private copies like Firefox's:

- **`Bookmarks.plist`**, shared by every Safari profile: the Favorites bar's links become the default profile's favorites; its folders, the Bookmarks Menu (at the top level) and other top-level folders become bookmarks in a space named after the profile, with their folders. Reading List becomes a folder there, and links directly under the root are bookmarks too. The History proxy is skipped.
- **`SafariTabs.db`**, in `~/Library/Containers/com.apple.Safari/Data/Library/Safari` (or beside the bookmarks on older Safari); without it only bookmarks and the default history are read. Its `bookmarks` table holds tab groups, profiles and tabs (`type` 1 folders, 0 tabs): top-level folders with `subtype` 0 are the default profile's tab groups and with `subtype` 2 profiles, whose tab groups sit in a `subtype` 3 folder under them. Each profile becomes a source profile, each tab group a space in its profile with its tabs as open tabs, and the ungrouped tabs of open windows open tabs in their profile's space: the window's `local_tab_group_id` (its profile, else `active_profile_id`) and each hidden group `windows_unnamed_tab_groups` lists for it, owned by the profile folder it sits under or by the default profile at the top level. After Safari quits, the windows it restores (`is_last_session`) are read. Private windows, hidden groups and deleted rows are left out. The layout comes from the SQL in macOS 27's SafariShared, not from documentation.
- **`History.db`** for the default profile, and `Profiles/<server or external ID>/History.db` for each other profile (assumed from SafariShared's log strings): one entry per page at its latest visit, titled from that visit. `visit_time` counts seconds from 2001.

Safari is named "Safari" as the default profile. Group tabs are identified by Safari's tab ID; window tabs, which Safari recreates each session, by URL and occurrence. Passwords live in the Passwords app, which other apps can't read; the credentials step explains exporting a CSV from it instead. Sign-ins come from `Cookies.binarycookies` (DEV-896); see [Passwords and sign-ins](#passwords-and-sign-ins).

## Arx archive

`ArxTransferArchive` is one JSON file, written atomically to where the user chooses:

- `format` is `dev.capturecontext.arx.transfer` and `version` is 2. Version 1 files still import. A newer version or a different format is refused before anything changes. Files over 64 MB aren't read. It's a single file, so there are no paths to check.
- `createdAt`, `appVersion` and `categories` describe the export.
- `profiles` hold a name, search engine, appearance and favorites. `spaces` hold a name, icon, appearance, `pinned` (tabs and nested folders, in order) and `regular` tabs.
- A tab has `savedURL` and `title` when pinned, and always `currentURL` and `currentTitle`, so where a pinned tab returns to and where it last was both survive. `customTitle` is the user's name for it.
- `preferences` holds appearance, search shortcuts, key bindings and link rules.

Version 2 adds three optional sections:

- `history`, only when the user includes it: each profile's history, newest first, with each entry's URL, title and last visit.
- `archivedTabs`, only when the user includes it: Tab Archive entries with their closing time, group, original space and position.
- `extensions`, always: each profile's installed extensions as ID, name and whether they came from the Chrome Web Store. No extension files, settings or data.

It holds no cookies, sessions, passwords, passkeys, profile directories, routing rules or MCP grants. Routing rules name local spaces and would need remapping.

On import:

- History merges into the profile its source profile maps to, like favorites. The history store keeps one entry per URL with its newest visit, so repeating an import adds nothing. AppFeature writes it before publishing the batch's ledger.
- Archived tabs join the Tab Archive of the space their source space maps to, keeping their closing time, group and position. A tab whose space wasn't exported goes to the destination space.
- Extensions are never installed from an archive. The `extensions` category commits nothing and lists each one as `reinstallManually` in the preview and the report, so the user can reinstall it. Archive extensions carry no source profile, so the store install after an Arc import (DEV-845) doesn't apply to them.
- A history entry or archived tab without a finite date, or with a negative position, is reported as `invalidDate`.

Item IDs come from the exporting browser and the source ID is the same for every archive, so importing a newer export of the same browser adds only what's new. Importing preferences keeps this Mac's search shortcuts and link rules and adds the file's new ones; appearance and key bindings have one value each, so the file's are used. Each distinct set of preferences applies once.

## Bookmarks HTML

`BookmarksHTML` reads and writes the Netscape format browsers share. It only knows folders and links:

- Exports turn profiles and spaces into folders and leave regular tabs out, and the summary says how many. A pinned tab exports its custom title and saved URL.
- Imports read structure only, and never interpret scripts or other markup. Non-web links such as `javascript:` and `place:` are reported as invalid. A link's identity is its folder, URL and occurrence, so importing the same or a newer file adds only what's new.

## Destination and mapping

`MigrationDestination` names an existing profile and space, which receives anything without a route, plus routes for source spaces and source profiles. A source space follows `routes`, then its profile's entry in `profileRoutes`, then `defaultRoute`:

- `newProfile` creates an Arx profile matching the source's and a space in it, with the source's folders at the top level. Sources with profiles default to this.
- `newSpace` creates a space in an existing profile.
- `existingSpace` adds to a space that exists, keeping pinned items together in a folder named after the source space.

`profileRoutes` is Customize's profile mapping (DEV-842), keyed by `MigrationSourceProfile.ID`: `newProfile(name:)` sends the profile's spaces into a new Arx profile with that name (blank keeps the source's name; a profile an earlier run created is reused and never renamed), and `existingProfile` makes each of its spaces a new space in that profile. A mapping to a missing profile is refused as `invalidDestination`. `MigrationPlan.profiles` names source profiles whose Arx profile must exist after the run even when no category brings anything there (passwords follow them): execution commits their profile records first, once. A Cancel that arrives meanwhile cancels the run even when it has no categories. `MigrationPreview.profiles` lists the source profiles the snapshot holds, from its spaces and from favorites and history, for the user to map.

Favorites follow their profile: to the new profile if any of its spaces gets one, otherwise to the profile its first routed space lands in, then to the profile's mapping. `BrowserOrganization.applyingMigration(_:ledger:makeID:)` maps a batch as one validated `BrowserOrganization.update`. Existing tabs, folders and spaces are never renamed, moved or removed. Records need an HTTP(S) URL with a host; blank titles fall back to the host and blank folder names are dropped.

## Transactions, retries and idempotence

- Inspect before committing. A `MigrationPlan` carries the preview's `snapshotID`; execution re-reads the source and throws `sourceChanged` if the data differs, so the user reviews it again.
- Each category is one transaction. `MigrationDestinationWriter.commit` applies a category's items and its `MigrationLedger` changes in the same write, or throws having changed nothing. Categories commit one at a time in `MigrationCategory` order.
- Partial success is explicit. A run where some categories commit and others fail reports `partiallyCompleted`; `failed` means no category committed. Invalid records are listed as issues and don't fail their category.
- Every imported item has a `MigrationItemKey` (source ID, category, source item ID), recorded per receiving space or profile. Running or retrying a plan skips recorded keys. Removing that space or profile lets the same data be imported again.
- Repeated URLs are kept. A source may hold the same URL in several places on purpose, and a URL may already be in the destination, so nothing compares URLs. A source item ID repeated within one snapshot is an issue.
- The ledger also remembers the profiles, spaces and folders an import created, so a later run adds to them instead of making new ones.
- Each category is planned against the destination's current state just before it commits.
- Cancellation takes effect between categories. A commit that has started finishes or fails as a whole; committed categories stay, and the remaining ones are reported as `notStarted` and retryable.

AppFeature's `MigrationWorkspace` applies batches through the normal save path, preparing new profiles' native data first. `BrowserPreferences.migrationLedger` holds the ledger, so it's saved atomically with the organization.

## Passwords and sign-ins

DEV-650. `CredentialMigrationClient` (the `credentialMigration` dependency) moves a Chromium source profile's saved passwords and persistent cookies into an ordinary Arx profile. `readProfiles` reads several profiles of one browser with one Keychain read (DEV-842), so Customize's mapping costs one macOS prompt; any unlisted profile refuses the whole read before the prompt. Only `MigrationAssistantFeature`'s credentials step calls it; MCP and the agent tools never reach it, and nothing here joins `MigrationCategory` or the Arx archive.

- **Key.** `ChromiumSafeStorage` names each browser's Keychain item: Chrome's `Chrome Safe Storage`/`Chrome`, Arc's `Arc Safe Storage`/`Arc` (confirmed, DEV-831), Brave's `Brave Safe Storage`/`Brave` and Edge's `Microsoft Edge Safe Storage`/`Microsoft Edge` are verified; Dia's (`diaUnverified`) is assumed from Chromium's pattern and still needs checking on a Mac with Dia installed. Brave, Edge and the browsers DEV-896 added are migration sources only with the unchecked sources switch; their items come from `ChromiumBrowser.all`. `readSecret` asks for exactly that one legacy-keychain item, which is what makes macOS show its access prompt. Deny or Cancel is `denied`, and the client never asks again for that source in this run; a missing or hidden item is `missing`. Both lead the step to the CSV import.
- **Order.** `read` checks that the profile is one `Local State` lists and that the writer can take records *before* the Keychain read, so the prompt never appears for nothing.
- **Decryption** (`ChromiumCipher`): PBKDF2-HMAC-SHA1 (`saltysalt`, 1003 rounds) gives an AES-128 key; values are `v10` + AES-128-CBC with a space IV; cookies from database version 24 on start with SHA-256 of their `host_key`, which is checked. The key is erased after the read.
- **Reading** (`ChromiumCredentialStore`): `Login Data`, `Login Data For Account` (Chrome's account store; a site and username in both is kept once, from the first copy that decrypts, so a damaged copy never hides a readable one) and `Cookies` are copied with their logs into a private (0700) temporary folder, read there and deleted. Never-saved sites, empty, expired and session-only cookies are left out; undecryptable rows are counted by site. These files are never copied into an Arx profile: Chromium deletes rows it can't decrypt, and a copied cookie fails its host hash.
- **Sites** (`CredentialSiteGrouping`): no public suffix list. Chromium refuses a domain cookie for a public suffix, so each domain cookie in the source (`.google.com`) names a registrable domain or below; a host joins the widest one it falls under and otherwise stays a site of its own. `accounts.google.com` joins `google.com`, while `alice.k12.ca.us` and `bob.k12.ca.us` stay apart.
- **Receiving profile.** `BrowserOrganization.receivingProfile(forSourceProfile:destination:ledger:)` (and `MigrationAssistantClient.receivingProfile`) name the Arx profile that got a source profile's data: the current or routed profile, or the one the ledger records as created for it. The credentials step preselects it. `MigrationSourceProfile.wholeSource` stands for a source without profiles of its own (Firefox or Zen with passwords only); it goes where the import puts items without a profile, the destination's profile (DEV-844).
- **Session.** Decrypted records stay in the client's actor between `read` and `migrate`, and are used once (`discard` drops them). Features see `CredentialInventory`: sites with counts. `CredentialPasswordRecord` and `CredentialCookieRecord` redact their descriptions.
- **Writing** goes through `CredentialDestinationWriter`: import password records, set cookies (keeping what Arx already has; the engine answers accepted, existing and rejected per cookie key and the client groups them into sites), read those keys back, undo a batch. The engine calls behind it are ABI46 (DEV-830): AppFeature installs `CredentialMigrationClient.live(writer:)` with `MigrationAssistantFeature`'s `.browserEngine` writer, which reports itself unavailable on an engine without them, so the step goes straight to CSV there. `liveValue` alone keeps the `.unavailable` writer. Each imported password carries the engine's creation stamp (`CredentialUndoRecord.Password.dateCreated`), and undo removes it only while the stored entry still has it.
- **Reporting** (`CredentialReporting`): per site, `kept` only after the read-back finds the cookies, `signInAgain` for a reason Arx saw (session-only, unreadable or session-only — including a site where only some cookies decrypted or some end with the source's session, refused, some cookies refused, a set cookie gone after writing), `notChecked` when the engine can't read back, and `skipped` for sites the user left out. No site is marked by domain in advance, Google included.
- **Undo.** Each report has a batch ID; `undo` removes exactly the passwords and cookies that batch added (`CredentialUndoRecord`, keys only). A cookie's key is its full identity (domain, name, path, partition, source scheme and port), so a sibling Arx already had isn't removed. If cookies fail after passwords were written, the report keeps the passwords and their batch, with the selected sign-ins marked refused.
- **Firefox, Zen and Safari** (DEV-896). `CredentialBrowser` names every source the step reads: a Chromium browser with its Keychain item, a Mozilla browser's folder, or Safari's home folder. `CredentialSource.access` says what reading asks of the user (`keychain`, `profileFiles` or `fullDiskAccess`), and the step's footer explains it.
  - *Firefox and Zen* (`MozillaCredentialStore`): `logins.json` holds each username and password as base64 DER (the key's `CKA_ID`, Triple DES or AES-256-CBC with its IV, the ciphertext). The key is in `key4.db`'s `nssPrivate` (`a11`, under `a102`), encrypted with a key derived from the global salt (`metadata.item1`) and the primary password: PBES2 (SHA-1 of salt and password, PBKDF2-HMAC-SHA256, AES-256-CBC with NSS's 14-byte IV after its DER header) since Firefox 75, PKCS#12's SHA-1 and Triple DES before. `metadata.item2` must decrypt to `password-check` with an empty password; otherwise the profile has a primary password, which Arx doesn't ask for, and the step offers CSV (`primaryPassword`). `DERValue` reads the DER. A form login's URL and `signon_realm` are both its origin with a slash, whatever page the form submitted to, so the engine's realm check accepts it; HTTP sign-in prompts' logins, which the engine doesn't import, stay in the browser and are counted on their own (`CredentialInventory.httpAuthPasswordCount`, `CredentialReport.Passwords.httpAuthNotImported`), so the summary says how many weren't imported, and Firefox's own entries are skipped. Cookies come from `cookies.sqlite` in cleartext: rows of another container, private browsing or a partition (`originAttributes`) are left out, an expiry in milliseconds (newer Firefox) is told from seconds by size, `schemeMap` gives the source scheme, and an insecure None cookie becomes unspecified. `key4.db` and `cookies.sqlite` are read from private copies.
  - *Safari* (`SafariCookies`): `Cookies.binarycookies` in Safari's container, or `~/Library/Cookies` on older macOS, with Full Disk Access: the `cook` header, big-endian page sizes, then little-endian records with flags (secure, HTTP-only), string offsets, and expiry and creation as seconds since 2001. Its SameSite isn't stored, so it's unspecified. Only the default profile's cookies are read; profiles' own stores aren't located yet. Safari's step reads sign-ins directly and still sends passwords to the Passwords app's export.
- **Headless** (`Arx --headless`). The migration assistant isn't shown in a headless run (no onboarding, Settings or menus), and AppFeature installs `CredentialMigrationClient.unattended` there: no source is offered and every read fails with `unattended`, so no Keychain, Touch ID or other prompt can wait for a person. Reading Firefox's and Zen's files never prompts, and Safari's files without Full Disk Access simply aren't readable (macOS doesn't prompt for it).
- **Leaving.** `discardAll` drops every unwritten session; `MigrationAssistantFeature.cancelInFlightWork()` calls it, so a host that removes the assistant (onboarding's Escape or close button) drops the decrypted records too.
