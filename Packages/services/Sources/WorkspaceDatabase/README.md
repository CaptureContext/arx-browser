# WorkspaceDatabase

The workspace in SQLite through SQLiteData: phase 1 of ADR 0001 (`.agents/adrs/0001-icloud-sync-with-sqlitedata.md`, DEV-560). `BrowserWorkspaceClient` uses it only while the `ARX_SQLITE_WORKSPACE` feature flag is on; otherwise nothing opens it.

Two databases sit beside `arx-workspace.json`, one per sync category: `arx-organization.sqlite` (Profiles and spaces) and `arx-preferences.sqlite` (Preferences). One connection opens the organization file and attaches the preferences file in rollback-journal mode, so each write to both commits atomically.

- **Synced tables** (phase 2 hands them to `SyncEngine`): `profile`, `space`, `folder`, `pinnedTab`, `favorite`, and `preference`, `searchShortcut`, `keyboardShortcut`, `routingRule`, `proxyLinkRule`, and `mergedItem` (DEV-1216). UUID or stable text primary keys, at most one foreign key each, no other unique index, no CloudKit reserved names, nullable or `NOT NULL ON CONFLICT REPLACE` columns. Ordered lists are rows with `FractionalIndex` `position` keys, ordered by `(position, id)`.
- **Device-local tables**: `storeInfo`, `retiredProfile`, `profileStorage` and `mergeRemap` (DEV-1216), `spaceState`, `folderState`, `tabState`, `regularTab`, `archivedTab` (empty since DEV-983), `splitGroup`, `tabGroup`, and `preferenceStoreInfo`, `localPreference`.

Both files record the store's ID and write revision. A pair that disagrees, as after one file was lost or restored alone, fails to load as a partial store rather than being read or migrated over.

Later migrations add only nullable columns to synced tables: `profile.darkPagesOffSites` (DEV-1020), the sorted sites dark pages leave alone, as JSON; and `icon` on `pinnedTab`, `favorite` and the device-local `regularTab` (DEV-1251), the `SpaceIcon` chosen for the tab as JSON, as `space.icon` is. Pins and Favorites sync theirs with the row; an open tab's stays on this Mac, as open tabs do. Tab Archive keeps no icon: a closed tab's goes with it, and only the window's ⌘Z, which puts back the tab itself, brings it back. An icon a load can't read is left out rather than failing the workspace. `profile.unreadBadges` (DEV-1258), the profile's unread badges as `UnreadBadgeVisibility`'s raw value, also in the local file's twin for "this Mac only" profiles. The site and tab levels of unread badges, `unreadBadgeSites` and `unreadBadgeTabs`, are device-local preference rows; the tab map's pairs are sorted like `tabsLastViewed`.

`OrganizationRows` and `PreferenceRows` translate `BrowserOrganization` and `BrowserPreferences` to rows and back; `BrowserOrganization` stays AppFeature's state. `WorkspaceDatabase.save` writes only the rows that changed since its last read or write, keeping each item's position while it stays in order. `migrate` writes a JSON workspace into an empty store in one transaction. Only the coding keys in `PreferenceDomain` sync; every other preference is a `localPreference` row. A `PreferenceGroup` kept on this Mac (DEV-982) has an `override.<group>` `localPreference` row with its coding keys, which the reader prefers to its synced rows; saves build the group's synced rows from their base, so they never write them, and `setPreferenceGroup` turns a group local or synced again as a save of its own, bumping the revision so a save that read the store before stops. The `routing` domain carries `removedProxyLinkDefaults` beside `routing`, so a default Proxy Links rule deleted on one Mac isn't offered on another (DEV-1113).

With iCloud sync (`init(directory:separatePreferencesConnection: true)`, DEV-977), preference rows are written through `preferencesDatabase`, the preferences file's own connection, because the Preferences `SyncEngine` only sees writes on the connection it was made on; the attached copy is then only read. A save writes the preferences file, then the organization file, each in its own transaction. A save cut short between them leaves the preferences file exactly one revision ahead, which a load accepts as that save's preferences with the previous save's organization; any other difference is still a partial store. The rows that landed become the base the next save diffs preferences against. Each transaction checks again that no other writer saved since the save's checks, the preferences one before it writes anything. Every save also holds `arx-workspace.lock` in the store's folder (`flock`), so a save from another process, such as a test build on the same profile, waits for the whole save before it rather than landing between its two transactions; one that waits longer than a busy database fails as `changedOnDisk` (DEV-1005). A first save or migration marks the preferences file (`StoreInfoKey.unfinishedFirstWrite`) until the organization file holds the workspace too, so one cut short there reads as an empty store, and the next first save or migration replaces the preference rows it left (DEV-990). Without that mark, a preferences file whose organization file is gone is still a partial store.

A profile in `retiredProfile` that iCloud sync brought back (another Mac edited it offline) is left out of what `load` returns, with its spaces, folders and tabs, so the workspace still validates; the next save that changes the organization deletes its rows again. `load(validate:)` runs the caller's check before the loaded rows become the diff base, so a rejected reload leaves the base as it was. The base is never re-read from disk behind the caller's back: sync writes rows without a new revision, and a save diffed against rows the caller hasn't read would undo them.

Tab Archive is a third file, `arx-archive.sqlite` (DEV-983, ADR 0001 decision 4), so it can sync on its own: `archiveEntry` (synced, real columns: the entry's profile, title, address, archive time, space and group, no foreign key since the profile is in the organization file) with its own `archiveDeletion` and `archiveDevice` for its zone (named apart from the organization's, since SQLiteData routes a fetched record by type whatever its zone), and the device-local `archiveState`. The organization connection attaches it as `archive` and reads it there; `BrowserOrganization.archive` still comes and goes with the workspace. Without sync it's written in the same transaction. With sync, its engine sees only writes on its own connection, `archiveDatabase`: a save puts its archive change (`PendingArchiveChange`) in the organization file's `storeInfo` in the organization's own transaction, applies it to the archive file after, and clears it. A save cut short in between, which could leave a restored tab neither in its space nor in Tab Archive, is finished on the next open or save, before anything else is read or written. Once Tab Archive has synced (`ArchiveStateKey.deletionsStayLocal`, which `WorkspaceSync` sets), removing an entry, as a restore does, writes an `archiveDeletion` row for this Mac and loads leave it out; before, it's deleted. The attached copy follows the same rules without sync. Of entries for the same tab, as two Macs can leave, only the latest loads. The two files share an ID (`StoreInfoKey.archiveFileID`, `ArchiveStateKey.fileID`), so an organization file whose archive file was lost, restored or replaced alone opens as a partial store rather than with an empty Tab Archive. Opening a store moves phase 1's JSON `archivedTab` rows into `archiveEntry` (`moveArchiveOut`), safe to repeat.

"This Mac only" profiles (DEV-981, `Profile.syncsWithICloud == false`) live in a fourth file, `arx-organization-local.sqlite`: the organization schema, never synced, attached as `local` and written in the organization's transaction through twin record types bound to it (`LocalOrganizationTables.swift`). `OrganizationRows.localProfileIDs` names them; `split()` gives each row to its profile's file (profiles, spaces, folders, pins, Favorites, space and folder state, open tabs, Tab Archive entries; the local file keeps entries as JSON in its `archivedTab`), and the reader merges the files, leaving out the synced copies of local profiles. Turning a profile local writes nothing to its synced rows (`keepingMoved`), records them as a baseline in the local file's `storeInfo`, and moves its state; turning it back on writes its rows over the synced copies and hides (or, without sync, deletes) the baseline rows it deleted meanwhile. The local file is paired by `StoreInfoKey.localFileID` and stamped with each save's revision, so one lost or restored alone opens as a partial store. `recordUse(of:)` leaves local profiles' items out.

Never edit a registered migration, and never drop or rename a synced column. Tests use temporary directories only.

With separate connections (iCloud sync), deletions stay local (DEV-980): a removed profile, space, folder, pinned tab or Favorite gets a `deletion` row for this Mac (`LocalDeletion`, `DeletionRecord`) instead of being deleted, loads leave it out, along with what can't show without it, and a hidden folder's other children show in the closest folder above it that's shown. Writes diff against the rows without the hidden ones, so they're never touched here, and writing an item again shows it again. Edits, a changed selection and an expanded folder record use in `usage` rows, and `recordUse(of:)` records the spaces, pinned tabs and Favorites this Mac opened, with their profiles, once a day each. A tab that moves between a pin and a Favorite, or to another profile, is a move: the row it left is deleted on every Mac. A move to another profile is known by the copy's `Tab.movedFrom`, which the moves in BrowserCore set and nothing saves, so a deletion beside an identical new tab in another profile stays local (DEV-1089). Without sync a removal deletes, as before. The WorkspaceSync README describes when a deletion goes everywhere.

A deletion row's `keepsElsewhere` (DEV-1336) says the person chose "Delete from This Mac Only" for a profile or space: `keepRemovalOnThisMac(_:)` names it, and the next save that hides it marks this Mac's rows for it and everything in it, by the rows the save diffed against.

Only a fetch or Arx's own code deletes a synced row that has a parent (DEV-1207). `SyncedDeletions.install(_:tables:)`, which WorkspaceSync runs on the organization connection when it makes its engine, adds temporary triggers that skip any other delete of a space, folder, pinned tab or Favorite, cascade included. That other delete is SQLiteData's answer to a save CloudKit refused with `referenceViolation`, which also comes when the parent's own save failed. Every write here goes through `writeAllowingSyncedDeletions(_:)`, which runs the closure with `SyncedDeletions.areAllowed` set. A new write on these connections must too, or with sync on its deletes are skipped without an error.

## Merging what matches (DEV-1216)

`mergedItem` (`MergedItemRecord`) is synced: an item merged into another from Settings › iCloud Sync, with the kept item's ID, which every Mac's repair pass applies (the WorkspaceSync README). `profileStorage` (`ProfileStorageRecord`) is this Mac's own: a profile whose website data is kept under another profile's ID here, as a merged profile's is under the kept one's. `load` publishes these aliases to `BrowserCore.ProfileStorageAliases` before it returns the workspace, so the engines name a merged profile's storage by the alias.

`mergeRemap` (`MergeRemapRecord`) is this Mac's own too: the items a joining Mac's merge replaced with iCloud's, and the items they became. The app can still hold the workspace from before the merge, with a save on its way. Until it reads the store again, each save is rebased across the merge inside its write transaction (`OrganizationRows.rebased(_:_:across:_:)`): both what it saves and the base it diffs against take the kept IDs, and each synced row it changed becomes the stored row with only the changed fields applied, so the edit lands and nothing the merge wrote is undone. `WorkspaceSync` forgets the rows at its next launch, when no store holds a workspace from before the merge; until then a store that loaded since rebases nothing, since its rows have the kept IDs already. A pin the save made a Favorite, or the other way round, keeps the stored item's title and address, with only what it changed. The legacy profile ID is never remapped, since it names Chromium's Default directory.
