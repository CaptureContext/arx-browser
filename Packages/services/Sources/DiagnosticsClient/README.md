# DiagnosticsClient

Crash reports and Report a Problem (DEV-887). Settings › Privacy and Help › Report a Problem… use it as `@Dependency(\.diagnostics)`. It never sends anything: problems are reported as GitHub issues the person files with their own account.

## Crash reports

`CrashReportStore` keeps Arx's own reduced copies in `~/Library/Application Support/dev.capturecontext.arx/Diagnostics/Crash Reports` (Arx Dev's under `dev.capturecontext.arx.dev`, DEV-1013), one JSON file each, at most 50 and 30 days. `collect()` reads, without moving or changing them:

- macOS's reports for Arx processes, `~/Library/Logs/DiagnosticReports/Arx*.ips` (`SystemCrashReport`). In a release build Chromium forwards the browser process's crashes to macOS, so this is where Arx's own crashes land.
- Chromium's minidumps, `…/dev.capturecontext.arx/Crashpad/{pending,completed}/*.dmp` (`Minidump`). Chromium doesn't forward helper crashes to macOS, so renderer, GPU, network and other helper crashes are only here. Chromium uploads nothing: Arx's engine has no crash server.

Both readers keep an allowlist and drop everything else (`CrashReport`): the process name, versions, the exception's type and signal or Mach code, the crashed thread's frames as module file name and offset (with macOS's symbol name when its report has one), and those modules' build UUIDs. They never keep a URL, a title, page content, memory, register values, file paths, `asi` or termination messages, or any identifier for the Mac or the person. A minidump's thread stack is only used to follow the frame-pointer chain; return addresses outside every module are dropped. `seen.list` remembers which raw files were read, so a pruned or removed report never comes back. `removeCrashReports` deletes Arx's copies and the saved problem report files, and keeps `seen.list`.

## Report a Problem

A `ProblemReport` is the person's description (trimmed, at most 10,000 characters), `DiagnosticsEnvironment` (Arx version and build, Helium and Chromium versions from `Arx Framework.framework`, macOS version, architecture) and, when Include diagnostics is on, `Diagnostics`: the Mac's model and memory and the crash reports of the last 7 days.

`GitHubIssue.newIssueURL` is the Arx repository's new issue page for the form `.github/ISSUE_TEMPLATE/problem-report.yml`, prefilled by field id with the description, the versions and the report file's name (never its path). Every value is percent-encoded, so a description can't add fields, and a description that would make the address longer than 8,000 characters is cut with `[…]`. `keep` saves the report as indented JSON in `…/Diagnostics/Problem Reports` (`Arx Problem Report <date> at <time>.json`, the newest 10 kept) for the person to attach; `reveal` selects it in Finder; `save` writes the same JSON to a file the person picks.

`testValue` is unimplemented. `previewValue` has one crash report and writes nothing.

## Hangs

`HangMonitoring.start()` runs for the whole app run (DEV-1010), started by `BrowserApplication` before Chromium's run loop:

- `StallWatchdog` stamps every pass of the main run loop with a run-loop observer. A watchdog thread parks while the run loop waits and, while it's busy, looks only when the current pass could have reached 1 s, so an idle app costs it no wakes and a busy one about one a second. Once one pass has been busy for 1 s it suspends the main thread just long enough to follow its frame-pointer chain (`ThreadSampler`, which allocates nothing while the thread is stopped), then names the frames with `dladdr`: binary file name, offset, demangled function, and the binary's UUID. The stall is appended to `…/Diagnostics/Hangs/stalls.jsonl` as it begins and again with its full length when the run loop comes back, so a stall the process was killed in is still there, unended. A pass that reached 1 s and ended before the watchdog looked is still logged, as the run loop measured it, without a stack. Uptime is the clock, so sleep isn't a stall, and nothing is logged while a debugger is attached.
- Strict mode, the `ARX_STALL_STRICT_MS` feature flag (milliseconds), is for smokes: a stall that long is logged and the process exits with status 86.
- In a Debug build, `ARX_STALL_INJECT_MS` blocks the main thread that long once, five seconds after launch, to check the watchdog by hand.
- MetricKit's daily payloads, and at launch the ones macOS kept from before, are reduced through an allowlist into `HangReport`s in `…/Hangs/metrickit.jsonl`: a hang diagnostic's duration and most-sampled stack (binary names, offsets, UUIDs), and the hang-time histogram, each payload kept once. `…/Hangs/metrickit.seen` lists a SHA-256 of each report taken in, with its date, for 30 days, so a payload macOS delivers again, including one removed since, isn't saved again (DEV-1079). Exception reasons and other free-form text are never read.

Both logs keep 30 days and at most 100 records. Include diagnostics adds the last 7 days' stalls and MetricKit reports, at most 20 of each (`ProblemReport.Diagnostics.stalls`, `.hangReports`). Remove deletes both logs and keeps `metrickit.seen`, which holds nothing a report could be read back from. Like crash reports, nothing here holds a URL, a title, page content or a path, and the logs and markers are readable by the person's account only.

## Clean-quit ledger

`CleanQuitLedger.begin(profile:)` runs at launch, after hang monitoring (DEV-1018). Each run writes a marker, `…/Diagnostics/Sessions/session-<key>.json`, where the key is a hash of the profile folder's path, so runs on different profiles (smokes beside a person's own run) keep separate markers and no file name shows a path. The marker holds the run's ID, process ID, start time, a last-seen time refreshed every minute, Arx's version, the workspace's tab and space counts, which `WorkspacePersistence` reports after each save, and the Mac's last memory-pressure level above normal with its time, which travels with an unclean exit as evidence for a memory kill that left no jetsam report. `BrowserApplication` removes the marker once Chromium's run loop returns, or when startup fails. A run only removes its own marker.

A marker the next launch finds belongs to a run that didn't quit, unless a process with its ID and Arx's name is running and started before the marker was written (a later process may have reused the ID). Claiming a marker happens under a `flock` other Arx processes respect, as do the logs, which several runs on different profiles share. Evidence counts only from the marked process (its process ID, when the report has one) and only between its start and two heartbeats after it was last seen, never past a later boot. The launch explains the exit, in this order: a crash report of Arx's own process during the run (`crash`), else the run's last stall that never ended (`killedWhileStalled`, with the stall's ID and length), else a `JetsamEvent` report naming the process, dated (its body's `date`, else its header's `timestamp`) inside that same window (`jetsam`, with jetsam's short reason), else a boot of the Mac after the run started (`systemRestart`), else `terminated`. A `terminated` exit is recorded at once, then explained from macOS's unified log on a background queue, since reading it takes seconds, and half a minute on a busy Mac (DEV-1070, `SystemExitLog`). RunningBoard logs the exit reason launchd reports for each app it launched, `[app<application.<bundle ID>.…>:<pid>] termination reported by launchd (namespace, code, status)`. Only that line for the run's process ID and Arx's bundle ID counts, and only between its last sign of life and the window's end. A signal (namespace 2) makes it `killed`, with the signal's number; a Force Quit of Arx within 5 s before the exit makes it `forceQuit`: a Dock line with the ASN `launchservicesd` logged for the run's process as it quit, or a Force Quit window (`loginwindow`) line naming Arx or its process ID. A request for another app, or one whose app the log redacts as `<private>`, doesn't count, so the exit stays `killed`; RunningBoard's own termination (namespace 15) makes it `watchdog`; jetsam (namespace 1) without a report makes it `jetsam`. The exit keeps the reason's three numbers (`exitReason`) and whether the log could be read (`systemLog`). No log text is kept. Reading the system log works for an administrator's account without root. If it can't be opened, as is expected for a standard account, the exit stays `terminated` with `systemLog` set to `unavailable`. Runs started outside LaunchServices, such as smokes run from the shell, aren't RunningBoard apps and stay `terminated`. It appends an `UncleanExit` to `…/Sessions/unclean-exits.jsonl`, kept 30 days and at most 100. Include diagnostics adds the last 7 days' unclean exits (`ProblemReport.Diagnostics.uncleanExits`), and Remove deletes the ledger. No URL, title or path is ever written.
