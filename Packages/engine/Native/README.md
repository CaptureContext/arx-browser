# Native Chromium integration

ABI11 adds [bounded semantic inspection](inspection/README.md) with a renderer-owned
DOM version and expiring node handles. The native surface is read-only and
requires separate real-page acceptance before app capability enablement.

Arx-owned Objective-C++ implementation of the C ABI. Compiled into the pinned Chromium browser target after Helium’s patches. A browser-main extra part reports readiness and shutdown; WebContents owns each page and its AppKit view. The stock Chromium helper entry points continue to dispatch child processes.

`Scripts/engine/overlay.py` adds the startup hook, GN sources, exported ABI entry point, and Arx branding. Keep ABI declarations in `Sources/ChromiumBridge/include` as the single source of truth. The build copies them into the prepared source tree.

Embedded mode also bypasses Chromium's profile-dependent native menu rebuilding. Arx owns the menu bar, so Chromium's bookmark/history menu tags are absent. Profile destruction must still notify Chromium observers without attempting to reconstruct those menus.

Every Arx browsing WebContents is registered as a Performance Manager tab, including private and secondary hosts. Arx has no Chrome TabInterface to perform that classification. Leaving the page type unknown bypasses Chromium's recently used tab protection and can freeze a playing source immediately when its view detaches, preventing its automatic PiP handler from running. The classification preserves native visibility and the normal freezing policy; it does not grant activation or weaken media command validation.

Startup turns off work Arx never uses (DEV-894): `--disable-features=AutofillAiWalletPrivatePasses,GatherProcessRequirementMetrics`. The first is Google Wallet passes in Autofill AI; while it was on, every ordinary page's autofill client asked LocalAuthentication, synchronously on the UI thread, whether device re-auth was available. The second is a code-signing self-check that only records histograms. `Scripts/engine/startup_metrics_overlay.py` also compiles out Chrome's launch-time TPM benchmark, which made and deleted Secure Enclave keys only for histograms.

`ARX_MEMORY_PURGE_ON_FREEZE` is a feature flag for Blink's `MemoryPurgeOnFreeze` (DEV-942), off on desktop and off in Arx (measured below). It's read once at launch from the environment, or else from Arx's defaults under the same name (`defaults write dev.capturecontext.arx ARX_MEMORY_PURGE_ON_FREEZE -string on`). `on` adds `MemoryPurgeOnFreeze` to `--enable-features`; `limit` adds `MemoryPurgeOnFreezeLimit` too; anything else changes nothing. The engine prints `ARX_MEMORY_PURGE_ON_FREEZE <features>` to stderr when it applies. Blink's `MemoryPurgeManager` then sends a critical memory-pressure signal in a renderer one second after one of its pages freezes (or when a background purge already pending fires), but only while that renderer is in the background (no visible page, no capture or loading boost), so unattended runs, which pass `--disable-renderer-backgrounding`, never purge. Performance Manager's tab freezing thaws frozen tabs for 5 s every minute, so `on` purges again at each refreeze; `limit` purges only the first time per background session. Without either, Blink already purges once 1 to 4 minutes after a renderer goes to the background.

Measured on Chromium 157 (2026-11-14, signed Release build of `d8e73c26`, a Mac mini (Mac16,10), load average under 3): `make benchmark ARGS='--launches 0 --tabs 50 --no-warmup'`, two runs per setting, reading the windowed step's 50 tabs after the 390 s freeze wait (39 to 43 of them frozen in every run). Memory after the wait was 1,527 and 1,603 MB with the flag unset, 1,530 and 1,517 MB with `on`, 1,516 and 1,524 MB with `limit`; renderers alone 1,094 and 1,139, 1,098 and 1,088, 1,094 and 1,095 MB. That's within run-to-run noise, since Blink's own background purge has already run by then. `on` raised the renderers' idle CPU from 0.5 to 0.9 % of a core to 1.5 to 1.6 % (purging again at each refreeze); `limit` cost nothing and saved nothing. So both stay off. The fixture pages hold little cache to purge; a page with large decoded images or fonts might gain more, which the benchmark can't show.

A page starts hidden to Chromium until its view first joins a window (DEV-936). Arx never calls `WasShown`/`WasHidden`; Chromium learns visibility only from the page's view, and it ignores hidden reports until a page has been shown once. A page the app creates is made with `initially_hidden`, so its PageNode is born hidden and goes to the front of the recently used order without the five-minute recently-visible protection. A page Chromium creates visible (a renderer's foreground window) gets `WasHidden()` when it's adopted. Either way the first mount still calls `WasShown()`. `initially_hidden` also hides the view itself, which Arx would never undo, so the view is unhidden at adoption. A background-opened, restored, agent- or extension-opened page that's never shown therefore runs throttled timers at background priority and can be frozen once it falls outside the five most recent tabs. Its first mount draws a first frame, as switching to any hidden tab does. `make background-visibility-smoke` covers it.

`downloads_bridge.mm` observes each profile’s DownloadManager and DownloadItems. It explicitly initializes deferred ordinary download history, emits copied snapshots after the native observer stack unwinds, and provides cancellation by GUID. Manager initialization is reported only after Chromium has loaded history and its in-progress cache. Target selection and filename reservation use Chromium’s default Downloads destination and UNIQUIFY collision policy. The bridge never bypasses danger/insecure validation, auto-opens files, or exposes unsupported pause/resume behavior. Private managers retain their OTR context after source pages close while downloads are active, then release through ProfileDestroyer. Observers are removed before profile shutdown.

A fresh Arx private context initializes its DownloadManager before it becomes available to pages. Pinned Chromium's `DownloadBubbleUIControllerDelegate` forces the OTR `download.prompt_for_download` user override to true during that initialization. Arx presents its own Downloads surface, so it then clears only that fresh context's ephemeral override and resumes the original profile's configured preference. The key is not in Chromium's incognito-persistent allowlist; clearing it never changes the original user preference or managed policy. Parent true still prompts, managed policy still wins, and later inherited changes remain visible. Existing-key preparation and download observation never reset a later intentional private preference. Destination sanitization, explicit Save As, collision resolution, danger/insecure checks and confirmations for invalid destinations remain Chromium-owned.

Private release immediately removes the logical key from the browsing registry once its pages are closed. Repreparing that key creates a fresh unique OTR context; it never reattaches the old storage. Retired contexts remain separate until their own active downloads and queued snapshot/initialization deliveries drain. Download observers are keyed by the exact Profile, while the public logical-key/GUID cancellation lookup includes both current and retired contexts. A monotonically tagged retirement task can destroy only its captured context, including across multiple reopenings of the same key. Logical keys keep their ordinary/private storage kind for the runtime lifetime; ordinary preparation reserves its key before asynchronous profile creation.

Retirement always runs in a posted task. External callbacks may reenter shutdown or cancellation, so notifications copy borrowed keys and callback data before delivery, cancellation snapshots weak observer identities, and native calls recheck those identities afterward. Shutdown first marks the engine stopped, then detaches observers before clearing profile registries. `test_private_profile_lifetime.py` compiles the production policy bodies against deterministic queued Chromium doubles under AddressSanitizer/UndefinedBehaviorSanitizer. It covers fresh reopening with retained transfers, terminal delivery ordering, stale retirement tokens, storage-kind races, reentrant cancellation and shutdown. The signed app fixture exercises real Chromium storage/download acceptance; sanitizer doubles alone do not establish it.

Quit checks use synchronous native active-count and Cancel All operations, so posted presentation events cannot hide active work. Cancel All snapshots GUIDs before invoking cancellation and re-reads items afterward to tolerate observer-driven changes.

`capture_bridge.mm` implements ABI5 viewport capture without scrolling, resizing, or emulating the page. It bounds dimensions, pixels, encoded bytes, and timeout, binds the primary document with WeakDocumentPtr, and rejects navigation, process loss, page closure, or changed viewport/scale. Page document UUIDs change only on committed cross-document navigation. CopyFromSurface callbacks marshal to the Chromium UI sequence before touching page identity; PNG encoding runs on a worker, then revalidates on UI before returning borrowed bytes. Viz may omit protected media without reporting that omission, so the service always warns the user to review the preview.

Only one physical copy/encode may run process-wide. Cancellation and timeout report promptly but retain that slot until unavoidable work drains; retries report busy. No unbounded waiting queue or detached encoding accumulation is permitted. Shutdown invalidates pending callbacks. App composition supplies the capture capability. Controlled pixel, stale-page, cancellation, and bounded-input fixtures run against the packaged framework; Swift boundary tests alone do not establish rendering support.

The standalone disposable smoke fixture may explicitly request Chromium’s supported `--use-mock-keychain` through the ABI5 run option. The original run entry point always supplies false. Only the explicit test path appends the switch and emits `ARX_ENGINE_SMOKE_MOCK_KEYCHAIN`; ordinary app startup keeps the real Keychain. This fixture isolates OS authorization prompts and must never be counted as validation of production credential persistence or security.

ABI6 adds `media_bridge` as an explicitly enabled observer for each ordinary page. It reads the existing MediaSession and routes supported play/pause and manual video PiP through that session; it creates no player, stream or extra WebContents. Commands re-read native state and require exact source generation/revision, then wait up to five seconds for state confirmation. Cancellation invalidates pending entry so a late website handler cannot open PiP. Navigation, metadata/player replacement, renderer failure and page destruction invalidate queued work. A replaced player (an ad, the next video) keeps the page's PiP, which Blink moves to the new player; only cross-document navigation, a crash, page destruction or no player taking over within three seconds closes it. New-document media stays absent until its player starts. Callback payloads are copied into posted tasks after Chromium observer stacks unwind.

The per-page delegate denies PiP unless a current manual or separately supported automatic command authorized it. Private pages are denied even when page JavaScript calls PiP directly. Document PiP (Google Meet's call window) opens for ordinary pages through Chromium's standalone `DocumentPipHost` from `AddNewContents`; private pages are refused. Media entry also completes on a document PiP. Automatic entry requires the separately advertised `kEnterAutoPictureInPicture` action and uses `EnterAutoPictureInPicture`, preserving Chromium’s scoped PiP request token instead of granting general user activation. It rechecks the source NSView/window visibility at both submission and the asynchronous entry callback; a visible split pane or background window remains visible regardless of keyboard focus. The app owns the per-profile/exact-origin decision (on unless the site was turned off) and stable host visibility transitions. Startup enables `BrowserInitiatedAutomaticPictureInPicture`, so a playing video on a site without its own `enterpictureinpicture` handler (YouTube) also advertises the automatic action; Chromium's own trigger needs a TabInterface Arx lacks, so entry still comes only from Arx's request. The global Chromium window manager owns the single video surface; explicit exit and source replacement do not pause, while its native Close button may pause. Return to Tab posts page/generation for application ownership routing. The optional observer is not activated by normal page construction.

`pip_overlay.py` restyles Chromium's PiP window (no ABI change). Since DEV-1295 its controls are Figma's "Scrim" variant: bare white symbols over Chromium's scrims (a light dim over the video, darkening towards the top and bottom edges), close alone top left (minimize is hidden), captions, mute and Back to Tab top right, play/pause between the skip buttons, and the elapsed time and duration over a progress bar across the bottom, or a red badge for live media. Chromium's circular ink drop lights the hovered button. Until DEV-1295 they were round glass buttons with the progress bar in a glass capsule; `PREVIOUS` puts the upstream anchors back over that hunk and its members. Chromium lays the controls out first and Arx moves them, so visibility, hit testing and state stay Chromium's. On macOS each button shows an SF Symbol, rendered white by `ArxSymbolImage` and re-applied after layout and after play, mute, microphone and camera state changes, which make Chromium redraw its own icons. On macOS (DEV-825) the window has continuous 16-point corners and rests at a corner 16 points inside a screen's visible frame (24 until DEV-848; `PREVIOUS` puts the upstream anchor back over DEV-825's 24-point hunk so the change applies once to a prepared tree), where it first opens bottom right. `pip/arx_pip_window_motion.mm`, copied into Chromium's overlay directory as a whole file, takes over Chromium's press-drag on the video and adds a two-finger trackpad drag. Both move the window 1:1; on release the velocity of the last tenth of a second is projected forward with UIKit's normal deceleration rate, and the window settles on the corner nearest that point, on whichever screen it lands, with a slightly bouncy spring that starts at the release velocity. The settle also resizes the window, faster than it moves, to fit the destination screen within Chromium's cap (80% of each side) with its aspect ratio kept, so a window thrown onto a smaller screen already fits when it crosses over. Chromium's minimum scales the whole window rather than one side, so a portrait video under Chromium's landscape minimum keeps its shape (DEV-848). Position springs relative to the corner placed for the window's current size, so the corner stays exact through any resize, and if Chromium resizes it anyway the settle carries on from that size without a jump. Any press stops a settle; release settles again. A settle that hasn't come to rest within three seconds finishes at its resting frame. `arx_pip::Settler` holds this logic, and the tests run whole settles against simulated Chromium resizing. Phase-less precise scrolling doesn't move the window. Reduce Motion keeps the corner but settles without bounce or carried velocity. Grabbing, pinching or two-finger dragging a settling window stops it where it is. A pinch resizes it about the pointer with its aspect ratio and Chromium's size limits, inside the screen, and then settles it; so does Chromium's edge resize. The math is pure C++ in `pip/arx_pip_motion.h`, tested by `Scripts/tests/test_pip_motion.py`. DEV-852: the window is created on every Space and over other apps' full-screen Spaces before it's first shown (activation independence and full-screen Spaces right after `Init`, as Chromium's Glic window has, and `canJoinAllApplications` when the motion starts), at the floating level. A throw's projection reaches at most one screen's width or height, so it can cross to a neighbouring display but not past it; the carried velocity is bounded and the bounce past the corner is squeezed under the inset, so no settle frame leaves the target's visible frame (or goes beyond where the window started). Settles run on the target screen's display link, which keeps firing while the window is between screens. A two-finger drag keeps 48 points on a screen; a release off every screen, a settle stopped by another move, or one ending off screen puts the window at the nearest corner at once. A screen-parameters change settles it back to the same corner of the same display, else the nearest. The elapsed, duration and live labels are sized for the widest text the duration's format allows (widest digit) and as tall as their own line (18 points for the times' `STYLE_BODY_4`; a 16-point label clipped it at every scale), and the controls are laid out again when that size changes, so the time never cuts off. The overnight media smoke reaches the motion controller through in-process notifications answered only under `ARX_MEDIA_SMOKE_ROOT`.

Performance Manager also protects its actual `PageNode::HasPictureInPicture`
state from freezing. An ordinary observed source holds an exact-page,
reference-counted media scheduling lease while it currently plays video and
advertises the registered automatic PiP action. The lease is acquired before
the native visibility change, so exhausting Chromium's five-tab MRU allowance
cannot freeze the handler before Swift submits its request. This resource
exemption applies even without the site's Swift opt-in; it grants no entry,
playback, activation or visibility. Pause, capability loss, destructive source
invalidation, failed-entry quarantine and observer teardown release it. Metadata
or session replacement retains it until fresh synchronous facts are evaluated,
avoiding a freeze gap between eligible generations. Successful entry hands off
to the actual-PiP reason. Existing playing/visibility/generation checks and the
five-second command deadline remain in force. Lease changes use PM's own frozen
bookkeeping and connected-browsing-instance rules; they never force page state.

The pinned overlay replaces ChromeMediaSessionClient's primary-OTR predicate with `BrowserContext::IsOffTheRecord()` so unique Arx private profiles also set `hide_metadata`. The singleton is retained. A boolean-only probe can verify this flag with a disposable private media page without exporting its metadata; macOS redaction happens later in SystemMediaControlsNotifier and still requires actual native/OS validation. Private media controls remain denied.

Controlled video/PiP fixtures exercise this native contract. Display/fullscreen/Stage Manager interactions, accessibility and protected-content behavior require separate manual acceptance; the fixture does not claim them.

ABI7 provides profile-scoped extension inventory and revision-checked management in `extensions_bridge`. Precise preference notifications distinguish only the pinned operational fields `active_bit`, `running` and `is_active`; these still rebuild the bounded snapshot using its current fixture classification and invalidate on semantic drift or read failure. Unknown/key-less preference notifications, every other key (including hidden granted/desired permissions), and registry/disable/runtime-permission transitions invalidate unconditionally, preserving permission and registry ABA. Legacy Chromium observers receive exactly one forwarded notification. Fresh owned extension fixtures log at most 64 sanitized, 96-byte key/category labels per inventory, with no preference values. Registry and preference observers invalidate tokens across load/disable/permission changes; each mutation rebuilds its bounded snapshot and repeats native management-policy checks. Enabling removes only the sole user-action disable reason, with no permissions escalation, unsupported manifest version or policy prohibition. It never calls the grant-permissions path. Other disable reasons, including unknown reasons, remain intact. Uninstall success means removal from Chromium's registry; asynchronous data cleanup is not represented as verified disk erasure.

Native Return to Tab uses a neutral, runtime-owned initiator callback on PictureInPictureWindowManager. Unset or unowned-source callbacks preserve Chromium's default. Generic WebContents activation/window.focus is not routed through Arx media. The hook posts generation-checked activation before non-pausing native close; per-page observers never overwrite/clear the global hook. Deferred invalidation also captures the PiP-entry epoch so it cannot close a replacement session.

The back/forward cache is on (DEV-943): `Page::IsBackForwardCacheSupported` returns true, so Back and Forward restore a cached document instead of reloading it. Each page keeps at most three cached documents by default (`kDefaultBackForwardCacheEntries`, set with `SetEmbedderSuppliedCacheSize`; Chrome keeps six). Settings › Advanced › Memory › Pages kept for Back and Forward chooses 0 to 6 (`kMaximumBackForwardCacheEntries`): `BackForwardCacheEntries()` reads it once at launch through `FeatureFlag("ARX_BACK_FORWARD_CACHE_SIZE")`, from the environment or else Arx's defaults where Settings writes it, prints it to stderr when it isn't the default, and keeps the default for anything unreadable or too large. 0 turns the cache off: `IsBackForwardCacheSupported` returns false and no size is set. No ABI change. Chrome's time to live (10 minutes, 3 for `Cache-Control: no-store` pages) and its memory-pressure trimming stay. Prerendering stays off. A restore commits as a cross-document navigation with no new document (`IsServedFromBackForwardCache()`), and an old `WeakDocumentPtr` becomes current again, so state that must not outlive one visit is keyed on the close generation, which every commit bumps, or ended when the document is left. Per-document prompt counters (ABI21/ABI22) live in `DocumentUserData` and come back with their document. Inspection and PDF export retire a frame's pipe and slots when it enters the cache (`RenderFrameHostStateChanged`), credential listings and pending reads end on `PrimaryPageChanged`, a sign-in waiting for its next step ends on any committed document change, the media observer doesn't wait for a restored document's players to start again (Chromium re-adds them paused, with no `MediaStartedPlaying`), while its command generation still changes, and it keeps the restored document's artwork (DEV-960, see `bfcache_media_session_overlay.py`), and `Page::RenderFrameDeleted` ends the Escape and link-menu state only when one of their own documents goes, never for an evicted cached document or its subframes. `make back-forward-cache-smoke` covers a restore.

An unconfirmed media entry that is canceled, times out or invalidates quarantines further PiP entry for that native page's lifetime. Website handlers carry no Arx request ID into the delegate; a late handler must not borrow a later command's authority. Chromium rejects currently inactive frames, but a delayed handler can survive a BFCache restore, so cross-document navigation alone does not clear quarantine. Recreating the native tab session clears it; play/pause/exit remain available. The retry-before-late-handler video fixture covers this conservative limit.

ABI8 appends `media_source_is_current(page, generation)`, a synchronous read on the Chromium UI thread. It resolves the live page registry, refuses OTR/unobserved pages and reads the observer’s current generation, presence, crash/awaiting-player flags and existing session. It neither refreshes nor posts work nor changes focus. Invalidation changes generation before queued snapshot delivery, so old Swift state cannot authorize Return to Tab.

ABI32 appends `media_position`, `seek_media` and `set_page_audio_muted` for ordinary observed pages; private pages are refused. The snapshot gains `ARX_MEDIA_CAN_SEEK` when the session offers SeekTo (controllable media that isn't live). `seek_media` uses the same single request slot, exact generation/revision check, five-second timeout and cancellation as other commands, clamps to a known duration and calls `MediaSession::SeekTo`; it completes once the session's position reaches the target, polling the session every 100 ms natively while the seek is pending because position notifications are coalesced. `media_position` reads `GetMediaSessionPosition` once, extrapolated to the time of the read, plus the page's audio mute; position never enters the snapshot, so playback doesn't publish per-frame changes. `set_page_audio_muted` calls `WebContents::SetAudioMuted`. Chromium removes a muted page's playing player from its media session (outside PiP), so that source disappears until the page is unmuted.

ABI53 (DEV-906) appends `ARX_MEDIA_NEXT_TRACK` and `ARX_MEDIA_PREVIOUS_TRACK` with their `ARX_MEDIA_CAN_NEXT_TRACK`/`ARX_MEDIA_CAN_PREVIOUS_TRACK` bits (set when the Media Session offers `kNextTrack`/`kPreviousTrack`), and the snapshot gains `artist` and `artwork`/`artwork_size`. The track actions call `MediaSession::NextTrack`/`PreviousTrack` under the usual request slot and generation/revision check, and complete as soon as the session has them, since nothing on the page confirms a track change. The artwork is the session's `kArtwork` image that `MediaImageManager` picks for 256 px (at least 48), loaded through `MediaSession::GetMediaImageBitmap`, which downloads it from the frame that set it at no more than 256 px; the bitmap is converted to N32 and PNG-encoded on the UI thread, and a newer image or a cross-document navigation drops a late load. A document restored from the back/forward cache keeps its artwork (DEV-960): it keeps its Media Session metadata, and the session announces that artwork once, when the restored page is routed again, which can come before the navigation finishes. The PNG bytes ride the snapshot like its strings: copied into the posted task and borrowed during `media_changed`. 53 was taken beside perf-integration's 52; the integrator renumbers if another branch claims it.

Per-tab volume (DEV-800) is exported as `ArxEngineSetPageAudioVolume(page, volume)`, outside the ABI table and its version, so the app looks it up with `dlsym` and runs on engines built before it without volume. It takes ordinary observed pages only and a volume in [0, 1], and calls `WebContents::SetAudioVolume`. `audio_volume_overlay.py` adds that by mirroring Chromium's tab mute: `ForwardingAudioStreamFactory` binds a `media.mojom.LocalVolume` for the WebContents' audio group (again on every reconnect), and `audio_volume/arx_local_volume.{h,cc}`, copied into `services/audio`, sets a group gain on every `OutputController` in the group, current and future. The controller multiplies the page's own stream volume by it, so every player is covered, WebRTC included. Snoopers (tab capture) keep the unscaled signal, and muting still wins. Every other `AudioStreamFactory` implements `BindVolume` as a no-op, or as a refusal for TTS like its `BindMuter`.

Idle profile release (DEV-880) is exported the same way, as `ArxEngineReleaseProfile(key)`; without it the app keeps every profile until quit. It refuses, changing nothing, while `OrdinaryProfileInUse(key)` (the check retirement's `ProfileErasureMayQueue` uses too) sees a preparation, a page, a download, extension install, load, view or request work, or a page's consent prompt, for a key that isn't loaded, and for `Default` when it's Chromium's startup profile and the private parent (no erasure). Otherwise it stops the profile's download observation and drops its saved-passwords presenter and extension inventory, which hold raw pointers into the profile. It then clears Chromium's `kWaitingForFirstBrowserWindow` keep-alive (`ProfileManager::ClearFirstBrowserWindowKeepAlive`), which only a Browser window's keep-alive would clear and Arx never opens one, while its own keep-alive still holds the profile, and last erases its `ScopedProfileKeepAlive`; Chromium unloads the profile once no keep-alive of its own holds it (`kDestroyProfileOnBrowserClose` is on for macOS). A `ProfileObserver` watches each released profile until `OnProfileWillBeDestroyed`; `ArxEngineProfileIsLoaded(key)` reports whether Chromium still has a live profile for the key (held, released but not destroyed, or loaded in `ProfileManager`), which the release smoke checks. A released profile's path keeps its session cookies when it loads again in the same run: `session_cookies_overlay.py` lets `ProfileImpl::ShouldRestoreOldSessionCookies` ask `ProfileManager::ArxKeepsSession`, which the engine answers from `ProfileReloadKeepsSession` (set in `PreProfileInit`); otherwise Chromium deletes session cookies on every load after a clean destruction and sites sign the person out. Site settings watchers, browsing-data jobs, site icon requests and private download links observe the destruction themselves. The key stays ordinary, and `PrepareProfile` loads it again; `CreateProfileAsync` waits for a destruction still pending. `Scripts.tests.test_profile_release_native` runs the production check, release order and destruction tracking against stubs.

Tab unloading (DEV-873) lives in `page_unload_bridge.{h,mm}` and is exported as `ArxEngineUnloadPage(page, reason, blockers)`, `ArxEnginePageIsUnloaded(page)` and `ArxEngineRestoreUnloadedPage(page)`, outside the ABI table like per-tab volume. Arx pages are bare WebContents without Chrome's `TabLifecycleUnit`, so Performance Manager's `PageDiscarder` (and Memory Saver, which Helium leaves on) can't discard them (`kNoLifecycleUnit`); the app decides when, and the engine discards in place with `WebContents::Discard()`. Startup enables `WebContentsDiscard` for that (Chromium 156 enables it only on Android). On macOS the feature also makes Chrome's own `TabLifecycleUnit` discard in place instead of swapping in a new WebContents, which no Arx page has, and makes `RenderFrameHostImpl`'s destructor clear the main frame widget's discarding flag; nothing else reads it off Android. `PageUnloadBlockers` is the one place the engine decides: Chrome's `DiscardEligibilityPolicy::CanDiscardWithCustomRecentVisibilityWindow` with no visibility window (the app applies its own hidden time), `PROACTIVE` rules for the inactive reason (which also keep pages with notifications or background title and icon changes) and `URGENT` ones under memory pressure, so audible and recently audible pages, picture in picture, form interaction and user edits, PDFs, capture, USB and Bluetooth, an extension's opt-out and DevTools stay; then Arx's own: shown in a window, Arx's DevTools or any attached debugger, audible, picture in picture, being captured, loading, and no live document. DEV-1104's `kPageUnloadWindowClosed` (2) is for a page no window holds any more: it reads the proactive reasons but ignores sound and recent sound, picture in picture, notifications, background activity, camera, microphone, window, screen and tab capture, an extension's opt-out and enterprise opt-out (`IgnoredForClosedWindow`), and Arx's own audible, picture in picture and live-connection checks, so closing a window stops what it played; `UnloadPage` ends the page's video or document picture in picture through `PictureInPictureWindowManager` before it discards, since PiP closes with the window that owns its tab. PDFs and non-web pages, USB and Bluetooth, DevTools, Arx's capture, loading and no document still keep it, and form interaction or user edits report `kPageUnloadBlockedUnsavedInput` (1 << 10). `UnloadPageForApp` accepts 2; an engine built before it answers unavailable. DEV-1107's `kPageUnloadWindowClosedAnswered` (3) is the same for a page whose window asked its before-unload question before closing, and drops form interaction and user edits too; it's reached only through `ArxEngineUnloadAnsweredPage(page, blockers)`, and `ArxEnginePageUnloadBlockers(page, reason)` reads `PageUnloadBlockers` without unloading, so the app can tell which pages a closing window must ask. Both are in `page_unload_bridge.mm` and `EXTRA_EXPORTS`. Picture in picture ends even when a blocker keeps the page. DEV-879's WebSocket/WebTransport exemption is there too (see "Live connections"). ## Idle renderers (DEV-944)

Before this change, with one tab open, Arx ran four renderers (`ps` shows each as `Arx Helper (Renderer)` with `--type=renderer`):

- the tab's page;
- uBlock Origin's background page in the tab's profile (`--extension-process`). Helium adds uBlock to every regular profile as a component extension, Manifest V2 with a persistent background page, so every loaded profile has one. Releasing unused profiles (DEV-880) removes the others;
- uBlock Origin's background page in the bootstrap profile `Arx-Bootstrap` (`--extension-process`), which the engine starts with when profile erasure is configured, as the app always does;
- Chromium's spare renderer, kept warm for the next page (no `--extension-process`, smallest footprint, no page).

The bootstrap profile never shows a page; it only starts the engine and parents the private contexts that have no opener (since DEV-889 a private window's context is its opener profile's off-the-record child). Its uBlock page filters nothing: uBlock's manifest says `"incognito": "split"`, so its `webRequest` listeners and messaging see only their own profile's traffic (`util::CanCrossIncognito` is false for split mode), and a private context gets its own instance from `IncognitoProcessManager`. Arx creates no Chrome `Browser`, so nothing calls `MaybeCreateStartupBackgroundHosts` for a private context, so, reading the code, private pages get no running uBlock instance today; the listing below in a private window confirms it (the manual says extensions aren't available in private windows). Refusing the bootstrap page doesn't change that. `background_pages_overlay.py` adds `ChromeProcessManagerDelegate::SetEmbedderBackgroundPageRefusal`; `EngineParts::PreProfileInit` installs a refusal for the regular profile named `Arx-Bootstrap` when erasure is enabled. uBlock stays installed and enabled there, because private contexts share its extension registry and prefs. Without erasure the startup profile is `Default`, which shows pages, and nothing changes. `ARX_BOOTSTRAP_BACKGROUND_PAGES` keeps Chrome's behaviour and prints `ARX_BOOTSTRAP_BACKGROUND_PAGES on` to stderr; it's on by default for the beta, like every feature flag (DEV-1143). `ARX_BOOTSTRAP_BACKGROUND_PAGES=off` (environment, or `defaults write dev.capturecontext.arx ARX_BOOTSTRAP_BACKGROUND_PAGES -string off`) installs the refusal.

The engine also starts with `KillSpareRenderOnMemoryPressure`. Chromium already stops making spare renderers under memory pressure, but keeps the one it has; with this, a memory limit of 50% or less (moderate pressure on macOS) scales the one spare to none and the spare exits. A new one is made by the next navigation or once pressure ends and the browser is idle.

To list them, with Arx running one tab on a fresh profile and idle for 30 s:

```sh
ARX=<pid of the Arx under test>  # not another running Arx
ps -A -o pid=,ppid=,command= | awk -v p="$ARX" '$2 == p && /--type=renderer/ {
  print $1, (/--extension-process/ ? "extension" : "page-or-spare") }' |
while read pid kind; do
  echo "$pid $kind $(footprint -p "$pid" 2>/dev/null | awk '/Footprint:/ {sub(/.*Footprint: /, ""); print $1, $2; exit}')"
done
```

Expect two `extension` renderers before this change and one after, and two `page-or-spare` renderers (the tab and the spare; the spare is the smaller one, and opening a tab on a new site reuses its pid). `sudo memory_pressure -S -l warn` simulates moderate pressure: the spare's pid exits. That's with `ARX_BOOTSTRAP_BACKGROUND_PAGES=off`; the default gives the old count. For the before/after memory, run the DEV-939 benchmark's idle 1-tab and 10-tab steps on one build with `ARX_BOOTSTRAP_BACKGROUND_PAGES=off` and with it on: total footprint should fall by about one extension renderer's footprint and the renderer count by one. The DEV-939 benchmark adds the same per-process listing.

## Memory feature flags (DEV-916)

Two feature flags, measured below; for the beta both are on by default like every feature flag (DEV-1143), so `ARX_SPARE_RENDERER` keeps Chromium's spare and `ARX_IDLE_TRIM` trims, and `off` turns either off. Each is read once at launch from the environment, or else from Arx's defaults under the same name (`defaults write dev.capturecontext.arx ARX_IDLE_TRIM -string on`), like `ARX_SCROLL_EDGE`, and prints its name and value to stderr when it applies.

- `ARX_SPARE_RENDERER=off` adds `SpareRendererForSitePerProcess` to `--disable-features`, so Chromium keeps no spare renderer (`RenderProcessHostImpl::IsSpareProcessKeptAtAllTimes` is false and `PrepareForFutureRequests` drops any spare). It saves one idle renderer; a new tab or cross-site navigation then waits for a renderer to launch. Ardia goes the other way (a spare before the launch tab, a 500 ms delayed fallback); that needs a hook where a profile becomes ready, so it waits for DEV-880.
- `ARX_IDLE_TRIM=on` checks every 5 s; once the page count has stayed the same for 5 s, there has been no input for 2 s (`CGEventSourceSecondsSinceLastEventType`) and the last trim was at least 30 s ago, it runs PartitionAlloc's `MemoryReclaimer::ReclaimAll` for the browser process on a best-effort worker. One trim per settled count, the first after launch settles. Chromium's periodic `ReclaimNormal` runs either way; `ReclaimAll` also decommits aggressively and purges thread caches.

## Live connections (DEV-879)

Infinite tabs freezing (Helium turns `InfiniteTabsFreezing` on) freezes every page outside the 5 most recently used that has no `CannotFreezeReason`, and a freeze ends the page's connections: `DOMWebSocket` fails its socket ("Page entered Back-Forward Cache") when its frame freezes while `DisconnectWebSocketOnBFCache` (stable) is on, and `WebTransport` closes its session. A chat tab without notification permission then disconnects at every freeze and reconnects in each 5-second periodic unfreeze. WebRTC is already Chromium's `kWebRTC`, and pages with notification permission `kNotificationPermission`.

`content/arx_live_connection.{h,cc}` (copied by `Scripts/engine/live_connection_overlay.py` to `content/public/browser/` and `content/browser/renderer_host/`, the latter added to `content/browser/BUILD.gn`) adds `content::ArxPageHoldsLiveConnection(WebContents*)`: any frame of the primary page has `kWebSocket`, `kWebSocketSticky` or `kWebTransportSticky` among its back/forward cache features (`RenderFrameHostImpl::GetBackForwardCacheDisablingFeatures`). With `DisconnectWebSocketOnBFCache` on, Blink registers only the sticky WebSocket feature, and a WebTransport's own `kWebTransport` never reaches the browser, so the check means "has opened one since this document loaded"; it stays true after the page closes the connection, until the document is replaced. The overlay makes `FreezingPolicy::UpdateFrozenState` ask it, lazily, before freezing for infinite tabs (with or without memory pressure); voting and Battery Saver freezing stay Chromium's. It isn't a `CannotFreezeReason` because nothing reports when it changes: a page frozen before it opened a socket is reconsidered at its next periodic unfreeze, which ends with a fresh `UpdateFrozenState`. `PageUnloadBlockers` adds `kPageUnloadBlockedLiveConnection` (1 << 9, `ChromiumPageUnloadBlockers.liveConnection`) for the inactive and memory pressure reasons, so tab unloading keeps the same pages; a closed window's reason ignores it (DEV-1104).

`kArxSpareLiveConnections` is on by default. `ARX_SPARE_LIVE_CONNECTIONS=off`, read like the memory feature flags below, adds it to `--disable-features` and prints `ARX_SPARE_LIVE_CONNECTIONS off`. Measure with it: idle CPU and wakeups at 50 real-site tabs after the freeze wait (`make benchmark`'s Native step, `--freeze-wait`), with and without the feature flag, and how many of those tabs stay unfrozen because of it (the frozen count difference). On the loopback fixture, `make benchmark ARGS='--live-connections 0.2'` makes a fifth of the tabs hold a WebSocket and counts their frozen pages and open connections apart. `make tab-unload-smoke` checks the exemption end to end; with `ARX_SPARE_LIVE_CONNECTIONS=off` in its environment it reproduces the disconnect and fails at `liveConnectionLost`.

## Widevine answered without a CDM (DEV-1144)

Arx uses no Widevine: no CDM, no component, no download, never registered or loaded (`component_updates.h`); every protected playback is FairPlay, through Arx's FairPlay helper or a WebKit page. Pages that saw no Widevine at all may treat that as a bot: Apple's online store answers its checkout steps with HTTP 541. `widevine_answer_overlay.py` adds `media::kArxWidevineAnswer` (on by default). While it is on and no Widevine CDM is registered, `components/cdm/renderer/key_system_support_update.cc` lists Chrome's Mac Widevine entry: software-secure VP8, VP9, AV1 and H.264, `cenc` and `cbcs`, temporary sessions only. `requestMediaKeySystemAccess('com.widevine.alpha', …)` resolves, and `createMediaKeys()` rejects with NotSupportedError because `MediaInterfaceProxy::CreateLibraryCdm` finds no CDM factory. Nothing can reach a real Widevine CDM, even one that appears on disk: the renderer skips any Widevine capability the browser reports, and `CreateLibraryCdm` refuses `com.widevine.alpha` before it looks for a factory. `ARX_WIDEVINE_ANSWER=off`, read at launch like the other engine feature flags, adds `ArxWidevineAnswer` to `--disable-features`; Chromium passes feature state to renderers.

The protected media handler moves with it. While the answer is on, `KeySystemSupportImpl::SetObserver` (a page's first EME question) no longer reports, since a probe that only asks would then offer WebKit for Apple's checkout. `CreateLibraryCdm`'s missing factory reports instead, through `arx::ReportProtectedMediaFailure` in `protected_media_hooks.h`; that's where a page that really wants protected media now fails. So does a document left without protected media, once: a `navigator.requestMediaKeySystemAccess` the renderer refused (a configuration the answer doesn't cover, such as a persistent licence or hardware-secure robustness, or another protected key system such as PlayReady or FairPlay), where the page never creates a CDM, and no protected key system granted to the document within 3 seconds (DEV-1205). Bot detection asks about every key system: Fingerprint's agent (resend.com) asks `MediaCapabilities.decodingInfo` about Widevine, then `requestMediaKeySystemAccess` for Widevine with and without a persistent licence, PlayReady, Clear Key, Primetime and FairPlay. Chrome on a Mac and Arx grant Widevine and Clear Key and refuse the rest, so the grant keeps such a page from being offered WebKit. `decodingInfo` is a capability query and never reports a refusal: only `MediaKeySystemAccessInitializer::RequestNotSupported` (`navigator_request_media_key_system_access.cc`) calls the new `WebEncryptedMediaClient::ArxReportAccessRefused`. `WebEncryptedMediaClientImpl::OnConfigSelected` reports every grant, from either API. Clear Key, under any of its names (`org.w3.clearkey`, `webkit-org.w3.clearkey`, External Clear Key), is never protected media. The client tells the frame's `KeySystemConfigSelector` delegate, which calls the new `KeySystemSupport.ArxReportAccessRejected` and `ArxReportAccessGranted` on a connection it keeps, so a refusal and a grant arrive in order (the renderer drops its first connection after `SetObserver`, so `KeySystemSupportImpl::Bind` takes the newer one; the observer stays single). `KeySystemSupportImpl`, one per document, starts a 3-second timer on a refusal and reports only if no grant came and its `RenderFrameHost` is still active when it fires: a document the person left for the back/forward cache keeps its timer, and a prompt for it would show over the next page. DEV-1211 (Max's rule: a streaming site falls back to WebKit with a prompt, and a likely bot check stays in Chromium with none): each report says why, as `arx::ProtectedMediaReason`. A media element that wants keys (`HTMLMediaElementEncryptedMedia`: `setMediaKeys` with keys, the `encrypted` event, playback waiting for a key) reaches the document's `KeySystemSupportImpl` through the new `WebEncryptedMediaClient::ArxReportMediaWantsKeys` and `KeySystemSupport.ArxReportMediaWantsKeys`, on the same kept connection. `arx::ReportProtectedMediaFailure` no longer calls the observer: it records the failed keys on the frame's document (`ArxNoteKeysFailed`). A media element counts in the document or in any same-origin document of its page (`ArxPageMediaWantsKeys`): a player may keep its video in an iframe and make its keys in the parent. Each document keeps its own state and reports. Keys that failed are `kPlaybackFailed` once a media element wants keys, and `kKeysWithoutMedia` until then: a bot check may create keys it never uses, and a streaming player may stop before it loads media, so the app decides by the site. A refusal waits 3 seconds for a grant, with the answer on or off: with it on, a document granted nothing is `kPlaybackFailed` (DEV-1205); with it off every page is refused Widevine, bot checks too, so it's `kPlaybackFailed` only once a media element wants keys, else `kKeysWithoutMedia`. The first question reports nothing. Each reason reports once per document, nothing after `kPlaybackFailed`, and only while the document is active, except that each failed key creation reports again, as before: the app may not have shown the first. `protected_media_overlay.py` upgrades a tree prepared with its DEV-877, DEV-1144 or DEV-1205 version, step by step. The overnight `webkit-fallback` app smoke checks it: a page whose keys fail and whose `<video>` meets encrypted media gets the prompt, and a keys-only page on a site nobody listed gets none.

## Page media bridge (DEV-1144)

FairPlay in Chromium tabs needs a script in the page's main world before the page's own code, and a private channel between it and the app. `page_media/` (copied to `components/arx_page_media` by `page_media_overlay.py`) has the `arx.page_media.mojom` interfaces and the renderer side: `PageMediaAgent`, a `RenderFrameObserver` made for each outermost main frame next to the inspection `Inspector`.

- **Preparing.** `page_media_bridge.mm`'s `PageMediaPreparer` (attached to every Arx page by `engine_bridge.mm`) sends `Prepare(origin, script)` on the frame's channel at `ReadyToCommitNavigation` for every cross-document commit of the primary main frame that isn't a back/forward cache restore: the script when the origin to commit is bridged, empty strings otherwise, so a stale preparation never runs later.
- **Running.** At `DidCreateDocumentElement` the agent picks the prepared script for the first document whose serialized origin is the prepared one; the frame's initial empty document keeps the preparation. It runs the script once, in the main world, from `ChromeContentRendererClient::RunScriptsAtDocumentStart`, where extensions run their `document_start` scripts and script may run (`DidCreateDocumentElement` runs inside Blink's `ScriptForbiddenScope`), before those extensions and the page's own code. The script evaluates to `function (send) { …; return receive; }`. `send` is a gin function passed as an argument, so the page never sees it as a global; `receive` takes the app's messages. A new document drops the previous one's script and host; `document.open()` keeps them.
- **Messages.** The script's first `send` binds `PageMediaHost`, registered in `ChromeContentBrowserClient::RegisterAssociatedInterfaceBindersForRenderFrameHost` through the dependency-free `page_media_hooks.h`. The binder accepts only an active primary main frame of an Arx page whose committed origin is bridged, and scopes the receiver to that document (`PageMediaDocument`, `DocumentUserData`), numbered by the engine. Every message is checked again (active, primary main frame, origin still bridged, at most 4 MiB) and posted to the app's handler with the page and document number. The posted task checks once more, through the document's `WeakDocumentPtr`, that it is still the page's current, bridged primary document, so a message sent just before a navigation commits never reaches the app as the next document's. The app's replies go to that document only: `ArxEngineSendPageMedia` refuses another document, and the agent drops a reply whose context is no longer the frame's.

`ArxEngineSetPageMediaBridge(origins, count, script, handler, context)` and `ArxEngineSendPageMedia(page, document, message, length)` are exported outside the ABI table; the app looks them up with `dlsym` (`ChromiumPageMedia.swift`), so older engines load without the bridge. Origins must be exact, serialized `https` origins, at most 64; the script is at most 1 MiB. Turning the bridge off affects the next documents; documents already running the script keep it, but their messages reach no handler.

- **Keeping a playing page running (DEV-1151).** While Arx's FairPlay helper plays a bridged document's track, Chromium sees a silent page with no player it knows, yet the page's script answers licence renewals and moves to the next track. `ArxEngineSetPageMediaKeepsRunning(page, document, keeps)` gives the page a `ScopedMediaRunnableLease` (from `media_freeze_overlay.py`), the resource-only exemption that keeps it out of voting, Battery Saver and infinite tabs freezing, as a page playing sound is. The app holds it while the helper holds the document's track, paused too, so Now Playing's commands still reach a running page (`FairPlayBridge.onHolderChange`). `PageMediaPreparer` owns it and drops it when the app does, when the primary page changes, or with the page; it refuses a document that isn't the page's current bridged one. In `chrome://discards` the reason reads as the picture in picture candidate's, the lease it shares. Exported outside the ABI table too.

## Dark pages (DEV-1020)

`dark_pages_bridge.{h,mm}` darken Arx's pages with Blink's own forced darkening, the `force_dark_mode_enabled` web preference that Chrome's Android night mode uses. `dark_pages_overlay.py` ends both of `ChromeContentBrowserClient`'s web-preference paths, `OverrideWebPreferences` (after the color scheme is computed) and `OverrideWebPreferencesAfterNavigation`, with `arx::ApplyDarkPages`. For an Arx page (one that `Page`'s constructor gave a `DarkPagesData`) whose main document should be dark, it sets `force_dark_mode_enabled` and a dark `preferred_color_scheme` and root scrollbar scheme. With both, an element whose `color-scheme` includes dark keeps the site's own dark theme (`ComputedStyleBuilder::SetUsedColorScheme`), `color-scheme: only light` opts out, and everything else is darkened. A site whose dark theme comes only from `prefers-color-scheme: dark` rules gets exactly that theme (DEV-1077, DEV-1094, DEV-1095). The overlay's Blink part has `MediaQueryEvaluator::Eval(const MediaQuerySet&, …)` note whether a whole query with a matching `dark` feature in it matched; `(prefers-color-scheme: dark) and (max-width: 600px)` on a wide window doesn't. `RuleSet::MatchMediaForAddRules` asks right after its evaluation and marks the rule set as holding a dark theme; rules under a media rule that doesn't apply are never added, so a dark query nested in one never counts. An empty query set (a media-less `@import`) never counts, a later query in a list may (`(min-width: 600px), (prefers-color-scheme: dark)`), and a cached rule set is rebuilt when its answer changes though every set kept its result (`RuleSet::DidMediaQueryResultsChange`). After every active style sheet update `StyleEngine` asks the active rule sets of the document, its shadow trees (adopted sheets included) and its user-origin sheets (an extension's `insertCSS`), and each sheet's own media (`<link media>`, `<style media>`); a media query in a CSS `@function` or `if()` counts while it applies (`EvaluateFunctionalMediaQuery` notes it, and the functional results are asked again before Blink drops them). When the answer changes, it updates the color scheme from a posted task (not inside the style update); `UpdateColorScheme` then drops `force_dark_mode_enabled_` for that document while it holds, keeping the dark preferred scheme. So a theme added or removed later, or one a media change brings in or out (rule sets are rebuilt then), is followed without a reload. Each document decides for itself, and a script's `matchMedia` doesn't count: only styles that apply do. Chrome's own pages, DevTools and extension pages have no `DarkPagesData` and are never touched.

A document is dark when the page's setting is on and its main frame's last committed URL is http(s) with a site that isn't turned off (the lowercased host without a trailing dot or `www.`, matching an off site or one of its subdomains, as `KeptLoadedSite` does), or is empty or `about:blank`, so a new page's blank document starts dark and never flashes white. The decision follows each navigation, so a page that moves between a darkened site and one turned off may show its first frame in the old look.

`ArxEngineSetPageDarkPages(page, enabled, off_sites, count)` is an optional export outside the ABI table (in `overlay.EXTRA_EXPORTS`): page 0 sets the default `Page` gives new pages; any other page, ordinary or private, gets its own setting and is restyled at once (`NotifyPreferencesChanged`) when its current document's decision changes. More than 4,096 sites are refused. Printing already turns forced darkening off (`StyleEngine::UpdateColorScheme`).

Renderer ends (ABI58, DEV-1016): `Page` numbers each end of its primary main frame's renderer in `PrimaryMainFrameRenderProcessGone`, with Chromium's `base::TerminationStatus` (the header's `ARX_RENDERER_END_*` values are static-asserted equal) and whether `EndRenderer` asked for it. The exit code comes from `RenderProcessExited` on the main frame's process, which `Page` observes and follows across process changes; whichever of the two arrives second completes the end, and `page_changed` follows. `page_renderer_end` copies the last end. An unload (DEV-873) isn't an end: it's neither numbered nor its exit code kept. `end_page_renderer` on an out-of-process frame's hung renderer forgets the hang there, since no main-frame end follows, and every renderer process it ends is remembered by id (`EndedRenderers`), so each page that process drew, the one that asked or another sharing it, reports the end as the engine's; the mark goes when the host launches a new child (`RenderProcessReady`) and after 30 s at most, so a later crash of a reused host is its own. Chromium's hangs are kept per renderer with each one's restarter: the page answers again only once every hung renderer has, and Wait restarts them all. `end_page_renderer` ends every hung renderer at once, the main frame's and out-of-process frames', so recovery never leaves one frozen.

ABI59 (DEV-1065) counts a page's main-frame documents: `Page` adds one to `main_documents_` wherever it starts a new `document_id_`, on a primary main frame's cross-document commit (a reload or the page's own `location.reload()` included; a fragment, `history.pushState` or a frame in the page isn't one), and `page_main_document` reads it. `page_changed` follows the commit.

ABI62 (DEV-1264, DEV-1073) reports the ⌘ keys a focused page used. `Page::PreHandleKeyboardEvent` hands each original ⌘ key down (`page_command_key.h`'s `PageCommandKey::IsCommandKey`: no repeat Chromium drops, `kRawKeyDown`) to `PageCommandKey`, which observes the focused frame's widget (`RenderWidgetHost::InputEventObserver`) for that key's ACK, matched by key code, modifiers and timestamp. A consumed ACK (the page called `preventDefault`) posts `page_command_key(..., consumed: true)` with the generation the key was pressed in. An unconsumed one waits for `Page::HandleKeyboardEvent`, which Chromium calls next with the same event, and asks the app synchronously (`consumed: false`); the app returns true when it ran its own command. A newer ⌘ key supersedes the followed one, and the widget's end forgets it. The app lets the keys whose Conflict resolution isn't Arx (DEV-1332), and ⌘Z and ⇧⌘Z, through to a focused page and decides from these reports; every other key keeps its route. Compile proof only until the engine is built.

DEV-1332 widens what's followed from ⌘ keys to every combination Arx can bind: ⌘ or ⌃ held, or an F-key with or without modifiers (`IsShortcutKey` in `page_command_key.mm`). Plain typing, ⌥ characters and Escape are never followed, so text input and IME composition gain no reports and no latency; a followed key is kept only until its answer, and the app ignores answers for keys it didn't let through. `bool ArxEngineFollowsAllShortcutKeys(void)` (outside the ABI table, in `overlay.EXTRA_EXPORTS`) returns true, so the app knows it may let ⌃ keys and F-keys through; with an engine built before it the app keeps them Arx's. Compile proof only until the engine is built.

Extension popup windows (DEV-1316): `ExtensionActionHost` shows an extension's action popup in a window instead of an `NSPopover`. The page is still the `ExtensionViewHost` popup (`kExtensionPopup`), so `chrome.extension.getViews({type: "popup"})`, a `setPopup` URL, messaging, the consent host and the popup's links work as before; only its host changed. `chrome.action.openPopup` still answers "No active window found", as before: Chromium opens it through a Chrome `Browser`, which Arx's pages don't have (DEV-1327). Each popup is its own `ExtensionView`: one per extension over a page, at most 8, the last shown named by ABI22's `PopupContents` and any of them by `HostsPopup` (`windows.getCurrent` from a second popup). A page is its window's active tab for `tabs.query` and `windows` only while one of its popups has the keyboard (or is still loading), `HasFocusedPopup`: a popup left open while the person works in another pane doesn't hold the active tab. The window is the app's when it gave one through `ArxEngineSetExtensionPopupPresenter(make_window, resize_window, closing, context)`, which gets the extension's name and the icon its toolbar button shows on that page for its header (the `setIcon` or declarative PNG, else the path of the action's default icon or the manifest icon nearest 64 pixels, joined and never resolved) (outside the ABI table, in `overlay.EXTRA_EXPORTS`), else the engine's own utility panel titled with the extension's name. The engine hangs it by the middle of its top edge from where the popover's arrow pointed (the app's point or the native button, kept relative to the page's window, so a popup that moved with its window stays there when it resizes), inside the screen's visible frame, as a child window of the page's window (above it, moving with it, full-screen auxiliary), makes it key, and keeps it the size the page lays itself out at, 25 × 25 to 800 × 600 points, through `resize_window`, which keeps the top-left corner; the engine then rehangs it from the anchor unless the person moved it. It closes on its Close (the window closing), on Escape the page doesn't take, on the page's `window.close()`, with the source page (navigation, closing, hiding, extension unload), and when it loses focus as `closing` says: `ARX_EXTENSION_POPUP_CLOSES_UNLESS_MOVED` (default; a window the person dragged, which AppKit announces with `NSWindowWillMoveNotification`, stays), `..._CLOSES_ON_FOCUS_LOSS` (Chrome's) or `..._STAYS_OPEN`. Focus going to its own sheet or a modal panel (a file chooser), back to it, or a debugger attached to it (DevTools) doesn't close it. Asking for an open popup's extension again brings it forward; opening another extension's closes the open ones the rule wouldn't keep. `make extensions-smoke` covers it in the `popup-window` phase (`ARX_EXTENSION_SMOKE_POPUP_WINDOW`).
