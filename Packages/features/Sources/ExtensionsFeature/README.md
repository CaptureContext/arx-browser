# ExtensionsFeature

Per-profile Settings panel for inventory, declared required/optional permissions, active/withheld permissions, native disable reasons, existing enable/disable and explicit removal confirmation. Depends on BrowserCore, BrowserExtensionsClient, AppUI and the TCA wrapper; never imports ChromiumEngine.

The panel's header is AppUI's `ArxHeaderBar` (DEV-782): a round Close button that also answers Escape, the title over the profile's name, and its actions (Load Unpacked, Chrome Web Store, Check for Updates, Install Package and Refresh, each when available) as icons in one `ArxIconActionGroup`, each naming itself in a tooltip on hover, so the title and profile never truncate (DEV-872). The extension list and details scroll under soft edges.

SettingsFeature configures the selected ordinary profile. Profile replacement/deletion, dismissal and new requests invalidate older callbacks and confirmation. Each request cancels the previous one synchronously in reducer order rather than through `cancelInFlight`, so a request that registers late cannot cancel a newer load and leave the panel working. Mutations carry the exact inventory token/profile/revision/extension ID and never optimistically change rows. Failed or canceled operations require refresh; no successful removal is claimed until authoritative inventory omits the item. Permission-escalation and unknown disable reasons cannot enable an extension.

The entry remains hidden when the injected capability is unavailable. The default client stays unavailable; the integrated BrowserCapabilities composition supplies live runtime readiness and current ordinary-profile ownership. The native inventory/management fixture verifies the corresponding engine boundary. A separate live options capability exposes Open Options for an enabled manifest-defined options page only. It consumes the displayed profile/inventory/revision and publishes an already-owned native session into a Little Arx for that exact ordinary profile (DEV-1185). Existing viewers stay in place. Action popups and native messaging remain separate. Tests are in ExtensionsFeatureTests and run on the macOS host with deterministic clients.

When the independent installation capability is available, a user may choose a signed CRX file for a new install or explicit update. An immutable picker context binds the selected profile and inventory; late picker results are rejected. The panel presents Chromium-verified package identity, source basename/hash, warnings and required/optional permissions before an explicit Install/Update action. No service or proxy choice is enabled by this consent. Profile changes/dismissal/cancellation invalidate pending prompts; the client retains native physical work until cleanup. Action popups and native messaging remain outside this UI. Tests are in ExtensionsFeatureTests and run on the macOS host with deterministic clients.

With app-wide developer mode on (AppFeature forwards it with `configureDeveloperMode`) and the independent folder capability available, the header offers Load Unpacked… and unpacked rows offer Reload and show their folder. The standard folder panel (`fileImporter` for `.folder`) returns into an immutable selection bound to the displayed profile and inventory, so a late result after a profile change, dismissal or developer mode change is ignored. Reload is a revision-checked management request; Remove is unchanged. Missing, unreadable and invalid-manifest folders each show their own message, the last with Chromium's reason. Turning developer mode off withdraws the controls and any open folder panel without touching inventory or installed extensions.

When the client reports Chrome Web Store installs available (DEV-765), the header offers **Chrome Web Store**, as does an empty extension list with a hint (DEV-801), which asks AppFeature (`delegate(.openWebstore)`) to open the store in a window of this profile. When the store's Add to Chrome runs in a page, AppFeature presents this sheet for the page's profile and sends `webstoreRequested`. The request waits for the profile's inventory, then the client downloads and verifies the package, and the usual review sheet shows it with **Chrome Web Store** as its source. A request the sheet can't take (another profile, another review open, a picker open) and a request still waiting when the sheet closes or switches profile are declined, so the store hears that the user cancelled. Presenting a sheet that is already open with work in flight (a load, a store download, a review) changes nothing, so a second Add to Chrome or Manage Extensions can't cancel it (DEV-801). `reveal(id)` selects an extension once the sheet lists it (the site menu's tiles), and an accepted install selects the extension it installed.

**Check for Updates** (DEV-776) appears when the client reports store updates and the profile has a store extension the user may replace. It checks them one at a time against the displayed inventory: nothing newer moves on with the same inventory; an update that asks for nothing new is accepted at once; one with `permissionIncrease` shows the usual review sheet and waits. A declined review or a failed check reloads the inventory and goes on. When the check ends, the sheet says how many were updated, skipped (declined) and couldn't be checked, and "up to date" only when nothing newer turned up.

**Update needs review** (DEV-1210, the `ARX_EXTENSION_UPDATE_REVIEW` feature flag, on by default, read at launch into `updateReviewsEnabled`): `updateReviews` is `@Shared(.extensionUpdateReviews)`, the store updates the app's automatic check turned down for asking more permissions, per profile and extension, with the version offered, its permissions and the installed version it would replace (`ExtensionUpdateReviews` in BrowserExtensionsClient). `pendingUpdateReviews` are this profile's. Such an extension's row says "Update needs review" with a mark beside it, and its details say which version waits; the mark and **Review Update…** send `ui(.reviewUpdate)`, which runs Check for Updates for that extension alone (`prepareWebstoreUpdate`, then the review sheet and `resolveInstallation`). `reviewUpdateRequested` (from the site menu, which opens the sheet first) waits in `requestedReview` until the inventory is in and a running check has ended. Declining an update check's review, or a package of the very version that waits (Update from Package…), records that version as declined, so the automatic check doesn't mark it again until a newer one turns up; `upToDate` withdraws the mark; and every loaded inventory drops the profile's marks for extensions that are gone or now have another version, so an accepted update, a manual update or a removal clears it. Off, nothing is marked and the actions do nothing.

`ExtensionInstallReview` is the review sheet itself, for the Extensions sheet's installs and updates and for installs an agent asks for. It names the publisher under the name when the package's manifest gives an author (DEV-968). Extensions brought over by an import get MigrationAssistantFeature's shorter `ExtensionImportReview` instead (DEV-1300), which shows each one's permissions with `ExtensionPermissionsList`, public for it.

DEV-889: `setAllowedInPrivate` turns Chromium's per-extension incognito switch on or off for a row whose engine offers it (`canAllowInPrivate`), from the row's Allow in private windows switch, off by default. A private window belongs to the profile it was opened from, and only that profile's extensions with the switch on run in it. Helium's uBlock Origin has no switch: it always runs there.

DEV-951: `automationInstallRequested` is an MCP client's `installExtension`. Like a store request it waits for the presented sheet to load its profile. It hands that inventory to the app (`automationInstallInventoryLoaded`) and holds the sheet until `automationInstallProceed`, then prepares the item by ID through `prepareWebstoreImport` (DEV-845's path). A profile that has only just started moves its revision while the package downloads; after each `staleInventory` the sheet reads the profile again (its own read, still holding the sheet; a cancelled request or an item installed meanwhile ends it) and prepares once more, and the third in a row fails the install and shows the same `ExtensionInstallReview`, with a line naming the client (`reviewRequester`). The review is the approval. `automationInstallFinished` reports `installed`, `declined` (Cancel, or the sheet closed or switched profile on the review), `alreadyInstalled` (no review), `failed` with the client's failure, or, before anything starts, `busy` (another review, store request, update check or package selection) or `unavailable`. Store requests, Check for Updates and Install Package wait while it runs (`AutomationInstallTests`).

Each row and the selected extension's details show its icon as AppUI's `ExtensionIconTile`, or its first letter when it has none (DEV-824 follow-up). After every load the feature reads, through `BrowserExtensionsClient.icon`, each listed extension's icon for the details' 50 pixels (`BrowserExtension.iconPath(pixels:)`) and keeps them in `State.icons` by path, so an unpacked extension reloaded after its icon changed shows the new one at the same path. Until they arrive the rows keep the icons they show, less those of extensions the inventory no longer lists. A path that can't be read shows the letter. A component extension, such as uBlock Origin, shows its `bundledIcon` instead, since its files aren't on disk.
