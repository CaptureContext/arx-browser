# AppFeature

The DEBUG `ArchiveSmoke` helper uses the app runner's owned disposable profile root and loopback identity page. It creates fresh source/destination profiles, verifies selected-only native closing, observes archive retention during staged opens, and checks fresh restored identities against distinct cookie/localStorage sentinels. It does not alter the application's workspace or claim native focus, VoiceOver or interactive before-unload acceptance.

SavedPageReset captures normal-window and borrowed-Peek placements when a saved-page reset starts. Once native close completes, it clears unchanged presentations and their saved pane references across windows. Native absence is checked on the main actor immediately before synchronous action delivery, and each later handoff revalidates pane or Peek identity. Reopened native sessions, new pane generations, and previews undergoing promotion are preserved. Borrowed Peek release reuses the existing handoff and does not ask for a second close approval or close the page twice.

Application composition and the Chromium-first bootstrap. Application forwards to BrowserApplication.main; Chromium installs its application and owns the main loop before AppKit starts.

AppFeature composes identified main windows and owns focused routing, shared organization, open/closed state and cancelable quit. BrowserWindow installs services and hosts the native windows. Cmd-N creates a window with its own selection and default sidebar width. Closing a window detaches presentation and releases the pages it held (DEV-1104, below); Dock reopen restores the primary window, its tabs unloaded until shown. Selecting a tab already shown elsewhere focuses its owning window. Organization changes propagate without replacing another window’s selection. Quit and Dock quit pass through save recovery and before-unload approval.

Window organization delegates publish their originating host's current sidebar state, not the captured payload. Other ordinary hosts reconcile synchronously at that boundary; only viewer and save effects remain deferred. An older notification therefore publishes the latest retained edit instead of restoring removed membership, and no queued reconciliation can overwrite the next host edit. Private hosts remain outside this publication path. This is notification ordering, not a merge of conflicting full-organization edits already overwritten by another publisher.

The production window uses AppUI, SidebarFeature, CommandBarFeature and identified ViewerItems through ViewerFeature. Cmd-T opens a new tab, Cmd-L edits the active address, Cmd-W closes or resets the active tab, Cmd-R reloads, and Cmd-S toggles the sidebar. The bottom menu creates folders and same-profile spaces.

ChromiumBrowserEngine uses isolated native profiles. The sidebar menu creates/selects profiles and offers explicit cross-profile tab moves. New native sessions retain separate credentials; failed destination creation leaves the source intact. Close/reset asks Chromium for before-unload approval. Viewer failures offer session recreation; history menus use native entry identities.

May depend on core, engine, services, AppUI and child features. Lower layers must not import AppFeature. IntegrationFeatureTests exercise reducer behavior. make app-smoke verifies a real local page, view attachment, title callback and clean Chromium shutdown in a disposable profile. make test-all checks the package graph, app and preview.

App startup loads the compiled AppIcon from the container bundle explicitly. BrowserCommands forwards app-owned shortcuts before Chromium consumes them, while standard text-editing key equivalents continue through the responder chain. The smoke check polls native attachment after navigation because a local page can finish before SwiftUI layout.

`LaunchSignposts` marks launch for `make benchmark` and Instruments (DEV-939): `ProcessStart` when `BrowserApplication.main` begins and `WindowShown` when the main window is first ordered on screen, as signpost events in subsystem `dev.capturecontext.arx`, category `Launch`; the engine adds `FirstPagePainted`. `BenchmarkDriver` runs only with `ARX_BENCHMARK_DRIVER=1` on a throwaway `ARX_ENGINE_PROFILE` in a windowed run. It reads JSON commands on stdin and posts synthesized key events to the app's own event queue, so the benchmark times ⌘T and ⌃Tab through the same key monitor, menus and command routing as real keys; it can also wait for the command bar's empty text field and insert an address there, as a paste would. Each command gets one `ARX_BENCHMARK_DRIVER {…}` reply line on stdout.

Dock reopen events are handled through NSAppleEventManager and routed to the Swift-owned window. Chromium retains its application delegate, but its default reopen handler must not restore Chrome windows against Arx's menu. Closed windows release their content host so retained pages can attach to a reopened window. The native app smoke test sends reopen Apple events with the window visible, minimized and closed, then verifies the loaded page is attached and exits cleanly.

LittleArxFeature owns temporary compact windows opened with Option-Command-A or incoming HTTP(S) links. AppFeature stages promotion, releases the old surface host, and selects the transferred tab in the main window. Same-profile promotion keeps the page identity; cross-profile promotion creates a new isolated session after confirmation. Settings is a singleton window opened with Command-comma. The packaged smoke also checks additional-window teardown, Settings reuse, and live Little Arx promotion.

Private Little Arx (DEV-1323, `PrivateLittleArx`) is an internal capability: `.privateLittleArx(.open(id, url))` prepares a private profile for that window alone, as a private window's, opens the address in a Little Arx marked `isPrivate`, and releases the profile when the window closes (`privateLittleArxProfiles`), by hand, by its page or by `.close(id)`. The window never joins the workspace or the archive, can't change profile or move to a space, and its command context is private. Nothing a person can do opens one: no command, menu, shortcut, setting or tool. Offering it is DEV-1329.

The member number's sign-in with Apple is its only caller (`MemberSignInWindows`). `MemberNumberClient` asks `MemberSignInWindow`; AppFeature opens Apple's authorize address in a private Little Arx and takes the redirect to `dev.capturecontext.arx.auth` in `onExternalLink`, before App Links, from that window's tab in its private profile only (`AppFeature.State.memberSignInLink`). Any other app's link from that window is dropped. The scheme isn't registered with macOS. The answer goes back to the client and the window closes; closing it by hand is a cancel, and ten minutes without an answer or a second sign-in is a failed sign-in. The app smoke's `member-sign-in` phase (`MemberSignInSmoke`, `Scripts/core/member_sign_in_smoke.py`) replays the server's post-then-303 shape on loopback.

Little Arx promotion publishes the added tab to every ordinary host synchronously, preserves background selections and panes, ends each window's open ⌘Z step (or, without `ARX_WINDOW_UNDO`, clears its history; DEV-1030), and marks the workspace unsaved before handoff effects. Surface release precedes explicit selection in the destination's saved layout; a newer user selection, window closure or navigation rejects delayed presentation without removing the promoted tab.

The packaged smoke runner also terminates only renderer children of its own disposable Arx process and verifies that ViewerItemFeature reports the failure and recreates the page. It does not enable internal Chrome navigation URLs. Physical keyboard/IME input, before-unload dialogs, and full-screen/multiple-display placement still require manual verification.

BrowserCommand defines stable identities and default equivalents; BrowserCommands builds native Arx, File, Edit, View, Tab, Window and Help menus from them and validates the focused host. Help uses macOS menu search. Application-local shortcuts are Cmd+, Settings; Cmd+N new window; Cmd+Shift+N incognito; Cmd+Option+A Little Arx; Cmd+Shift+C copy URL; Cmd+S sidebar; Cmd+D duplicate; Cmd+B pin; Cmd+R reload; Cmd+Shift+R clear the profile HTTP cache and reload. Existing Cmd+T/L/K/W/Q routes remain. Text-editing actions keep responder-chain targets. Custom bindings share these commands; the global Little Arx shortcut is an explicit opt-in.

RelocationRetry carries a failed move to Applications from the launcher in `Sources/Application`. While `isOffered` is set, BrowserCommands adds Move to Applications… under Onboarding in the Arx menu, and choosing it retries `AppRelocationClient.relocate(askFirst: false)` and quits when Arx was moved.

PrivateWindows creates a distinct Chromium off-the-record context per window. Its organization is held only by that window, excluded from persistence/export/reconciliation, and disposed after before-unload approval on close. Bookmarking in a private window is temporary. Creating additional persistent profiles is disabled there. Little Arx's app command is disabled while an incognito window is focused to prevent silently opening a private context in a normal profile. Each private profile is prepared with the ordinary profile that opened it (the focused window's profile, or for a private window the profile it was opened from, kept in `privateProfileOpeners`; with no window focused, as in a headless run, the main window's profile, else the workspace's first), so the window belongs to that profile: its context is the profile's own off-the-record child, which runs the profile's extensions allowed in private windows (DEV-889), and its downloads folder and "Ask where to save" follow the profile's (DEV-729). A profile with a private window open can't retire (`ProfileRetirement`), and ProfileLifetime keeps it loaded.

LittleArxPanel uses a borderless, content-measured command presentation with eight-point padding and no animated resizing while typing. Losing key-window status dismisses only this initial presentation. Submitting a destination switches to the resizable viewer with a unified toolbar. The shared AppUI window-control host aligns native traffic lights with both the main sidebar toolbar and Little Arx toolbar.

BrowserHostingView publishes explicit SwiftUI minimum layout bounds to AppKit: main windows (including additional/incognito windows) use 760 × 620 points; expanded Little Arx uses 600 × 320. The initial command panel retains its measured height. These limits must be part of hosted layout: AppKit ignores NSWindow minSize/contentMinSize when Auto Layout is active. WindowChromeTests cover the minimum layout proposals and command-to-viewer transition.

AppSettingsView supplies live workspace profiles and the native BrowserCommand registry to the settings shell. The settings window uses a native NSToolbar in preference style, with selectable CocoaExtensions ToolbarItems driven by SettingsFeature. The window is 760 points wide and not resizable, so zoom stays disabled. Its height follows the selected pane up to 720 points, and Profiles and Spaces take 640 points for their scrolling columns. Command definitions stay out of SettingsFeature.

OrganizationManagement applies Settings commands to the canonical workspace and reconciles all normal windows, leaving private windows alone. Profile preparation and before-unload approval precede destructive edits; stale approvals cannot overwrite newer workspace changes. Removal keeps at least one profile and space. Profile removal retains on-disk website data and is blocked while a Little Arx window uses the profile.

Link actions resolve the hosting window's live current URL and title, including navigated pins, while explicit ordered items support context targets. URL-bar, tab and Favorite menus offer exact, clean, proxy, original-Markdown and proxy-Markdown copy, proxy sharing, and saved-link copy for pins. Sidebar context actions preserve ordered selected-tab identities, skip folders, and validate every target against the current space/profile or profile Favorites before copying anything. Missing, moved or foreign targets cancel the whole action; live metadata follows a normal tab's actual pane/borrowed-Peek owner, while private snapshots stay local. Saved-link copy remains tied to the clicked saved tab. `LinkSharingClient` is an injectable AppKit clipboard/share adapter; copy failures and share cancellation are observable outcomes. The result shows as a toast at the window's top-right corner (`LinkFeedbackToast`, AppUI's `ArxToast`, DEV-769): "Copied Current URL", "Copied Clean Link" and so on, a share button for the copied URLs, Copy Original when cleaning or a proxy rule changed the link, and a ⋯ menu of other matching proxy rules. In split view the feedback records the source pane (`LinkActionFeedback.paneID`: a command's or link context menu's pane, the pane of the one sidebar tab copied, otherwise the focused pane; never over Peek), and the toast draws on that pane's page through `browserPageNotice` instead, falling back to the window's corner once the split or pane is gone (DEV-780). At the window's corner `LinkFeedbackToast` also sets `arxToastStackOffset` on the content under it, so toasts there, such as the sidebar's notice, stack below the link toast: below the corner's own toast by its measured height, or below a pane's toast whose frame (reported in the window's coordinate space through a preference) reaches into the corner a notice can cover. A pane's toast resets the offset around its own placement (DEV-777); `ToastStackingTests` cover the arithmetic. It shows from `ui.linkFeedbackShown`, expires 2.5 s later through `event.linkFeedbackExpired`, and `ui.linkFeedbackHovered` holds it while the pointer is over it. A cancelled share shows nothing. Copy/share never writes organization or navigates. Native in-page link context menus require renderer link-target support.

CommandRouting dispatches commands from both BrowserCommands and the command bar. Every command carries an explicit originating host and rechecks the shared BrowserCore availability rules before execution. Native menus observe persisted shortcut bindings and update immediately; editing commands retain responder-chain handlers. AppUI supplies localized registry titles.
IncomingURLRouting owns a readiness-gated FIFO queue for external HTTP(S) events and confirmed Route URL actions. The native URL handler registers before Chromium startup and is reclaimed when ready. Each request captures its source space, creates a fresh profile-isolated session, and revalidates the current routing decision before committing. Failed/missing destinations keep the original URL in a visible inbox with retry, override, copy and cancel actions; cancellation closes partial sessions. Main destinations commit workspace state before progressing the queue; Little Arx destinations remain temporary. Page navigation, redirects, Peek and authentication callback flows are not intercepted. Native cold-launch Apple Event delivery still needs a packaged-app manual check.
RoutingProfilePicking (DEV-858) asks about a link whose route, or `Otherwise`, is Ask for a Destination: instead of the inbox, `RoutingInbox.picker` lists the profiles with a space, most recent first (the profile of the request's source space, then of `recentSpaceIDs`, then sidebar order), each with the space a `.profile` route resolves to. The request is `.choosingProfile` and later requests wait behind it, so several links ask one at a time in order. Nothing is prepared or opened before Return, which sets a `.profile(id)` Little Arx override and requeues it; Esc, or the panel resigning key (`lostFocus` names its request, so a closing panel can't cancel the next one), drops the link. BrowserWindow shows `RoutingProfilePickerPanel`, a borderless non-activating panel at the pointer that gives its search field the keyboard when it becomes key, whether or not SwiftUI has laid it out yet, and cancels on Esc the view hasn't handled yet. The search field is the only thing in it that takes the keyboard: the rows never take focus or draw a focus ring, Tab stays in the field, and the field takes the keyboard back when another window's SwiftUI field takes the field editor SwiftUI shares between windows (DEV-953). BrowserWindow sends `hostAvailable` at launch; headless runs never do, so Ask there keeps using the inbox. Its content is AppUI's `RunwayView`, the Runway, regular or compact as `LinkClickPreferences.runwayAppearance` (Settings › Links › Air Traffic Control › Runway appearance) chooses; the panel takes the view's fitting size with every option listed. Hovering a row only lights it; the selection moves with the arrow keys, with no focus ring, and a click opens that row. ⌘1–⌘9 send `openNumber`, which opens the result with that number: the panel takes them in `performKeyEquivalent`, before the main menu's ⌘1–9. RoutingProfilePickerSmoke covers Esc, focus loss and Return in `make app-smoke`.

ExplicitURLRouting presents Route URL in a sheet attached to its originating normal or Little Arx window, including a captured Peek target. The exact URL, tab, pane, profile and source space stay frozen while the user reviews the matching rule and chooses a profile/space and main/Little destination. Cancel leaves the queue untouched; closing the source removes its preview, and stale dismissals cannot clear a newer preview. Confirmation revalidates the source and displayed destination. Confirmed requests pin the resolved profile/space/mode through startup waits, retries and final asynchronous publication; changed targets require another explicit choice. Once confirmed, the request owns its copied URL independently of the source page. Automatic external routing retains its existing rule behavior. Native sheet presentation and keyboard/VoiceOver interaction need a packaged-app manual check.

App links (DEV-857). When a page opens a link for another app, the engine offers it (ABI50) and BrowserWindow asks `appLinkPresentation(for:hasSystemApp:)`: Arx takes it when its tab is shown in a window and an Air Traffic Control handler matches it or, with none, macOS has an app for its scheme (DEV-1259). Such a link gets the same prompt, Open ‹app› with the app macOS assigns, from a handler that isn't saved (`AppLinkDecision.isSaved`); Always allow saves it as the person's own app link with the site (`saveHandler`; if a handler that takes the link was saved or switched on while the prompt was open, nothing is saved, so the site never gets that handler's own handling unasked). Only a link no app on this Mac opens stays with Chrome, which then neither asks nor opens anything, so Chrome's "Open app?" dialog never shows for an Arx tab. `AppLinkRouting` puts an `AppLinkPrompt` on that window (`AppLinkPromptPresentation`, a sheet, as Route URL's). The prompt resolves the handling for the page's profile: a script is announced as **Land in ‹handler› ‹profile›**, Open app as **Open ‹app›**, the name macOS gives the app. Private windows never run scripts. A link that fails validation (not a URL, another scheme, control characters, over 8 KB) is offered Open app only. The prompt is portrait, about 4:5 (DEV-872, AppUI's `AppLinkPromptCard`): the app's icon (`AppLinkClient.appPath`, or the chosen app's) and the title, the site and the link, the notes, the script on request, any failure and Always allow, then full-width Arx modal buttons at the bottom, Show Script, Cancel and the main button last. Return presses the main button, the default for the keyboard and VoiceOver, and Esc is Cancel (DEV-872). The main button takes no click or Return for 600 ms after the prompt appears or Arx comes back to the front, as Chrome's dialog protects its input. The main button is split, with Copy Link in its dropdown, which copies through `AppLinkClient` and shows Copied for a moment. Show Script reveals the script. Always allow ‹site› to open this (ordinary windows, HTTPS or loopback sites only, as Chrome's remembered consent) saves the origin on the handler, and a later link from that origin runs at once, with the prompt shown only if the script fails. A failed or timed-out script shows its error and the end of its log, with Open app as the fallback. Before Land, Open or an always-allowed run, `AppLinkRouting` checks that the tab still shows the document that asked (its document revision) and that the frame that asked is still there (`BrowserEngineClient.externalLinkIsCurrent`, Chrome's own guard kept natively); if not, the prompt says the page moved on and nothing runs, opens or is remembered. While a handler runs, Arx takes other pages' links and drops them (DEV-1259). A second link from the running prompt's own page still goes to Chrome: the engine keeps one source token per page (`external_link_is_current`), and taking it would replace the token the prompt's Open app fallback checks. A handling that opens a chosen app (DEV-862) names it in the prompt and opens the link with it; a script's fallback opens the handler's app. If the chosen app is gone (not at its path, and its bookmark finds nothing with the same bundle ID), the prompt says so and offers Open with System Default; nothing falls back on its own. When the app was found somewhere else after a move, the prompt reports `applicationMoved` and `AppLinkRouting` saves the new path and bookmark in every handling that used it. `AppLinkSmoke` is the app smoke's `app-link` phase; `runChosenApp` adds the chosen-app part, and `runUnconfigured` a scheme no handler takes (DEV-1259).

Page permission prompts (DEV-963), behind the `ARX_PAGE_PROMPTS` feature flag (`PagePrompts`, on by default since DEV-1143; environment first, then defaults). With it on, BrowserWindow asks the engine once it runs (ABI56, `setPagePromptsHosted`) to hand ordinary site permission prompts to the app instead of its `NSAlert`; a headless run doesn't. `PagePermissionPromptRouting` takes each report (`pagePermissionPromptChanged`, a tab and the prompt's token, 0 when it's withdrawn because it was answered, replaced, or the page navigated or closed), reads the prompt (`pagePermissionPrompt`) and keeps it on the window showing that tab (`permissionPromptWindow`: the main, additional or Little Arx window, or the window a Peek of it opened over; none for a page floating in Page PiP, whose window shows only a placeholder), never another one; a prompt no window shows, or one in an unattended run, is dismissed, which never blocks. `PagePermissionRequest(prompt:)` turns it into what the prompt shows: the site without `https://`, "Embedded in" for a frame of another site, the permissions Arx names (`geolocation` is Location), Chromium's wording for the rest, Allow Once when every request supports it, and Approximate or Precise when a location prompt offers the choice, or the one accuracy it's fixed to (approximate only, or an upgrade to precise), which the prompt states. `PagePermissionPrompt` answers once: Allow, Allow Once, Block, or Cancel, which dismisses and never blocks, with the picked accuracy; the routing removes it and answers the engine for that token (`answerPagePermissionPrompt`), which rechecks the source window and its 500 ms input delay. `PagePermissionPromptPresentation` draws AppUI's `PagePermissionPromptCard` as a sheet on the main, additional and Little Arx windows, with Esc as Cancel; a quiet request first shows a "Permission request" button at the window's lower trailing corner that opens it. It sits outside the page full-screen host, so that button stays above a full-screen page. With the flag off the engine keeps its own sheet and reports nothing, so nothing here changes. The ABI31 dialog MCP reads keeps working either way (`PagePermissionRequest(dialog:)`).

Link status (DEV-1111), behind the `ARX_LINK_STATUS` feature flag (`LinkStatusFeatureFlag`, read through `FeatureFlag`, on by default since DEV-1143; environment first, then defaults), which BrowserWindow reads once at launch into `settings.linkStatusAvailable`, and Settings › Links › Show where links go (`LinkClickPreferences.showsLinkStatus`, on by default, shown only with the flag). BrowserWindow makes a `LinkStatusPresenter` for windowed runs and feeds it `ChromiumBrowserEngine.onLinkHover`. After `LinkStatusToastMetrics.showDelay` it shows AppUI's `LinkStatusToast` in a child panel at the hovered page's bottom-left corner (a window's pane, a Split View pane, Peek or Little Arx, private windows too), at most two thirds of the page wide, moving to the bottom-right while the pointer is over its spot. While a link is hovered, a local monitor follows `flagsChanged` and pointer moves, so the words change as keys are pressed and released; the pointer leaving the link (after `hideDelay`) ends it, and the pointer leaving the page or Arx going to the back only hides it, so it shows again when the pointer returns or Arx comes forward, though the engine reports nothing new. The panel ignores the mouse and never becomes key. `AppFeature.State.linkClickOutcome(for:modifiers:opensInWebKit:)` (`LinkStatus.swift`) decides what a click will do by the rules the click goes through: `LinkClickDisposition` is Chromium's choice from the keys (⌘ a tab, in front with ⇧; ⇧ a window; ⌥ a download; ⌃ the context menu), then `linkOpenAction`'s Peek and Little Arx checks, Settings › Links (Shift-click Peek, the Little Arx binding, links to other sites from Favorites and pinned tabs through `crossSiteLinkRoute(from:)`, which `crossSiteLinkAction` shares; links from Favorites and from pinned tabs each go to Peek, Little Arx, a new tab or stay in the tab, DEV-1239), `linkTabDisposition` (DEV-952), Little Arx's new Little Arx (DEV-855), Peek's own rules, WebKit pages and Air Traffic Control's app links (the app the resolved handling opens, or the person's script); private windows keep Chromium's choice. A plain click follows the link's `target` (DEV-1118): a `_blank` link is described as the page's own new tab (in front from a pane, a new Little Arx from Little Arx, a window from Peek), and Peek or WebKit are promised only for a known navigation of the page itself, so a frame's link or one with an unknown target shows only its address. BrowserWindow turns the engine's hovered-link reports on (`ChromiumBrowserEngine.setLinkHoverReports`) only while the flag is on and Show where links go is, since each report runs a script in the page's frames. `LinkStatus` puts it in words: the address alone for an ordinary click (`https://` left out), or a verb and an action around it.

GlobalShortcuts owns the opted-in Little Arx registration lifecycle through GlobalShortcutClient. Carbon exclusive registration uses the current keyboard layout, reports failures, updates after layout/binding changes, and unregisters while recording shortcuts. Generation checks reject stale callbacks after disabling or rebinding. Each registration cancels earlier ones synchronously and reports in on the main actor immediately before calling the client, because the native registration is a single slot that a late stale start would replace. The default remains off; no accessibility or event-tap permission is requested. Global invocation reuses command availability, including private-window restrictions. Device checks for full-screen/display behavior and non-US layouts remain separate acceptance.
BrowserAutomation owns local assistant approvals, grant editing, scoped inventory and explicit commands. Native BrowserWindow bridges an authenticated BrowserAutomationHost into typed actions; private and temporary organization is excluded. Requests bind grant and target revisions, recheck after asynchronous work, serialize mutations, and cancel on revoke/disconnect/stop. BrowserEngineClient guarded calls perform final authorization immediately before native navigation. Organization edits reuse Sidebar Undo and normal-window reconciliation. Endpoint start/stop transitions cancel earlier transitions synchronously and report in on the main actor before touching the control client, so only the newest toggle reaches it. Settings → Advanced exposes the default-off endpoint, one-time client configuration, capability classes with plain explanations, whole-profile or per-space/tab scopes, a standing approval policy, the focused-tab opt-in, 15-minute temporary approval grants (a headless run's own client alone may hold its run-long `manage` grant, and only while the session is unattended; an attended session revokes such a grant at startup, and Settings shows one as the headless run's access rather than a date), revoke/stop and bounded metadata activity. Editing a grant rotates its revision and drops work bound to the old one without ending sessions; revoking a client disconnects it. AutomationData answers history, archive and download reads from app state (history snapshots, the workspace archive, the downloads queue), resolves links with the user's Proxy Link rules and search shortcuts, and runs archive restore and download start/cancel/reveal. The queue streams into state only while a Downloads surface observes it, so every request that needs the downloads class first copies the ledger's `snapshot()` into state once; progress never streams through actions. `startDownload` (DEV-670) targets a granted profile item, asks every time unless the client's standing policy skips mutations (`AutomationOperation.ignoresTemporaryGrant`; temporary grants and batch approvals don't cover it), calls `BrowserDownloadsClient.start`, then hands the ledger snapshot and the result to state together (`downloadStarted`), so a list and the response gate see the new download. The gate releases a start only when its `targetID` is a granted download of the requested profile. Download actions need only the downloads class, not organize. AutomationManagement runs profile, space, Favorites, saved-entry, folder, Split View and window commands through the Settings transaction (`organizationChangeApproved`), the sidebar's organization edits with Undo, the main window's own actions, profile retirement and `MainFeature.transferConfirmedTabs` (the sidebar transfer without its confirmation, which the automation approval replaces), and settles each by observing its result. A committed action that removes its target (`AutomationCommand.Action.removesTarget`: destructive actions and `ungroupFolder`) answers without a `targetID`, since the IPC host's response check only lets through targets the client can still see. A batch plan is checked against the grant, approved once in AutomationApprovalView with every step listed, and recorded per connection (`batchApprovals`); its steps then pass approval only in order and with their exact bindings. AutomationPDF runs PDF export and PDF text (extracted with PDFKit and chunked) through the capture client, and native find through the engine's find command, waiting up to 2 seconds for the page's result. AutomationCapture resolves element captures from the session's released snapshot with bounds, and lets offscreen captures read pages that aren't visible. AutomationLoad opens a detached background page for a saved tab through `openAuthorized` without selecting, focusing or attaching it, and reports `alreadyLoaded` for a tab that has a page. AutomationCapture lets the native frame reach 16 MiB, then scales and re-encodes it as JPEG when the request asks, so the delivered image fits its 4 MiB cap. `automationChanges(for:snapshots:)` answers the helper's resource polling. `automationFocusedTab(for:snapshots:)` resolves the focused-tab alias to the focused pane's tab of the focused ordinary window (`MainFeature.State.focusedPageTab`, the pane last clicked or focused with the keyboard in a split, DEV-835) when the grant covers it. Cross-profile transfer remains unavailable and is refused as `crossProfileTransferUnsupported`. AutomationSettings (DEV-666) answers `browser_settings`: sections are built from Settings state per grant with a revision over their contents, and every change is checked (grant, revision, schema, conflicts, routing destinations inside the grant) before anyone is asked. An approved change is planned as the exact `SettingsFeature` UI actions the Settings window would send (for example `assignKeyboardShortcut` then `replaceKeyboardShortcut`, or the routing editor's `changed` and `save` followed by the user's own draft restored) and settles once Settings holds the expected preferences (`Settlement.preferences`), so Settings updates at once and saves as usual. Extension changes go through the same `BrowserExtensionsClient` Settings uses, against a fresh inventory whose revision must match; an open Settings list for that profile refreshes afterwards. `setSpaceAppearance` and `setProfileAppearance` (DEV-706) apply `AutomationAppearanceChange` through the `OrganizationChange` appearance transactions the Settings window uses.

Automation waits while folder deletion, archive, or profile transfer is active. During asynchronous workspace publication, differing normal-window organization snapshots return `busy`; window-local selection differences are ignored. Archive restoration, tab transfers, and Settings profile reassignment retain automation origin metadata, but fresh tab identities and changed profile ownership do not inherit old explicit grants.

Back/forward commands share editable bindings, native menu and command-bar availability. Toolbar history menus remain a fallback while continuous trackpad arbitration is unverified. The disposable packaged-app smoke verifies native direct-entry navigation preserves forward history and rejects stale revisions.

Split commands capture both window and pane identity through shared native and command-bar dispatch. Availability is computed from the originating pane, and removed-pane actions are ignored. Automation selection focuses an existing pane in its current host. Address entry uses current-URL mode (Cmd-L); command entry remains separate (Cmd-K).

WindowPresentationPersistence restores normal windows and their active space layouts, excludes private windows, and saves split divider changes at drag completion. DEV-881 adds optional native frame, display identity and full-screen state to each saved record. BrowserWindow clamps restored frames onto available displays, cascades new windows and restores full-screen windows sequentially while retaining their normal frames. Geometry updates are accepted only after initial placement and never persist private windows. A window places itself, and saves its record, before its view first shows the selected tab; a window that never split saves that selection for its one pane, so the next launch doesn't restore an empty pane and deselect the tab. SplitPresentation checks other windows’ pane ownership before restoring or opening a split.

PeekPresentation owns one preview per normal or expanded Little Arx host with explicit source window, pane, tab, space and profile IDs. Little sources also retain their viewer generation; their single-pane identity is the window ID. Temporary HTTP(S) sessions stay outside the workspace until promotion; existing tabs retain membership and return without closing. Replace, close and host-close share before-unload cancellation. Promotion keeps the same session, validates its origin after engine readiness and surface release, and commits only afterward. Both drivers wait until the login page has finished loading and the workspace has recorded it before reading a revision to bind a sign-in to; `make sign-in-smoke` and `make sign-in-interface-smoke` refuse to start while the login session is locked. Where the store driver sends a stale approve or confirm for an ended handoff, the interface driver requires that the control is gone. It must report `ARX_SIGN_IN_INTERFACE_CONTROLS_PRESSED` before success.

MCP host operations retain the existing PeekPresentation/LittleArxWindows session
transfer handlers. An explicit permitted source tab selects Peek's unique owning
pane; no focused-window fallback or visible-session stealing occurs. Foreground
consent is required. A bounded per-client/session handle exposes value-free
presentation metadata through inventory while temporary content remains outside
generic page inspection. Promotion captures exact host/native snapshots before
approval and fences asynchronous readiness and surface-release commit callbacks.
Canceled/revoked requests cannot authorize a later handoff; expiration never closes
user content. Operation receipts distinguish model publication from native/page
readiness and are revalidated before IPC delivery. Unattended runs refuse host
operations as `unsupported`, and an outdated presentation revision is `staleTarget`.

AutomationRouting resolves an `openTab` that opts in with `route` through
`URLRouter.decide`, using the explicit target space as the current space. It
replaces the pending request with the resolved `openTab` or `openLittleArx`

resolved command. A route into an ungranted space is `denied`, a Little Arx
destination without focus or in an unattended run is `unsupported`, and an
unresolved decision is `routeUnresolved`. Cross-profile tab, folder and Little
Arx moves return `crossProfileTransferUnsupported`.

## Onboarding

AppFeature owns onboarding presentation. `onboarding` holds OnboardingFeature state while its native window (identifier `onboarding`) is open; BrowserWindow creates and tears the window down from that state, as it does for Settings. The window has a transparent title bar, fades in while its content springs in, and is sized by `OnboardingView.size`. On launch BrowserWindow sends `presentOnboardingIfNeeded` when `OnboardingLaunchPolicy` allows it, which shows the flow only while `OnboardingPreferences.introductionDismissed` is false. Headless runs, runs with `ARX_ENGINE_PROFILE` (every smoke and fixture profile), `ARX_SKIP_ONBOARDING`, and XCTest-hosted runs never send it, so automated runs don't gain an extra key window.

The flow opens at the first unfinished step in `completedSteps`, so quitting partway resumes there on the next launch. `BrowserCommand.onboarding` ("Welcome to Arx…") reopens it from the Arx menu or the command bar at any time, including after it ended. `ui(.openOnboardingStep(_:))` opens one step on its own; Settings › General lists the steps in `OnboardingFlow.steps` order next to Open Setup Guide. Settings' Import opens the migration step on its own and starts the assistant. Reopening an open window only refocuses it. The close button, Escape and Close Tab (`CommandTarget.onboarding`) close the window. The first close, or the end of the flow, writes `introductionDismissed = true` through the existing workspace save path (`delegate(.save)` with `unsavedOrganization` set, so save failures use the usual recovery banner). Later closes don't save again. While a profile is being retired the window still closes but the preference isn't written, so onboarding returns on the next launch.

A first launch holds the main window back while onboarding is open (`mainWindowWaitsForOnboarding`, DEV-838). Every path that opens the main window goes through `State.openMainWindow()` (MainWindowHold.swift): Open Window, the commands that need a window, Media, routed links and the routing inbox, Little Arx promotion, focusing an unmounted tab, agent approvals and focus, and the failed-quit reopen. While the window is held it bumps `onboardingFocusRequest`, which raises the onboarding window and activates Arx, instead of opening anything. New Window and New Private Window are refused the same way, and the command context sets `mainWindowIsHeld` so those menu items are disabled. Links routed into Arx stay queued (`processRouteQueue` waits) and open when `revealMainWindowAfterOnboarding()` drains the queue. Only Reopen in BrowserWindow, which raises onboarding natively, bypasses the store. When onboarding settles a provisional Default profile (DEV-841) the window stays held until the checks answer, so nothing done in it can race them. A separate timeout (`provisionalProfileTimeout`, five seconds) settles Default as holding data even while a check that ignores cancellation is still running, and the late answer changes nothing. A save that fails while quitting reveals the held window, since its error and recovery controls live there; BrowserWindow keeps the closed onboarding window still until then and grows it into the main window when that opens.

A first launch that will show onboarding starts in a provisional workspace (DEV-841): BrowserWindow builds `ProvisionalProfile.organization`, a Default profile and space with no tabs, and records it in `OnboardingPreferences.provisionalProfile` with the first save, so a relaunch partway through still knows. Automated and headless runs keep a Default workspace with one starter tab and nothing provisional. When onboarding first ends (hand-off, finish or close), `settleProvisionalProfile()` clears the mark. If an import made profiles of its own and Default is still pristine, it first checks Default's history, saved passwords and removable extensions (a check that can't answer counts as data); ProvisionalProfileSettlement then selects an imported space if Default was shown and removes Default's space and profile through `settings.delegate.changeOrganization`, the same transaction Settings uses. Otherwise Default stays as an ordinary profile. Chats, Air Traffic Control rules, download and site settings and other stores live outside the workspace where the pristine check can't see them, so Default stays provisional only while the user does nothing but onboarding: any `Action.isActivityOutsideOnboarding` (opening a window, Little Arx or Settings, a command other than onboarding's, a Settings edit, a chat, an agent approval, a link routed into Arx) ends its provisional state at once. The pristine and browsing-data checks remain a second guard. If Arx quits after onboarding ended but before the checks answered, `presentOnboardingIfNeeded` finds the provisional mark with `introductionDismissed` set on the next launch and settles it then. The removed profile stays `legacyProfileID`, the owner of Chromium's original Default directory.

OnboardingICloudAdoption is the host side of onboarding's "Sync with iCloud" (DEV-1215). With `ARX_ONBOARDING_ICLOUD` on (the default) and iCloud sync possible here (`ARX_SQLITE_WORKSPACE` and `ARX_ICLOUD_SYNC`), BrowserWindow makes the provisional Default "This Mac only" and records it in `OnboardingPreferences.heldForICloud` with the first save, so the step turning sync on doesn't upload it. `presentOnboardingIfNeeded` offers the step (`offersOnboardingICloud`) only while Default is held and `WorkspaceSyncClient.isAvailable()`; otherwise it lets Default sync at once. When the step reports `adopted`, the workspace is read again (`event.workspaceSyncChanged`, so the rows the step fetched are in), and once no read waits (WorkspaceSyncReload runs it in the same action, or after the save or page answer it waits for), Default's space and profile are removed through `settings.delegate.changeOrganization` as the import settlement does, the main window selects the space any Mac used last (else iCloud's first), the provisional mark clears, and onboarding's import page is pointed at that space without Clear Arx data first: `migrationExistingData` offers no clear while the workspace came from iCloud, since retiring it would reach every Mac. Default stays, and syncs, if nothing came or it isn't pristine any more. `continuedWithoutWaiting` keeps Default held (`waitsForICloudInBackground`) while a background wait asks iCloud with `joinFromOnboarding(false)`, which never turns sync on, every 30 seconds while it can't be reached: a starter uploaded once Profiles and spaces has started would sit beside what iCloud has, since DEV-1216's merge on joining runs only before that category first starts. A workspace in iCloud is then adopted as above while onboarding is open, and the flow's `iCloudResolution` becomes `adopted` so the import page that follows is limited; otherwise, or when iCloud is empty or sync was turned off (`turnedOff`), Default syncs, and profiles of the same name are DEV-1216's to merge. A relaunch doesn't wait again but lets Default sync: what an import put in Default meanwhile can't be told, and Default synced later meets iCloud's the same way. No adoption, the step's own or a late one, removes Default once onboarding has shown its import page (`OnboardingFeature.State.importWasShown`, kept in `ICloudAdoption` when onboarding closes first): an import, of passwords and sign-ins too, may have filled Default in ways the workspace doesn't show. Every other outcome (`empty`, `notNow`, `unavailable`), onboarding ending before the step decides, and a relaunch after onboarding ended let Default sync again (`releaseProfileHeldForICloud`, `setSyncsWithICloud(_, true)`), so it's the starter iCloud gets; it stays provisional for the import settlement. A pending adoption or background wait isn't undone by onboarding closing. `OnboardingPreferences.adoptedICloudWorkspace` keeps an adoption across a relaunch until onboarding ends, so the import page stays limited and no clear is offered. The flag is read at launch into `onboardingICloudEnabled`: off, a held Default syncs at once and the step isn't offered. `ProvisionalProfile.isPristine` ignores whether Default syncs.

When BrowserWindow installs onboarding (the same `OnboardingLaunchPolicy` check), it also observes `NSApplication.didBecomeActiveNotification` and sends `event(.applicationBecameActive)`. `DefaultBrowserRefresh` forwards it to Settings while its window is open and to the onboarding window while it shows the default-browser page, so both read the default again after the person changes it in System Settings. It also forwards the event to the connect-your-agent page, which reads Claude Code's and Codex's sign-ins again, and to the import page, which checks Full Disk Access for Safari again (DEV-840). ProblemReportPresentation (DEV-887) opens FeedbackFeature's `ProblemReportFeature` in `problemReport` from Help › Report a Problem… (`ui(.reportProblem)`) and Settings › Privacy (`settings.delegate(.reportProblem)`), keeping a report already open, shows it as a sheet on the main window (`ProblemReportSheetPresentation`), clears it on its `delegate(.close)`, and on `delegate(.openIssue(url))` keeps the sheet (it now says where the report file is), brings Arx back in front of Finder (`appActivationRequest`), opens the prefilled GitHub issue page in a new tab of the main window, and reloads Settings › Privacy's status, which counts a report file just saved. BrowserWindow reports Arx windows to extensions after each render (`ExtensionTabPlacements`): the main window, additional ordinary windows and Little Arx panels by AppKit window number. A window holds its visible space's tabs in sidebar order (favorites, saved tabs through folders, then open tabs), so a tab's `index` is its sidebar position and does not move when other tabs load. With independent windows (DEV-822) a window lists only the open tabs it keeps (`Window.openTabFilter`, from its sidebar's `openTabFilter`), so another window's background tab is never placed in the main window, and an open tab kept by a window showing another space is in no window. A tab shown in a pane belongs to that window, any other to the first window whose visible space lists it; the active pane's tab is active and shown tabs are highlighted. Private windows report nothing. BrowserWindow gives the engine only the placements that changed since its last report (`ExtensionTabPlacements.changes`), so a tab switch sends two. `ChromiumBrowserEngine` keeps the whole set, and resends it to Chromium (whose call replaces every placement) only when what Chromium last received differs, including when sessions gain or lose pages.

A headless run's own client is scoped to the run's whole profiles (`HeadlessRun.scopes(for:)`, DEV-865), so spaces that appear during the run, with their folders and tabs, are in its grant without changing it; that includes the profiles' Favorites. The client can't create spaces itself (`createSpace` needs browser admin), so new spaces come from other clients of a persistent profile or other changes.

MigrationWorkspace serves MigrationAssistant's reads and commits. BrowserDataExporting asks where to save through `BrowserDataExportClient`. LinkClickGesture sends modified clicks on page links to Peek, Little Arx or a new tab. Each choice maps to a `LinkOpenRoute` that `linkOpenAction` opens, as the link menu's items do. Option-Command-click looks the same as Command-click, so it reads the keys held at that moment. A Force Click on a link opens it in Peek, Little Arx or a new tab, or does nothing special (Settings call that Look Up), as Settings say; anything it can't route keeps Chromium's Look Up and click. `AutomationDeveloper.swift` runs the developer tier (DEV-668): `browser_evaluate` (`.script`, script class) and `browser_logs` (`.logs`, devtools class). `ChatPlacements.swift` (DEV-761) decides where chats show.
