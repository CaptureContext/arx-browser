# SettingsFeature

Production settings state with composed appearance and search sections. App-wide preferences are `@Shared` per-domain keys backed by the workspace document (`chromeAppearance`, `searchShortcuts`, `routingPreferences`, `proxyLinkRules`, `keyboardShortcuts`, `linkClicks`, `general`, `automaticPictureInPicture`); every window reads the same keys, and AppFeature saves edits with the workspace's versioned atomic recovery contract. Validated domains are written only from these reducers, after validation. AppUI only receives values. The preview uses the same reducer and controls with in-memory fixture storage.

Grain is static. Appearance & Sound (DEV-734) starts with the theme (`ui.appTheme`, `general.appTheme`: System, Light or Dark, drawn as small Arx windows by `AppThemePicker`); AppFeature's BrowserWindow sets `NSApp.appearance` from it, and a profile or space theme override still wins inside its windows. It then edits the app-wide window background (`ui.chromeAppearance`, tint and grain, committed when a slider is released); each profile's page edits its override with `ChromeAppearanceEditor`, and Use Global Appearance clears it. Search definitions support create/edit/disable/delete, unique case-insensitive keywords, and validated HTTP(S) query-value/path-segment templates. Arx starts with none of its own and has no reset (DEV-1321): the bundled bangs cover GitHub, YouTube and Wikipedia, which the removed starters only repeated, and the empty list says so. No remote suggestions are used. Below the user's shortcuts, Built-in bangs lists Helium's bundled !bang list (`State.bangs`, see BrowserCore's `BangCatalog`): searchable by name or keyword (`ui.bangQueryChanged`, `bundledBangResults`, at most 50 rows) and read-only. A row notes when one of its keywords is answered by the user's own shortcut. The footer carries the attribution (Kagi Search and imput, MIT).

The settings shell uses a sidebar of categories: Arx, General, Profiles, Sync (iCloud Sync, listed while `ARX_ICLOUD_SYNC` is on; DEV-1336: it was a section of the Arx pane, and `arx://settings/arx/icloudsync` still leads there), Assistant, Links, Shortcuts, Appearance & Sound, Developer and Advanced (`SettingsCategory.available`). Category, panel, profile selection and shortcut-query state belong to the reducer and never trigger preference saves. Appearance and bang editors retain the existing persistence behavior. Profile and space editors send validated organization commands to AppFeature; shortcuts are supplied by AppFeature's command registry, avoiding a second list of key bindings.

Unfinished options are compiled only under `#if DEBUG`, labeled “Not yet available” rather than using editable controls that imply working behavior. Release builds hide them. The Previews panel (General › Preview Settings…, DEV-802) is in every build: switches for folder previews, unread mail in Gmail and recent pages in Linear, Notion and Figma (`ui.hoverPreviewSources`, stored in `general.hoverPreviewSources`), disabled while Previews on hover is off, with calendars and Outlook mail as debug-only pending rows. Its "Pages that aren't loaded" section has two switches (the site's picture and description, Full previews; DEV-730) or, under `ARX_SITE_PREVIEW_IMAGES` (DEV-1142, on by default), one choice of what a card shows without a saved picture: the site's preview image, loading the page, or no picture, written through `HoverPreviewSources.unloadedPages`; its footer then says the request carries the profile's cookies for that site only. Under it, Shift + hover loads the page instantly (DEV-1029) is a switch of its own, apart from the choice, shown while `ARX_SHIFT_HOVER_PREVIEW` is on. The Assistant category is shown in every build: it holds the built-in assistant's per-profile chat settings, which AppFeature supplies as a view (`assistant:`) because it owns the chats. Which options to support is tracked in Linear DEV-568. Resource text comes from AppUI's generated package-resources catalog. No account details or other apps' assets are copied.

Category navigation is hosted by AppFeature in a native NSToolbar using NSWindow.ToolbarStyle.preference. SettingsView renders only the selected pane and sheets; it does not imitate the toolbar with SwiftUI buttons.

Settings panes share compact system typography and centered content widths. They draw AppUI's own controls (DEV-743): `settingsControls()` makes every button without a style of its own an Arx button, at the root and on each sheet. Primary actions use `.arx(.primary)`. Shortcuts' Alias and Record Shortcut use the small size, and Record Shortcut turns primary while it records. Inline fields (the Alias field, the URL field in Air Traffic Control routes) use `.textFieldStyle(.arx)`, and whole-row fields stay `SettingsTextField`. A route's Domain / Domain and Subdomains choice and its window choice are `ArxDropdown`s. The space menu is a system menu drawn as an Arx button, and every other picker in Settings stays a system pop-up. Every pane is a grouped list built from AppUI's `SettingsSection`: an optional header and caption, its rows on one filled rounded card with dividers between them, and a footnote. Rows are `SettingsRow` (title, optional detail, control on the right) or `SettingsToggle` (a switch on the right). Every sheet shares `SettingsSheet` (DEV-744): AppUI's `ArxModalScaffold`, a bar on top and the content scrolling edge to edge under it, where it fades out softly, with no hard clip line (DEV-782, DEV-790, DEV-806), on the window's own background with no tint. The sheet scrolls its content itself. The bar (`SettingsNavigationBar`, DEV-762) is AppUI's `ArxHeaderBar`: a rounded-square raised Close tile (×, Escape), the title in bold and, under it, the trail that led there in small grey type, such as "General" for Preview Settings, then the sheet's own trailing controls. Preview Settings (`SettingsDetailView`) and AppFeature's Local assistants (MCP) sheet use it; a profile's Site Settings and Passwords sheets use `ArxModalScaffold` with the same bar, "Profiles › name" as the trail, their description at the top of the content, their search in the bar (`ArxHeaderSearch`) and, for Passwords, Add and Import as capsule buttons beside it; a notice pins under the content. Search Shortcuts is a list like Air Traffic Control's routes: each shortcut has a switch, Edit and Remove (and a context menu with both); Add Shortcut (`ui.addShortcut`) and Edit open one editor row (`isEditingShortcut`, `editingKeyword`), which Save or Cancel (`ui.cancelShortcutEdit`) closes. The bundled bangs follow; the sheet bar's search, a raised capsule that expands into a wide search capsule, filters them, and while it holds a query only the matching bangs show. The sidebar's search (DEV-747) finds settings inside panes, not only panes. Each pane declares its entries next to its view (`SettingsView.generalSearchIndex`, `SettingsShortcutsView.searchIndex`, …), and `SettingsCategory.searchIndex` gathers them after each pane's own entry. A `SettingsSearchEntry` has a title, localized keywords, its pane and trail (shown as the path, such as "Advanced › Local assistants (MCP)"), and a `SettingsDestination`: a pane, a row (`SettingsAnchor`), a page (`SettingsPage`), a sheet over its row, or Local assistants (MCP), which the reducer asks AppFeature to open (`delegate.openAutomation`), or `extensions`, which opens the selected (else the first) profile's page and presents its Extensions sheet (DEV-801; found by "add-ons", "Chrome Web Store" and "options" too). Rows mark themselves with `settingsAnchor(_:)`, which gives them a scroll id, highlights them while `highlightedAnchor` names them, and reports them through `SettingsAnchorsKey`; a test lays out each pane and checks that every entry's anchor is placed. Choosing a result (`ui.searchResultChosen`, by click, or ↑ ↓ and Return in the field) selects the pane, opens the page or sheet, scrolls to the row and highlights it for `highlightDuration`. Custom content such as the identity card sits on a `SettingsGroupCard` beside the sections; `SettingsCard` is the same card for panes that lay out their own rows. The sidebar's search is a safe-area bar over the categories, which scroll under it with the soft scroll edge. The window's title bar is transparent, so the view ignores its top safe area and lays out from the window's top edge: the sidebar's search starts just below the window controls (`SettingsMetrics.sidebarSearchTop`), and each pane has a navigation bar of its own, a 52-point safe-area bar that spans the title-bar area like a unified toolbar, with room above it (`SettingsMetrics.navigationBarTopInset`) so its controls start level with the sidebar's search, clear of the window's top edge (DEV-806). The bar has no background and no divider: it's pinned with AppUI's `arxScrollBar`, and rows fade out softly under it (DEV-790, DEV-806). It's laid out like every header bar, an `ArxHeaderBar` with no leading button: the pane's icon tile (30 points), its title in bold and its description under it, leading-aligned and always shown; the pane has no centered header of its own. A pane's own search, such as Shortcuts', sits on the bar's trailing edge as AppUI's `ArxHeaderSearch` (DEV-782, DEV-790): a raised capsule with a magnifier and ⌄ (⌘F) that expands into a wide raised search capsule, and stays open while it holds a query; the title truncates before it. A page inside a pane (`SettingsPage`, opened with `ui.pagePresented`), such as Assistant › AI Commands or Assistant › Assistant Features, uses the same pinned bar with `SettingsNavigationBar`: AppUI's rounded-square raised Back tile (‹, ⌘[) and, beside it, the page's title in bold over its pane's name (DEV-762). Every list that grows with use is a page of its own (DEV-1114): General › Search Shortcuts (the bar keeps the bangs' search), Links › Proxy Links, Links › Air Traffic Control (routes and tester), Links › App Links, Advanced › Sites kept loaded and Advanced › WebKit sites. In its pane, each is one `SettingsDrillDownRow`, the shared row Assistant's pages and a profile's sheets use too: an optional symbol, the title, a count on the right ("3 rules", "12 sites") and a chevron; a click, Return or → opens it. On a page, ← goes back like ⌘[ while the page itself has focus, not a field on it. Search results and the command bar's settings results name pages as `.page(_)`, and the old sheet ids (`panel/search/…`, `panel/routing/…`) still read back as their pages. Advanced › Feature Flags (DEV-1115; `SettingsFeatureFlagsPage.swift`, its view `SettingsFeatureFlagsView.swift` and `FeatureFlagsClient.swift`) is a page of the same kind: every flag in BrowserCore's `FeatureFlag` with its name, what it does, its `ARX_*` name, a warning where it's risky, why it's off by default for one in `FeatureFlag.offByDefault` (`offReason`, DEV-1143) and a switch. `ui.featureFlagsAppeared` reads them through `FeatureFlagsClient`, the first time also as the values Arx launched with; a switch (`ui.featureFlagChanged`) saves to user defaults, a flag the environment sets shows a lock and can't change, and while a changed flag that reads only at launch differs from its launch value the page offers Relaunch (`ui.relaunchForFeatureFlags`). A list's add button is a "+" on the window's top bar (Max, 18 Nov; `SettingsToolbarAdd.swift`): Profiles' pane bar, and the Proxy Links, Air Traffic Control, App Links, Sites kept loaded and WebKit sites pages' bars. It's AppUI's `ArxHeaderIconButton`, the raised squircle Shortcuts' search draws, whose title is its hint on hover and what VoiceOver reads: New Profile, New Rule, New Route, New Handler or Add Site (`SettingsAddTarget`). It sends what the button over the list sent and greys as it did; Air Traffic Control's unsaved New Route is the store's `routingDraft`, so the bar and the list share it, and it's dropped as the page closes. Each hint is also a search keyword of its page. With the `ARX_SETTINGS_TOOLBAR_ADD` feature flag off (the `settingsToolbarAdd` environment value, which snapshots set), the buttons sit over the lists as before. Each page is classified for agents (`SettingsPage.access`): Search Shortcuts and Air Traffic Control through their sections, the others the person's own. Profiles (DEV-746) is a pane like the others: one plain list of profiles (smiley, name, space count, chevron) under a Your Profiles header, New Profile on the bar, and a footnote that nothing crosses between profiles. Each row's context menu opens, renames or removes it. A row opens the profile's own page (`SettingsPage.profile`, titled with its name) with grouped sections: Search, Tabs, Window background, Downloads, Browsing History, Your Data and Settings (Site Settings, Passwords, Extensions, Clear browsing data as drill-down rows), and Linked spaces with Rename… and Remove Profile…. The native toolbar retains system typography.

Back from a page returns its pane to where it was scrolled (`SettingsScrollRestore`, `ARX_SETTINGS_SCROLL_RESTORE`, on by default; Max, 18 Nov), whichever way it goes back: the Back tile, ⌘[ or ←. The pane's `ScrollView` reports how far it has scrolled into a `SettingsPaneOffsetReading`, a reference, so scrolling doesn't redraw Settings. When a page opens over the pane, `SettingsPaneScroll.navigated(from:to:lastOffset:)` saves that offset as the pane's `ScrollPosition`, and the pane, made again on Back, starts there through `scrollPosition`. Choosing another pane in the sidebar forgets it, as macOS Settings does, so a pane chosen there starts at its top, and so does the pane of a page the sidebar's search opens from another pane. The window keeps one size, so the pane comes back at the same layout. Sheets, such as Preview Settings and a profile's Site Settings, cover the pane or page without replacing it and keep their scroll anyway.

Profiles support creation, renaming, and removal once their spaces have been reassigned or deleted. With iCloud sync and another Mac syncing Profiles and spaces (`ICloudRemoval.asksWhere`, DEV-1336), the removal sheet of a synced profile or space asks "Delete from This Mac Only" or "Remove from iCloud" (`OrganizationEditor.keepsElsewhere`, Delete from This Mac Only selected); "this Mac only" tells the store before the change (`keepRemovalOnThisMac`). A profile row and a space in a profile's Linked spaces that another Mac removed from iCloud show AppUI's `DeletionMarkBadge` and its hint, with Remove Here Too (an ordinary removal, which doesn't ask) and Keep (`ui.keepMarked`, `WorkspaceSyncClient.keep`). Removal explicitly retains Chromium website data on disk. Spaces support creation, renaming, icon choice, profile assignment, deletion with confirmation, and ordering by drag or arrow buttons. Drafts do not modify the workspace until saved. AppFeature handles native profile preparation, close cancellation, concurrent-edit protection, cross-window reconciliation, and the existing save-failure recovery flow.

The Links pane sets which click opens a link in Little Arx, and where each link gesture opens a link (DEV-1239): a Shift-click (Peek, Little Arx, a new tab or a new window), a Force Click (Peek, Little Arx, a new tab or Look Up) and a link to another site from a Favorite or from a pinned tab, each with its own choice (Peek, Little Arx, a new tab or the current tab). It also provides ordered Proxy Links rules, enable/disable, in-place edits, delete, and a local live tester for saved rules, the draft rule and Clean Copy. The first enabled match is the preference, so the order decides which of two rules for the same site wins: rows reorder by a drag handle on their right (`RuleDrag`), and there are no move arrows (DEV-1113). A focused row also moves one place with ⌥⌘↑ and ⌥⌘↓, and its menu and VoiceOver offer Move Up and Move Down where it can go (`RuleMove`, DEV-1163). Changing order persists with other browser preferences. Every rule, Arx's defaults too, can be deleted from its row menu, its form or the Delete key while its row has focus. Deleting a default adds its ID to `removedProxyLinkDefaults`, so no launch or Mac offers it again; Restore Default Links brings the defaults back as they ship and empties that list. The tester exposes matched rule, output and validation errors. Clean Copy's rules are inspectable: the parameters removed everywhere, the prefixes as `utm_*`, and a line per site (`ProxyLinksSettingsView.cleanRulesSummary`, DEV-918). Provider availability and real Discord/Telegram embeds require manual verification before presets are added.

Settings › Shortcuts is one searchable list of every command: its icon and name, its Conflict resolution picker (DEV-1332), an alias field and its hotkey. The picker (an `ArxDropdown`: Arx, Site, Both, Delayed; `ui.shortcutConflictResolutionChanged`) shows what the chosen mode does as its tooltip, and writes `shortcutConflictChoices`, a device-local key that stores only choices other than the command's default, so the recorded shortcuts never change with it; it's disabled at Arx for `BrowserCommand.keepsItsKeys` and while the command has no ⌘ shortcut, and Reset All Keyboard Shortcuts clears it too. The footer explains it under the heading "Conflict resolution". The page lists the commands in two sections (DEV-1332): Customized Shortcuts, every command whose shortcuts, alias or conflict resolution differs from its default (`State.isCustomized`), shown only while there are any, then Default Shortcuts; a row being recorded stays in its section until the recording ends. A command with no shortcut has no picker, and one whose shortcuts can't reach a page first keeps it disabled at Arx: shortcuts without ⌘ until the engine reports them (`followsAllShortcutKeys`, from `ArxEngineFollowsAllShortcutKeys`). An alias (`commandAliases`, `ui.commandAliasChanged`) is saved on Return or when the field loses focus, lowercased; one that has a space, starts with `!` or belongs to another command is refused with a note under the row. The hotkey records in a popover that also shows conflicts with Replace Assignment, Remove Shortcut and Reset to Default; the row's context menu has the last two. KeyboardShortcutSettings owns recording, explicit conflict replacement, removal and individual/all resets. ShortcutRecorder is a first-responder adapter, active only while recording; Escape cancels. Preferences flow through the existing changed delegate and workspace save path. The Links pane explicitly opts into global Little Arx invocation using its current binding; registration status/errors are reported by AppFeature.
Air Traffic Control is a builder: each route is a URL line (Domain or Domain and Subdomains, one pattern field read by `RoutingPattern`: a host with an optional `scheme://`, port and path prefix, a switch and a remove button) and an Open in line (`RoutingSpaceMenu`: Most Recent Space, Ask for a Destination, or under each profile its Most Recent Space or one of its spaces; Ask hides the window choice, which the person makes when the link arrives; `RoutingWindowPicker`: Main Window or Little Arx, which opens in that space's profile). Edits save as they're made (`routing.update`); New Route adds a draft that's saved once its pattern names a host (`routing.add`); a refused change shows its error on that route's row (`failedRuleID`). Otherwise sets where unmatched links open, or Ask for a Destination. The Links pane's Air Traffic Control section ends with Runway appearance (`ui.runwayAppearance`, agent key `runwayAppearance`): Regular or Compact, the look of the picker Ask opens. It edits persisted ordered routing rules, enabled states and the unmatched-link fallback. Its local tester reports the winning saved rule and resolved profile, space and window mode without opening a URL. Matching help states exact encoded path-prefix and default-port semantics. Missing destinations remain visible until repaired; rule edits do not alter the original URLs.

App Links, a page beside Air Traffic Control in Links (DEV-857, DEV-1114, DEV-862; `AppLinkSettingsView`, `AppLinkEditor`, `SettingsAppLinks`) list handlers for pages' links to other apps, one card each. Row 1 is the app picker, Name, Scheme and Remove; row 2 Host and Path prefix (AppUI's labelled `AppLinkFields`, prompts `claude`, Any host and Any path); row 3 the links the card catches ("Catches claude://login/callback…") or the rule its scheme breaks, as you type; row 4 Add profile on the leading edge and the Enabled switch on the trailing one. The picker is a rounded button with a plus until an app is picked, then that app's icon; it never shows an app just because it matches the scheme. It opens a searchable popover (`AppLinkEditor.pickerChoices` filters by name, scheme and bundle ID): the apps macOS registers for the scheme, then installed apps that declare schemes and apps chosen this session, each once and one row per scheme an app declares (`PickerChoices.entries`), Choose… for an `.app` anywhere, and System Default. ↑ and ↓ move the highlight from the search field and Return picks it. Picking fills Name (unless you wrote your own) and Scheme and makes Open app use that app; a new handler is saved as soon as a pick gives it a scheme, and lives in `AppLinkEditor.draft` until then. Under the card come the routes in the order link routing reads (`AppLinkEditor.routes`): each profile's, then **Otherwise** (the default) last. Add profile inserts a profile's route just above Otherwise, starting as Otherwise does. Each route's dropdown offers System Default, Open in each of the handler's apps, Other App… and Run script. A script route shows `AppLinkEditor.scriptExample` (`fxclaude open-url work "$1"`) as ghost text; Tab or → in the empty field uses it (`useScriptExample`, empty scripts only), with a "Tab to use the example" hint while the field is focused and empty (AppUI's `AppLinkScriptField`). Under the field, "The link is `$1`. Quote it." sits with Test and Remove; a failed Test is on its own line below, wrapped. Test runs the script once with a sample link (`AppLinkEditor.sampleLink`) as that profile. Origins Always allow remembered are listed with Forget. The footer links to the manual's Scripts section about fxClaude's and fxCodex's `open-url`. Handlers are saved in the routing shared key (`RoutingPreferences.appLinks`) after validation; web schemes and duplicate profile routes are refused on the card. Lookups go through `AppLinkClient` (`installedApplications`, `applicationsForScheme`, `chooseApplication`, `bookmarked`).

The Advanced pane exposes a host-supplied Local assistants (MCP) action. AppFeature owns its approval/session state and credential presentation; SettingsFeature remains independent of transport and engine services.

Profile details expose local Browsing History. Clear History captures one explicit profile and requires confirmation, while retry and operation errors remain scoped to that profile. Clearing history does not remove saved tabs or Chromium site data.

ExtensionsFeature is composed as a capability-gated Manage Extensions panel under the selected Profile. AppSettingsView supplies current ordinary profiles, profile selection reconfigures the child synchronously, and settings dismissal cancels it. Existing permission escalation remains disabled; removal requires exact inventory-bound confirmation.

Remove Profile retains website data by default. A separate capability-gated permanent-erasure option requires typing the exact profile name and explains app shutdown, a later Mac restart and verification. The Settings delegate requests retirement without removing metadata itself. Durable pending requests remain visible after the profile leaves the active list; uncertain requests can be checked/retried with the same consent. Only a verified native erased state displays confirmed removal, and blocked cleanup explicitly preserves uncertainty.

Automatic picture-in-picture is configured per origin and profile from a row's context menu on the Library's Media page. It is implemented and is not listed among pending Advanced settings.

Advanced offers exporting an Arx archive or bookmarks HTML and importing browser data, with choices to include browsing history and the Tab Archive in archives, and an export's progress with Cancel. The buttons, choices and progress are host-supplied through `SettingsBrowserDataExport`: AppFeature saves the file and opens the import flow.

Arx has the Default Browser row in place of the pending one. `SettingsDefaultBrowser` reads `DefaultBrowserClient` when the row appears (`ui(.checkDefaultBrowser)`) and on `event(.applicationBecameActive)`, which AppFeature sends while Settings is open. The row names the current default browser and offers Make Default (`ui(.makeDefaultBrowser)`) when it isn't Arx; after a declined prompt it says the default wasn't changed. Automated runs get the client's `unavailable` value, so the row says the default can't be read and offers nothing.

General starts with Updates (DEV-859), in place of the pending Automatic updates row. `SettingsUpdates` follows `AppUpdaterClient`: AppFeature sends `ui(.startUpdates)` once at launch, and each status lands in `updates`. The section shows the last check or a check in progress, Check Now (`ui(.checkForUpdates)`, also the Arx menu's Check for Updates…, both only while Sparkle can check), and switches for automatic checks and automatic downloads; downloads need automatic checks. In a Debug, unsigned, automated or unconfigured build the client reports why it's off, a single row says updates aren't set up (or that development builds don't update), and nothing reaches Sparkle. A relaunch request from Sparkle becomes `delegate(.quitToInstallUpdate)`, which AppFeature turns into its usual quit. While an update waits for Arx to quit (`isReadyToInstall`), the row says so and Check Now becomes Quit and Install (`ui(.installUpdate)`), which sends the same delegate action. When the build has a beta feed (`offersBeta`), an Update channel picker switches between Stable and Beta (`ui(.updateChannel)`, DEV-888); its detail says switching back keeps the current version until a newer stable one. The first launch after an update gets `event(.whatsNewReady)` from the updater's stream into `whatsNew`; `WhatsNewView` shows the notes and Full Release Notes (`ui(.openReleaseNotes)`, which closes the sheet and sends `delegate(.openReleaseNotes(url))`) and Continue (`ui(.dismissWhatsNew)`).

Privacy (DEV-887) is its own category. `SettingsPrivacy` follows `DiagnosticsClient`: AppFeature sends `ui(.startDiagnostics)` once at launch, which keeps new crash reports and sends them only while sharing is on; the pane reads the status when it appears (`ui(.loadDiagnostics)`). Share crash reports is off by default and can't be turned on in a build without a feedback relay, where its detail says reports stay on this Mac. The pane lists how many crash reports are kept, with Remove (`ui(.removeCrashReports)`, Arx's own copies only), and Report a Problem… (`ui(.reportProblem)`), which sends `delegate(.reportProblem)` for AppFeature to present.

General › Tabs ends with Unload inactive tabs (DEV-873): a picker of `TabUnloadDelay` (After 1, 2, 3, 6 or 12 hours, or Only when memory runs low; 3 hours by default, DEV-1326) that sends `ui(.tabUnloadDelay)` and saves into `general`. AppFeature's tab unloading reads it on each sweep. Search finds it by memory, Memory Saver, sleeping tabs and similar words.

General ends with the setup guide: Open Setup Guide reopens onboarding where it left off, and Open Step lists the host-supplied `onboardingSteps` by their AppUI titles so one step opens on its own. `openOnboarding` passes the step, or `nil` for the whole guide, to the host.

The Arx pane shows `ArxIdentityCard` in `general.identityCardStyle`. Its cycle control sends `ui.cycleIdentityCardStyle`, which moves `general.identityCardStyle` to the next style; AppFeature saves it like any other shared setting. The back of the member pass counts the profiles, spaces and tabs in the organization Settings is shown with. Every face's Member since is `installDate`, a read-only shared key of the workspace preferences (`BrowserPreferences.installedAt`) that AppFeature records at launch (DEV-1323). The share control sends `ui.shareIdentityCard`; while `isSharingIdentityCard` is true, `identityCardSharing` renders the card with `ArxIdentityCard.image` and shows the system share sheet with Copy and Save… added, then sends `ui.identityCardShareFinished`.

`MemberNumberFeature` (DEV-701) is the Member number section beside the card, AppUI's `MemberNumberSection`. When the pane shows it reads the providers this build offers and the number this Mac saved, which restores the claimed number after a relaunch without signing in. Get your member number (`ui.claim`) runs `MemberNumberClient`'s sign-in, sends the ID token once, saves the answer and shows it; its states are not claimed, signing in, claimed and failed (no connection, cancelled, refused, sign-in failed), and Try Again claims again. The number goes in every card face's top-right corner and into the shared image. It's kept per Mac, not synced through iCloud: the server gives the same account the same number on every Mac, and the Production CloudKit schema stays as it is. Its anchor, `memberNumber`, is the person's own (`user`).

Appearance & Sound also holds Sound feedback (`general.soundsEnabled`, off by default), which SoundFeedbackClient reads before each of its three sounds (DEV-1256): a capture copied or saved, a download finished, and a download that failed or a capture that couldn't be taken. The pane also holds the application icon, which shows the one icon Arx ships with as the chosen option.

Saved passwords (DEV-721): the Passwords row in a profile's data card sends `ui.showSavedPasswords`, which opens `SavedPasswordsFeature` for that profile only if Settings lists it, so a private profile never gets one. `SavedPasswordsView` lists sites and usernames with search, Copy Password, Show Password, Edit, Remove, Add and Import, the profile's "never saved" sites, and the sites where agents sign in without asking (the host passes `agentSignInSites` and `removeAgentSignInSite`; AppFeature keeps them in `automationPreferences`). State holds no password: `LentPasswordField` registers an AppKit field with `BrowserPasswordFields`, the engine reads a typed password from it or writes a revealed one into it after LocalAuthentication, and the field is emptied when it goes away. Copy puts the password on the pasteboard, concealed, cleared after a minute. A stale list reloads; import reports imported, kept (already saved) and skipped rows.

Autofill (DEV-875): Settings › General › Autofill has "Ask before filling passwords" (`GeneralPreferences.asksBeforeFillingPasswords`, on by default, searchable as `autofillAuthentication`). On, choosing a saved account in a page asks for Touch ID or the login password first, as revealing a password does; payment cards always ask.

Addresses and cards (DEV-893): Settings › General › Autofill also has "Fill addresses" and "Fill payment cards" (`GeneralPreferences.fillsAddresses`, `fillsPaymentCards`, on by default). A profile's data card has "Addresses and Cards", which sends `ui.showAutofill` and opens `AutofillDataFeature` in `AutofillDataView`: addresses and cards listed, added, edited and removed (asking first). A card's number goes in through `LentPasswordField`, so state holds only its last four digits; an edit with an empty number keeps the saved one (`AutofillDataFeatureTests`).

Site settings (DEV-716): the Site Settings row in a profile's data card sends `ui.showSiteSettings`, which opens `SiteSettingsFeature` for that profile only if Settings lists it, so a private profile never gets one. `SiteSettingsView` shows each permission's default, each site's own settings (search, change, remove one, remove a site, Add Site…) and page zoom (default and per site, Add Site…); managed settings are shown but can't be changed. Every change is a `SiteSettingsEdit` the engine applies, answering with a fresh listing; any change the engine reports for the profile (a page's permission prompt, automation) reloads it.

Clear Browsing Data and the downloads folder (DEV-647): the Clear browsing data row in a profile's data card sends `ui.showClearBrowsingData`, which opens `ClearBrowsingDataFeature` for a listed profile. `ClearBrowsingDataView` offers a time range and the kinds to remove, each with what that range holds (history and the Downloads list counted by the app, the rest by the engine). Clearing asks the engine first, then removes the profile's finished downloads from the list and sends `clearHistory` (all time) or `clearHistorySince` to the app, and `clearedSiteData` when cookies or the cache were cleared, so hover cards forget site details fetched with them (DEV-1142); if the engine fails, the app's own lists are cleared only when nothing else was asked.
