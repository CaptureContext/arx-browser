# CommandBarFeature

Entries carry an optional bounded destination identity for their labeled profile/space/location. Execution carries the frozen selected entry, mode and presentation sequence; the hosting feature revalidates context before applying it. Query edits retain that sequence, while reopening the bar advances it.

Controlled query, stable selection and typed command intents.

Entry modes keep presentation and navigation intent explicit: `newTab` leads with open tabs, then Favorites, then history, and opens submitted destinations in a new tab; `commands` favors commands and space/folder actions and navigates the current page when a URL is submitted; `currentTab` edits the selected page's URL in place. Address editing preselects the full URL and shows suggestions before the first edit. Reopening requests native input focus again without rebuilding the store. Outside `commands` mode an empty query lists only those pages; commands, spaces and folders appear on a text match. Return follows the highlighted result: a typed link, a suggestion or the page the text leads toward. Tab never follows anything. Keyword + Tab starts a site search, and so does a `!bang` + Tab; an unedited address stays as it is; any other typed text closes the bar and goes to a new chat (`delegate.startChat`, DEV-720) when the host allows chat (`isChatAvailable`, off in private windows). ⌫ in an already-empty field (`ui.deletedWhenEmpty`, sent by AppUI's input outside composition and key repeat) first leaves a keyword search, then closes the bar like Esc when `GeneralPreferences.closesCommandBarOnEmptyDelete` is on (the default; DEV-750). `showsAgentHint` is true exactly when Tab would start a chat (`chatPrompt` set and no `pendingShortcutKeyword`); the view then shows the "Ask an agent ⇥" hint, whose click sends `ui.tabPressed` (DEV-751). Bangs and keyword + Tab search work in every mode.

No inline completion (DEV-1223): the field shows only what was typed, so a long address scrolls like any text. The page the text leads toward, as in Safari, still leads the results and is highlighted, so Return opens it. `AddressMatchIndex` holds the candidates' web addresses, sorted once per presentation, in three forms: without the scheme and `www.` (a front page drops its trailing slash), with `www.`, and in full. Each keystroke is a binary search plus a scan of the addresses that start with the query. Until a `/` is typed a front page wins over a site's other pages; then the higher `Entry.frecency` (DEV-1015), then the shorter address, then the earlier candidate. Only an address that starts with the typed text, ignoring case, matches, never one that merely contains it, and never for text with spaces, a `!bang`, an active keyword search or a prefilled address before its first edit. A deletion is an edit like any other (DEV-719's `queryDeleted` went with the completion). The match is computed from state, not sent through the store; the store still receives one query action per keystroke. Filtering works the same way (DEV-946): `CandidateMatcher` keeps the last filter's results by mode and query, made again whenever the candidates are set, so the several reads of `entries` one keystroke or arrow key makes (the reducer, the view, the highlighted result's actions) filter the list once. Matching is `localizedCaseInsensitiveContains` on each title and subtitle; titles aren't case-folded ahead of time, because no fold done once matches it for every script (emoji sequences, combining marks, the Turkish dotted i, ß). A cached answer still reads `candidates`, so observers of `entries` follow them. Marked text (IME composition) keeps arrows, Return, Escape, Tab and Delete, and the field isn't redrawn while it's marked. A `!keyword` resolves through `BangCatalog.target(for:shortcuts:)`: the user's shortcut owns its keyword, even while disabled, and Helium's bundled list (`State.bangs`) answers the rest. Suggestions list the user's matching shortcuts, then up to six bundled bangs ranked by the list's order; each keystroke is a dictionary lookup or a binary search over sorted keywords. Keyword + Tab without `!` stays with the user's shortcuts, because bundled keywords include ordinary words such as `price` or `define`.

Bangs and the person's shortcuts behave alike (DEV-1321). A `!keyword` with nothing after it lists one row, `.useShortcut`, so Return or choosing it enters the scoped search (`siteSearchKeyword`); Tab does the same (`pendingShortcutKeyword` reads `typedBangKeyword`), and so does Space typed right after the keyword (`ui.queryChanged` to `!keyword ` with the previous query `!keyword`). `enterSiteSearchScope(_:)` is the one way in. `!keyword query` searches at once. In a scope, before a query, the one row (`front-<keyword>`) opens the site's front page: the shortcut's or bang's homepage, or else the front page of the site its template searches (`BangTarget.site`). Arx has no starter shortcuts: `BrowserPreferences.searchShortcuts` starts empty, since the bundled bangs cover those sites.

Typed text has rows of its own (DEV-978): `destination` opens it when it's a link (a web URL, text with a dot and no spaces as `https://`, or `localhost` with a port or path as `http://`), and searches the profile's engine for it otherwise; a link also gets `search-typed`, the plain search for exactly what was typed. They come within the first five results (`typedRowsWithin`), link first, after only what leads: an exact alias, the page the text leads toward, and the calculator and create rows. In `commands` mode they follow up to the first three results, so commands stay first. An unedited prefilled address keeps only its `destination` row, at the end. Filtering itself is untouched, so `CandidateMatcher` still filters once per keystroke.

Addresses with other schemes (DEV-1189, `ARX_SCHEME_ADDRESSES`, on by default) open too. BrowserCore's `TypedSchemeAddress` reads the text:
- `about:blank`, `file:` and `view-source:` open a page. `data:` and `javascript:` never open from the bar.
- `arx://settings/…` and `chrome://settings/…` open Settings through BrowserCore's `SettingsAddress` table.
- Other apps' links, such as `slack://`, `zoommtg://` or `mailto:`, open in the app macOS assigns: the window's delegate hands them to AppFeature, which opens them as App Links' Open does (`appLinks.openApp`). The engine never navigates to them. One no app on this Mac opens isn't offered: it searches, so nothing is lost silently once the bar closes.
`scheme:rest` without `//` is an address only when browsers know the scheme or an app on this Mac opens it. `CommandBarSchemeApps` asks once per scheme as the text is typed and keeps the answer in `schemeApps`; tests answer "no app". So `note:milk` and `re:invent` still search, `spotify:track:…` opens Spotify, and `example.com:8080` stays a host and port. `javascript:` never opens. `arx://` and `chrome://` addresses Arx has no place for search as before. The address's row (`destination`, subtitled "Arx Settings", "Opens in <app>" or the address) leads in every mode, right after an exact alias or title match. Return takes it, and the search for the same text is the second row. `chrome://downloads`, `history` and `extensions` list Arx's command for them, as `arx://extensions` does.

⌘↩ opens exactly what's typed as an address (DEV-1189, same flag):
- It's never a search or the highlighted result. `typedURL` reads the text: a scheme address, a web address, `localhost`, or anything else without spaces, with `https://` added. Text with spaces, a `!bang`, a keyword search and `scheme:rest` that's no address give none.
- `openURLEntry` opens it in the current tab from the address field and Little Arx, and in a new tab from ⌘K (`openInNewTab`) or ⌘T (`open`, which makes a tab there).
- While there's one, `actionID(forShortcut: "⌘↩")` answers `openURLID`, in the actions panel too. Every result's actions list it second as Open as is with ⌘↩ (DEV-1319), and a result's Open in New Tab then shows no key, though it stays in its actions, so no two actions claim ⌘↩. Choosing Open as is runs exactly what ⌘↩ runs. ⌘-click on a result (`ui.commandClicked`, from AppUI's row when ⌘ is held) highlights it and runs what ⌘↩ then would: Open as is, else the result's Open in New Tab, else nothing.

Icons (DEV-1311): the field's icon is the highlighted result's, which AppUI's `CommandBar` reads from the results it's given, so the field and the row share one request. A bang's row carries `SidebarItem.SiteIcon` for the front page of the site its template searches (`BangTarget.site`, `https://github.com/` for `!gh`) in `bangIconProfileID`'s profile, with `siteIconFetch: .storedOnly`: listed or highlighted, it shows only what's stored for that page, or the magnifying glass. Only a scoped search (`!yt` then Return, or a keyword then Tab) asks the site: `scopeSiteIcon` is the scope's site, which the field shows whatever is highlighted and may fetch when the profile has none stored; leaving the scope stops a fetch under way, and the icon is stored for next time. The window sets `bangIconProfileID` to its space's profile when the bar opens, nil in a private window, whose bangs never show or fetch an icon; Little Arx sets its tab's profile; Page PiP's address bar sets none.

Remote search suggestions come from `SearchSuggestionsClient`, using the profile's search engine while `suggestsRemotely` is on. The owning window sets it from its profile's setting (on by default) and never in a private window; Little Arx doesn't ask yet. Typed text goes out 150 ms after the last keystroke, and a newer keystroke or closing the bar cancels the request. Nothing is sent for an unedited address, a keyword search, a `!bang` or text with a scheme. Up to four suggestions are listed, without the typed text itself, each searching the profile's engine. In `newTab` and `currentTab` modes they follow the typed rows below; in `commands` mode they follow the local results, so actions stay first. Kagi and Perplexity have no anonymous suggestion service and show local results only. Changing the profile's engine cancels the old request and drops its late responses. Suggestions only show while they belong to the current text and engine, and a failed request shows none. A new request cancels the previous one synchronously in reducer order rather than with `cancelInFlight` (DEV-606); an older request that registers late was already invalidated.

Candidates come from the owning window. MainFeature supplies current-profile tabs and the profile's persistent local history. A history entry for a page an open tab shows is listed too, right after that tab, so Return on it opens the page again (DEV-810). Before the index loads, and for private browsing, only the active page’s transient stack is used. Persistent history results capture profile, space, entry identity and exact URL; the host rejects selection after those identities change or the entry is cleared. Candidate lists remain frozen while presented. Result selection emits a typed intent for the host to execute.

`Entry.commands(in:)` lists every command enabled in the window's context, and a command `BrowserCommand.isListedDisabled(in:)` disabled (DEV-1262): the proxy link commands on a page no proxy link rule matches. A disabled entry has the `disabledCommand` intent and `CommandBarResult.isEnabled` off, so AppUI dims its row; choosing it does nothing and the bar stays open.

Requires macOS 27 and Swift 6.4. Features use core, services, AppUI and lower-level features; services never import features. Verify with `make test-all`.

`arx://extensions` (DEV-633) is Arx's own page address: typed in any mode, it lists only the Extensions command, and nothing where that command is off (private windows, Little Arx). `CommandBarFeature.State.internalCommand` maps the address.

Command aliases (`CommandAlias`, the `commandAliases` shared key, set in Settings › Shortcuts) are words that find a command: an entry built with `Entry.command(_:bindings:aliases:)` shows its alias as a tag after the title, typing the start of an alias lists the command, and typing an alias exactly puts the command first in every mode, ahead of search suggestions, so Return runs it.

The `.history` mode (DEV-795; Show History, ⌘Y, opens the Library's History page instead since DEV-817) lists only history entries, in the order the host gives them (newest first), up to 50, filtered by title or address as you type. It never asks the search provider for suggestions, and it has no address match or alias matches, so only listed entries can be selected. MainFeature gives it the profile's whole history, including pages open tabs show.

## Calculator and quick create (DEV-895)

`State.entries` puts two kinds of rows from BrowserCore's pure functions first, after the page the text leads toward so Return still opens it, in every mode but `.history` and never for a prefilled address: the calculator's result (`CommandCalculator`, id `calculator`, intent `copyText`) and what "new …" or "create …" can make (`QuickCreate`, ids `create-<host>`, intent `open` of the `.new` address). "new" or "create" alone lists every target after the other matches, so New Tab stays first. Return on the result runs `copyText` in the bar itself: it closes the bar as Esc does and copies through the `commandBarClipboard` dependency (`NSPasteboard` live, unimplemented in tests); hosts never see the intent.

## Actions (DEV-810)

While the bar is open, ⌘K (routed by the host: MainFeature's pane command, LittleArxFeature's `dispatchCommand`, AppFeature's Little Arx routing) or the footer's Actions button sends `ui.actionsToggled`, which opens `State.actionPanel` for the highlighted result. `State.actions(for:)` lists a result's `ResultAction`s; the first (`primary`, shown with ↩) is always what Return does, so nothing changes for Return. An open tab adds Open in New Tab, Open in Peek, Open in Little Arx and Copy URL. A history result adds Switch to Tab when a listed tab shows its page, Peek, Little Arx, Copy URL, Delete from History and Delete All from the site (`BrowsingHistoryRemoval.site`, ignoring case and `www.`). A typed address or search adds Peek and Little Arx, and Copy URL for the typed address. A search (`Entry.isSearch`: typed text that isn't a link, searched with the profile's engine, `search-typed`, a suggestion, `search-original` or a bang's search) says Search, not Open (DEV-1319): its row's label (a bang's keeps "Search site"), its first action, and Search in New Tab, Search in Peek and Search in Little Arx. A typed link and pages still say Open. Outside `newTab` mode, where Return replaces the page, pages also offer Open in New Tab. Commands, spaces and folders have only their own action. `actionAvailability`, set by the host before every presentation, leaves out what it can't do: private windows have no Peek, Little Arx or history removal; Little Arx has no new tabs or history, and Peek only over a page.

`ui.actionQueryChanged` filters by title and keeps a visible highlight; `ui.actionHighlighted` and `ui.actionSelected` drive the panel; `ui.actionsDismissed` (Esc in the panel) and `ui.dismissed` close the panel before the bar, and both bump `inputRefocusRequest` so the field takes focus back without counting as a new presentation. While the panel is open, `ui.highlighted` is ignored: the panel belongs to the result it opened on. Running actions send `delegate.execute` with the result's identity and the action's intent (`openInNewTab`, `openInPeek`, `openInLittleArx`, `copyURL`, or a tab's `selectTab` with its destination), so hosts revalidate them as any result. Delete actions drop the matching results at once, keep the bar open, move the highlight to the next result left, and send `delegate.removeHistory`; MainFeature forwards it as its own `delegate.removeHistory`, which AppFeature's ProfileHistory applies to every window and writes with `BrowserHistoryClient.removeEntries`.

The interaction follows Raycast's action panel, in Arx's style. Actions ⌘K floats in the bar's bottom-right corner (AppUI's Raised look, DEV-1277); ⌘K or a click turns it into the actions' search field with the actions above it, each with its key. The first is what Return does on the highlighted result (`primaryActionTitle`). Each action has a key that also works straight from the bar or the panel (`State.Shortcut`, after Arx's link clicks): ⌘↩ Open in New Tab, ⌃↩ Switch to Tab, ⇧↩ Peek, ⌥⌘↩ Little Arx, ⌃X Delete from History, ⌃⇧X Delete All from the site. AppUI's `CommandInput` names a key with ⌘, ⌥ or ⌃ (or ⇧↩) and `actionID(forShortcut:)` finds the action; the view then sends `ui.actionRequested(id)`. Copy URL uses the app's Copy URL binding (`copyURLShortcut`, ⇧⌘C unless rebound), which the main menu takes first, so AppFeature's command routing (before it copies the page's link), MainFeature's pane command and LittleArxFeature's `ui.copyURL` send `ui.actionRequested("copy-url")` while their bar is open on a result that offers it (`offersCopyURL`). The app's own bindings win: hosts pass every other command's key in `reservedShortcuts`, setting all three keys from their bindings with `State.useShortcuts(_:)`, and an action whose key is among them shows none and answers to none.

Removals stay pending in AppFeature's `ProfileHistoryState.pendingRemovals` until the store answers (`history.removalFinished`), and every snapshot that arrives meanwhile has them applied to entries last visited before the removal was asked for, so an older answer can't bring a removed entry back while a later visit stays.

Suggestion requests have a reducer-owned invalidation token. Changing the query, provider, privacy setting or presentation invalidates it synchronously before cancellation effects run. A late-starting or cancellation-ignoring debounce cannot admit text to the previous provider. This does not change TCA’s wider cancellation ordering behavior tracked in DEV-606.

Diagnostic pages (DEV-898): `arx://version` and `arx://gpu`, and with developer mode on net-internals, process-internals, media-internals, serviceworker-internals, webrtc-internals and inspect, typed as `arx://` or `chrome://`, offer one entry that opens the engine's `chrome://` page. Without developer mode a developer page offers nothing, not a search.

## Ranking, exact matches and Settings rows (DEV-1015)

History entries carry `visitCount`, `typedCount` and `lastSpaceID` (BrowserCore's `BrowsingHistoryEntry`). `HistoryFrecency.score` weighs visits, typed visits (×4), the current space (×1.5) and the last visit's age (in steps after 4, 14, 31 and 90 days). MainFeature's `commandCandidates` ranks history by it as of the profile's latest visit, so nothing reads the clock, and gives an open tab its page's score; Show History keeps newest first. A visit is new when the tab's page, back-forward entry or list length changes, not on a title update or reload (AppFeature's `ProfileHistoryState.lastVisit`; the length covers WebKit's relative entry IDs), and one recorded out of order still counts. `Execution.isTypedAddress` marks the typed link's own row, the page the text leads toward or a history result taken from the field, when what runs loads a page. Once the window has opened it, MainFeature or LittleArxFeature sends `delegate.typedAddressOpened(url, tabID)`, and the next new visit to that site in that tab within 30 seconds counts as typed (`ProfileHistoryState.typedAddresses`). Migration Assistant seeds both counts from Chromium's `urls` and Firefox's `moz_places` (Safari has visit counts only), and `merge` keeps the larger counts, so importing twice counts nothing twice.

DEV-1068: history also matches the words inside pages. With `pageTextProfileID` set (the window's profile, never a private window's), each change to three or more typed characters asks `pageTextIndex` after `pageTextDelay`; `pageTextFound` keeps the hits only for the text still typed. `entries` then lists, after what matched by title or address, up to `pageTextLimit` history entries found only by their words, by `frecency`, each with its passage as the subtitle; the `.history` mode lists them after its own. The Library's History page, which Show History (⌘Y) opens, doesn't search page text yet. A prefilled address and the action panel aren't searched. Each search is cancelled in reducer order, as suggestions are, so an older one registering late can't cancel the newest.

`State.exactMatch` is a command or Settings row whose title is exactly the typed text, ignoring case and accents. It leads right after an exact alias, ahead of the completed page, history and suggestions, and `edit` highlights it.

Settings rows come from the `commandBarSettingsRows` dependency, read when the bar opens: AppFeature sets it to `.settingsIndex`, Settings' search index as entries (`openSettings` with `SettingsDestination.id`, keywords, and `CommandBarResult.state` On or Off for a switch). They answer typed text only, keywords from the third letter. MainFeature sends `delegate.openSettingsRow(id)` and AppFeature opens Settings at the row as its own search does. Little Arx lists none.
