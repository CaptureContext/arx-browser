# MigrationAssistantFeature

Customize: the import flow over the MigrationAssistant service. The user picks the source and the kinds of data (Passwords and sign-ins among them), then reviews a profile mapping and the preview, and imports; progress, cancellation, results and retry follow. It is reusable from OnboardingFeature (its migration step) and SettingsFeature; the host supplies the `MigrationDestination` and handles the delegate. Onboarding's "Make it yours" page opens it from Customize… already at `selecting`, with its discovered sources, browser, categories and Keep its spaces (as `mapsToNewProfiles`) filled in, so it doesn't discover again.

Phases run `idle → discovering → selecting → inspecting → previewing → importing (→ cancelling) → finished`. Discovery selects the first source and all of its categories. Continue runs `inspect` and shows the review: per category, new items, items already imported there, records that can't be imported and what Arx has no equivalent for. Import builds a `MigrationPlan` from the preview with an injected UUID and consumes the execution stream; events for any other plan are ignored.

## Profile mapping

DEV-842. For a source that `offersLayouts` (browsers, and bookmarks files), the review starts with **Profiles**: one row per source profile from `MigrationPreview.profiles` (`mappings`, a `ProfileMapping` each). Each goes into a **New profile** with an editable name (the source profile's name to begin with), or into an existing Arx profile from the host's `spaceOptions` (`profileOptions`, with the current profile first), where its spaces become new spaces. Sources with profiles of their own (`preservesOrganization`) start with new profiles; others start in the current profile. `mapProfile` inspects again, because what's already imported depends on where it goes; `renameProfile` doesn't, and the plan takes its destination (`resolvedDestination`, with `profileRoutes`) when Import is pressed. The first read can't know the source's profiles, so when their default mapping sends them somewhere other than where that read went (existing profiles instead of the current space), the review is read again, and the plan always describes what the review showed. Mappings survive going back to the selection and inspecting again, and a profile seen for the first time gets the default. Choosing another source, or clearing Arx's data, starts them over. Files without profiles of their own go into the current space with no mapping. While Passwords and sign-ins are on, the browser's profiles that hold passwords but nothing the review read (no bookmarks or open tabs) join the mapping too, and leave it when passwords are turned off.

Cancel during review cancels the inspection effect. Cancel during an import asks the service to stop at the next category boundary and keeps consuming the stream until the `cancelled` report arrives, so committed categories are shown. The window can't be dismissed while an import is running or cancelling. Retry reruns the same plan; the service skips items already committed by key, so retrying is idempotent. A `sourceChanged` failure returns to selection and asks the user to review again. Problems are typed (`Problem`) and localized in the view.

Delegates: `finished(MigrationReport)` when the user closes the results and `dismissed` otherwise. The feature never writes the organization itself.

The view is drawn as an Arx modal (DEV-791): `ArxModalScaffold` with an `ArxHeaderBar` (Close, the source's name, and Choose a File… as a raised capsule while selecting), `SettingsSection` cards with `ArxDropdown`s for the source and each profile's mapping, a name field for a new profile, `SettingsToggle` rows for the kinds of data and count rows for the review and results, and `ArxModalButton`s pinned in the footer. Onboarding shows it under the window's traffic lights.

The review lists the source's spaces with an `AppearanceSwatch` of their colors when any of them brings colors (DEV-897).

A source that `requiresFullDiskAccess` (Safari, DEV-840) shows `FullDiskAccessPrompt` instead of the category toggles: why Arx needs Full Disk Access and Open System Settings (`ui(.allowFullDiskAccess)`, through `FullDiskAccessClient`). The state's `fullDiskAccess` (`unknown`, `denied`, `granted`) is checked when such a source is selected and on `event(.applicationBecameActive)`, which the host forwards; Review is refused until it's granted. A granted answer is kept. Onboarding uses the same prompt view on its page.

When no supported browser is found, the view says so. The user can also choose an Arx archive or bookmarks file, which joins the source list; a file that can't be read, or is from a newer Arx, is reported with its reason. Strings come from AppUI's generated catalog (`migration.*` keys).

## Extensions

DEV-845. For Arc, Extensions is a kind of data like the others. The review counts the extensions from the Chrome Web Store, which Arx installs after the import, and the ones to reinstall by hand, which are listed by name. When the import finishes (not cancelled), `ExtensionImportFeature` takes the report's extensions (`extensionImport`). Each store extension with a source profile goes into the Arx profile that profile went to (`MigrationAssistantClient.receivingProfile`), one at a time: the inventory is read, an extension the profile already has is reported as already there, and otherwise `BrowserExtensionsClient.prepareWebstoreImport` downloads and verifies the store's package and the user reviews it in `ExtensionImportReview` (DEV-1300): "Add “name”?", the publisher, its place in the series ("2 of 3 from Chrome") and the Arx profile it goes into, what it can do, and its package details folded away, with Skip All, Skip, Install All and Install. Install All, offered from the first review while at least two are left, installs the open one and every one after it with the permissions each asks for, without showing their reviews (`acceptsAll`), and the sheet says so in one line. An answered review can't be skipped any more; Skip All declines the open review and skips the rest. A failed install never waits for a press: the series moves on, and the results count it. Every extension ends as installed, already there, declined, skipped, not from the store, or failed (no Arx profile, an engine that can't install by ID, blocked by policy, or a failed download or check). The results list them. Close and Done are refused until the step ends, and passwords start after it. The plan makes the Arx profiles store extensions go to, even when nothing else goes there (`MigrationPreview.extensionProfiles`). OnboardingFeature's page runs the same step after its own import. Both show the review through `extensionImportReview(_:)`, a view modifier over the step's optional store (DEV-854).

## Passwords and sign-ins

`CredentialMigrationFeature` (DEV-650, reworked in DEV-842) is **Passwords and sign-ins**, a kind of data next to the categories for browser sources only (`MigrationSource.offersCredentials`), off until the user turns it on (`ui(.toggleCredentials)`). With it on, Continue works even with every other kind off. Turning it on creates `credentials` and sends it `load`; choosing another source turns it off. It has no profile pickers of its own: it follows the mapping. The assistant hands it the mapped source profiles (`mappedProfiles`) whenever the review is read; without a mapping it uses the browser's own profiles, or the whole source as one (`State.wholeSource`), all into the current profile. It goes through `CredentialMigrationClient` (see the MigrationAssistant README). MCP and agents have no path to it.

`CredentialDestinationWriter.browserEngine(_:)` (`CredentialEngineWriter.swift`) is the live writer over `BrowserEngineClient`'s ABI46 calls (DEV-830): it is available only when the engine has them, maps unavailable to `writerUnavailable` and other engine failures to `writeFailed`, and reports a failed read-back as not checked. AppFeature installs it.

- **loading → configuring.** `load` asks the client for the browser's Keychain item and profiles and whether the engine can take decrypted records, and sets `mode`: `direct` straight from the browser, or `csv(reason)`. Firefox and Zen read their own files and Safari its cookies with no Keychain item (DEV-896; the footer follows `CredentialSource.access`). Safari without a cookie file is `csv(.passwordsApp)` (its passwords are in the Passwords app: File › Export All Passwords…), and its direct mode moves sign-ins only; an unknown browser `csv(.unsupported)`; an engine that can't write `csv(.engineNotReady)`, without touching the Keychain. While the user reviews (`configuring`), `CredentialConfiguration` shows under the mapping: in direct mode what will happen and the Keychain item macOS will ask about (Allow Once recommended, with a note when the name is unverified), with **Use CSV files instead**; in CSV mode a row per source profile to attach its export (`csvChosen(profile, url)`, `removeCSV`), and, when the user chose CSV over a working direct path, **Read from … instead**. Nothing is read meanwhile. In CSV mode Import waits for at least one file (`isReady`).
- **start.** When the ordinary import finishes (not cancelled), the assistant sends `start(plan.destination)`. `resolving` asks `MigrationAssistantClient.receivingProfile` for the Arx profile each source profile went to (`targets`). With passwords on, the plan carries the mapped source profiles (`MigrationPlan.profiles`), and the run makes each one's new Arx profile before its categories, so a passwords-only import still has somewhere to put them. A source without profiles of its own (Firefox or Zen with passwords only) is one whole source (`State.wholeSource`), and it goes into the destination's profile, as the import's items without a profile do (DEV-844). A source profile that still has no Arx profile is skipped, with a note. From here the step takes over the modal (`showsCredentials`); Close and dismissal are refused while it resolves, reads or writes.
- **intro** (direct) says what moves, lists each source profile with its Arx profile, and explains macOS's prompt. **Skip** closes it, **Use CSV Files Instead** goes to the CSV phase. Continue checks that Arx is in the foreground, then asks the device owner (`confirmPresence`), checks the foreground again, then reads every target profile with one Keychain read (`readProfiles`). Background or a failed confirmation returns here with a problem and no read. Denied goes to `csv(.denied)`, missing to `csv(.missing)`, a Firefox or Zen primary password to `csv(.primaryPassword)` (logins for HTTP sign-in prompts aren't imported; each profile's choices and the summary say how many stayed behind), a writer that's gone to `csv(.engineNotReady)`.
- **choosing** has a section per profile ("Personal → Home"): Saved Passwords with its count (and how many couldn't be read) and its sign-ins per site, all movable sites selected at first, with Select All / Select None. Session-only and unreadable sites are listed but can't be selected. A read result that arrives outside `reading` has its records discarded.
- **importing → finished** writes each profile's selection into its Arx profile; a profile with nothing selected has its records discarded instead. The report shows imported passwords, conflicts and skipped ones, and every site's outcome after Arx checked it: Signed in, Sign in again (with the reason), Not checked or Not imported. A profile whose write failed gets its own row in the report, naming it; if every write failed the step returns to the intro. **Undo Import** removes every profile's batch; when one fails, the undone ones leave the report and trying again covers only the rest.
- **csv** (after the import) attaches a file per source profile with an Arx profile and imports them all; files attached during the review go in as soon as the targets are known, with no extra click. A file that fails (bad format, unreadable, an engine error) stays attached with its reason, so the user can import it again or replace it; files that went in are done and take no other. Once every file has gone in, the results show per profile. Each file goes through `BrowserEngineClient.importPasswords` (DEV-721) into its own profile, and the results (or the failure) are shown per profile.

Closing the step or dismissing the assistant before writing discards the decrypted records. Strings are `migration.credentials.*` and `migration.mapping.*`.

## Clear Arx data first

DEV-650, Maxim's decision of 11 November: when Arx already has data, the assistant offers an opt-in **Clear Arx Data First** toggle while selecting, off by default. A host turns it on by passing `existingData` (profile names, space and tab counts); with `existingData` nil (a fresh Arx, or a host that can't clear) it's hidden. With it on, Review goes to `confirmingClear`, which names the profiles and counts what's removed (including each profile's passwords, sign-ins, history, extensions and site data) behind a destructive **Remove and Continue** with no Return shortcut; Back keeps everything. Confirming moves to `clearing` and sends `delegate(.clearExistingData)`. The host removes Arx's data through profile retirement, keeps one fresh profile and space, and answers `event(.cleared(destination, spaceOptions:))`, after which the assistant reviews against the clean Arx, or `event(.clearFailed)`, which imports nothing. Dismissal is refused while clearing. Mappings onto existing profiles start over after a clear, and passwords resolve their Arx profiles only after the import, so they never land in a removed profile. No host provides `existingData` yet (DEV-833), so the toggle doesn't show in the app.
