# ViewerItemFeature

Navigation state and cancellable observations for one browser page. Native objects remain in services.

Each `show` cancels earlier observations synchronously, in reducer order, before starting its own. It does not rely on `cancelInFlight`, which cancels only when the effect task registers off the main actor, so back-to-back shows of the same tab could let an older observation cancel the newer one. An older observation that registers late is cancelled by its own generation on its first stale event.

A navigation that became a download (DEV-1116) isn't a page error. A tab showing a page keeps it. One with nothing to keep reports `navigation.download`, and `ViewerItemView` draws AppUI's `BrowserDownloadingPage` over the empty page: the file, its site and progress, then Open and Show in Finder; Cancel while it runs, Resume when it can continue, and Retry, which navigates to the file's address again, when it was cancelled or failed. While a tab is shown, the item follows that tab's transfers in the downloads queue (`tabDownloads`); `download` is the live one the navigation names. Little Arx and Peek show it too, since they draw `ViewerItemView`. A failed Open, Cancel or Resume there shows DownloadsFeature's `downloadFailureMessage(_:)`, the localized text.

With no tab, `ViewerItemView` draws AppUI's `BrowserEmptyPage`, the homepage, which MainView gives the person's shortcuts through `browserShortcuts`.

A chat tab (`Tab.isChat`, DEV-761) never reaches the engine: `show` keeps its tab and title and starts no observation, and `ViewerItemView` draws the `browserChatTab` environment's content, which the app fills with the profile's chat, instead of a page surface.

`isObserving` is true from a `show` of a tab until `suspend` or a `show(nil)`. ViewerFeature keeps such a pane through a space switch instead of showing its page again (DEV-771).

Observation generations never wrap. At exhaustion, a new `show` is refused; clearing or suspending removes the tab identity before cancelling, so already queued callbacks cannot update that suspended placement.

Requires macOS 27 and Swift 6.4. Features use core, services, AppUI and lower-level features; services never import features. Verify with `make test-all`.

History menu actions capture tab identity, viewer generation and the entire history snapshot. The reducer rejects stale or current-entry selections; the engine snapshot and guarded revision call revalidate immediately before native direct-entry navigation. Replacing or suspending the viewer cancels pending selection. A newer selection cancels earlier ones synchronously in reducer order, and each selection reports in before reaching the engine; one reduced earlier but registered later is cancelled there, so only the newest selection navigates. No continuous gesture recognition is implemented by this fallback.

Page failures use `BrowserNavigation.Failure`. A loopback HTTP(S) page (`localhost`, `*.localhost`, `127.0.0.0/8`, `::1`) that refuses the connection explains that nothing is running on its port; one that fails certificate validation suggests `http://` on localhost or trusting the development certificate in Keychain Access. A loopback `https://` page that fails with `ERR_SSL_PROTOCOL_ERROR` (`-107`) says the server probably serves plain HTTP and offers a button that opens the same port, path and query over `http://` (`ui.openPlainHTTP`, which navigates only while that failure is current). These explanations show for every user, not only in developer mode, and never offer to bypass validation. Other failures keep the generic message with the net error code. DEV-1226: when the failed navigation committed the engine's own error page (Chromium's "This site can't be reached" for a DNS failure, a refused connection or no network, with its own Reload button), the generic card doesn't show over it; `engineErrorDocument` remembers that page's document, so its later events and the tab shown again keep it quiet. A failure that commits nothing (a blank tab, the page before it still showing) and a stopped renderer still get Arx's card, and so do the local development explanations, which name a fix the engine's page doesn't (`Failure.addsToEngineErrorPage`).

`ui.retry` closes the page and reopens it at the URL it last showed, failed or not, unless that was `about:`. The shown `tab` keeps the URL it was opened with, and a pinned tab would reopen at its saved destination, so retrying after a renderer crash or a failed load in a tab that had moved on no longer goes back to where the tab started. `show` then observes the page that is already open.

Find in page belongs to each item: `findQuery` holds the bar's text while it's open, `findSeed` keeps Use Selection for Find text while it is closed, `navigation.findResult` reports the matches, and showing another tab closes the bar. `BrowserCommand.findAction` maps ⌘F, ⌘G and ⇧⌘G to it from any host. ⌘F always focuses the find field (DEV-1222): each one bumps `findFocusRequests`, and `FindInPageBar` takes focus back from wherever it went (the page, the article in reading mode, the URL bar, the sidebar) and selects the field's text, so the next keystroke replaces the query, as in Safari and Chrome. An open bar keeps its query and doesn't search again.

Zoom In, Zoom Out and Actual Size (DEV-726) reach the item as the engine command `.zoom(PageZoom)`. After the engine zooms, the item reads the page's factor and shows it as `zoomBadge` for `zoomBadgeDuration` (1.5 s); each zoom restarts the timer. A page the engine can't zoom is left as it is, with no failure.

ViewerItemView draws the host's `browserPageOverlay` (such as a capture) and then its `browserPageNotice` above the page, both by tab and both skipped while the page is lent to Peek. A notice never hands the keyboard back when it goes, so a toast coming and going leaves focus alone (DEV-780).

DEV-1009: when the page stops answering (`navigation.unresponsive`), the page area shows `UnresponsivePageCard`: Wait (`waitForPage`, which remembers the hang in `waitedHang`, so only a later hang asks again; `show` forgets it, since hang numbers are a page's own) or Reload (the reload command, which ends the renderer first). Chromium reports a hang only after an input went unanswered, so the card appears once the person tried to use the page.

DEV-1016: a page whose renderer ended says why (`message(for:rendererEnd:)`): it crashed, ran out of memory, macOS ended it, Arx ended it after it stopped answering, it couldn't start, or several pages stopped at once. A page that keeps crashing or running out of memory says so, and Arx doesn't reload it by itself; Retry still does.

Reading mode (DEV-1028) belongs to each item too. Once a web page in the engine has loaded, it's checked once for an article (`readabilityChecked`, after `readabilityDelay`) and `isReadable` offers reading mode in the address bar. `readerToggled` reads the article with `pageReader` and lays `ReaderOverlay` over the page (`reader`), closing Find; `readerClosed` takes it away and the page, never touched, is as it was. Going to another page closes it, while a fragment doesn't; a link in the article closes it and navigates the page. `BrowserCommand.readerAction` maps Reading Mode to it from any host.

DEV-1065: any new main-frame document closes reading mode and checks the page for an article again, not only Arx's Reload: the page's own `location.reload()` and AppleScript's reload too. The item keeps the document reading mode is about (`document`) while the same tab is shown again, so the first report after a show closes nothing; a fragment or a frame loading keeps it open, and an article check that finishes for an older document is ignored.

The sidebar URL bar's page button (DEV-1254) is chosen per item by `URLBarPageButton`, a pure rule: reading mode while the page is read, else an extension pinned to the URL bar, else reading mode on a page with an article, else nothing. `urlBarPageButton` follows it after every action, and it changes only once the page has settled (loaded, and its article check answered in `readabilityAnswered`, or it gets none); until then a slot that had a button is `reserved`, so the address doesn't move twice for one navigation. Arx can't pin an extension to the URL bar yet, so no pin reaches the rule.
