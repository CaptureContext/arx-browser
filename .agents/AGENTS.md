# Arx browser

This directory is the project root for a macOS-only Chromium browser. Use the parent directory only as a project collection; keep Arx browser outputs here.

- Use GitHub issues and pull requests for Arx planning and work tracking; follow [issue-tracker.md](issue-tracker.md) for routing. Keep plans, decision logs and implementation status in the issue or the pull request.
- Keep AI-specific context in this single `.agents` directory. Consult the `ai-infrastructure` skill before adding AI artifacts.
- This file is the one source of truth for agent instructions. The root `AGENTS.md` and `CLAUDE.md` only point here, and `.claude/skills` and `.codex/skills` are symlinks to `.agents/skills`; put no rules in them. The skills in `.agents/skills` are public with the repository: `swift-style` and `ai-infrastructure` are published copies (MIT) that must stand alone, so they never point at a skill that isn't published here.
- Follow the `app-structure`, `swiftpm`, and `swift-style` skills when changing the package graph or Swift sources.
- Follow [DESIGN.md](DESIGN.md) when building interface: how lists space, inset and scroll their rows, and how floating controls and nested corners sit.
- Follow [LOCALIZATION.md](LOCALIZATION.md) when adding or changing text a person sees, and when translating: every such string goes through AppUI's catalog, and translations name things as Apple does in that language.
- Use semantic manifest helpers: `.fork`, package-role properties, `.group`, role-based target references, and named shared dependencies. Keep native SwiftPM dependency wiring in helper definitions and third-party wrappers. Preserve selected package identities, versions, traits, and linkage when refactoring helpers.
- Group manifest targets under `// MARK: - <Letter>` sections, using the first letter after any leading `_` for wrapper targets.
- Structure feature actions into `ui`, `event`, `delegate`, and `observation` domains, retaining empty domain enums when unused. Keep internal operations at the top level and use the resolved fork's `Pullback` handlers instead of a monolithic `Reduce` switch.
- Keep `Containers/macOS` limited to bundle resources and its entry shim. Keep Application a forwarding bridge. AppFeature owns application composition.
- Use role-based local packages and neutral module names. Create packages only with a concrete target and README. The supported platform is macOS 27 or later.
- Use the Composable Architecture for browser feature state and effects. App-owned packages require Swift 6.4.
- Chromium is the intended renderer. Do not substitute WebKit. Read [Packages/engine/README.md](../Packages/engine/README.md) before adding engine integration.
- Change `project.yml` and `.xcodegen` inputs, then regenerate. Generated Xcode artifacts are ignored and are not authoritative.
- Keep repeatable operations behind Make and local scripts. CI calls Make. Run `make test-all` for infrastructure changes.
- Keep every package, target, and container README current. Tests belong with their owning package.
- When an MCP tool, argument, error or grant changes, update the `arx-browser` agent skill in the same change: `Packages/services/Sources/AgentToolsClient/Skill/arx-browser/SKILL.md`, its compiled copy `AgentSkillText.swift` (bump `version` in both and in `AgentSkill.version`), and the compact server instructions in `BrowserMCPServer/AutomationInstructions.swift`. Check the site skills in `Skill/arx-*/SKILL.md` too (with `AgentSiteSkillText.swift` and each skill's own `version`).
- Invariant tests enforce the rules that tie the menu bar, the command bar and Settings › Shortcuts together (DEV-1014). Each lives in `Packages/features/Tests/IntegrationFeatureTests/MenuCommandInvariantTests.swift`; when one fails, fix the code, not the test's exception lists.
  - Every menu item is a `BrowserCommand` or one of AppKit's standard actions: `everyMenuItemIsACommandOrAStandardAction`. A new Arx menu item becomes a command, which puts it in the command bar and Settings › Shortcuts.
  - Every menu command is in the command bar wherever the menu bar enables it: `everyMenuCommandIsInTheCommandBar` and `theWindowsCommandBarListsTheCommandsItsMenuBarEnables`.
  - The menu and the command bar show a command's current shortcut: `everyMenuCommandShowsItsShortcutInTheMenuAndTheCommandBar`.
  - Every menu key is in the shortcut catalog: a command's binding, a reserved key, or a text menu key that gives way to a binding (`KeyboardShortcut.textMenuKeys`), and no two items share one: `everyMenuKeyIsInTheShortcutCatalog`, `textMenuKeysGiveWayToABoundCommand`.
  - Every default shortcut is valid, unreserved, takes no text menu item's keys and belongs to one command: `everyDefaultShortcutIsValidUnreservedAndUnique`.
  - Every command can be rebound in Settings › Shortcuts: `everyCommandIsInSettingsShortcuts`.
- Classify every Settings row for agents (DEV-1023). A new anchor, page or panel in `SettingsFeature` doesn't build until `SettingsRowIndex.swift` says who may change it: `agent` (with the preference keys or the `browser_settings` section that edits it), `user` (the person's own decision: privacy, security, passwords, accounts, AI, permissions, system and resource limits) or `ui` (sets nothing). Plain switches and choices are `agent`, added to `AutomationPreferenceKey`; `SettingsRowAccessTests` fails when an agent key isn't reached by a row.
- Register every `ARX_*` feature flag in BrowserCore's `FeatureFlag` (DEV-1115), with whether it needs a relaunch and whether it's risky, and read it through the registry. A flag is on by default (DEV-1143); one that must stay off goes in `FeatureFlag.offByDefault`, empty for the beta. An engine flag's default lives in `engine_bridge.mm` too, and a test keeps the two in step. Settings › Advanced › Feature Flags lists it from there. `FeatureFlagRegistryTests` scans the sources and fails for a flag that isn't registered; a variable that isn't a feature flag goes in its short `notFeatureFlags` list.
- Keep the user manual current. When a change adds, removes or alters something a user can see or do (a feature, setting, shortcut, menu item, MCP tool or default), update the user manual in the sibling repository `../arx-browser-manual` in the same piece of work. Changes with nothing user-visible (refactors, tests, tooling) need no update.
  - Follow that repository's `README.md`. Write only what Arx does today. Use `status: planned` or `::planned` for anything that isn't shipped yet, and keep `content/8.help/2.planned.md` in step with it. Add a `::recording` placeholder with a shot list when a page needs a clip. Run `pnpm typecheck` there.
  - It's a separate Git repository, and pushing its `main` deploys the live manual on Railway. Commit there locally with explicit-path staging, and never push without the user's go-ahead.
  - Name the manual commit, or "no manual change needed", in the pull request description.
- Core, services, design-system, and features are browser-specific. Shared forks and wrappers live in `Forks/`; keep them as they are. Never commit credentials or signing settings.
- Arx is registered in Apple Developer and App Store Connect with bundle ID `dev.capturecontext.arx`. Debug builds (`make run-dev`, the smokes, Xcode) are Arx Dev, `dev.capturecontext.arx.dev`, with their own data folder, defaults and Keychain item (DEV-1013, DEVELOPMENT.md › Arx Dev). `make run` builds Debug as Arx on the installed Arx's data, and `make run-preview` as Arx Preview with a data folder and Keychain item of its own. Use `ArxEdition` instead of naming any bundle ID or folder in app code. Local `.env` supplies `DEVELOPMENT_TEAM`. Keep secrets out of committed files and tool output.
- Arx's own code is licensed under GPL-3.0 (root `LICENSE`, the unmodified text; decided 21 November, DEV-1279). It embeds Helium (GPL-3.0) and ungoogled-chromium code (BSD-3-Clause), whose texts are in `Packages/engine/Licenses/`. Pull requests aren't accepted yet; when they open, contributors sign a CLA so Arx stays GPL while its maintainer can also license his own code under other terms (`CONTRIBUTING.md`). A new dependency needs a GPL-3.0-compatible licence. `GOVERNANCE.md` says who decides what, `CODE_OF_CONDUCT.md` how people are expected to behave, and `.github/labels.yml` is the one list of the public repository's labels (the Labels workflow syncs it; add a label there, not by hand). The name "Arx", the icon and the wordmark are reserved (`TRADEMARKS.md`, decided 21 November): forks that distribute builds rebrand. Keep `THIRD_PARTY_NOTICES.md` current when adding dependencies and run `make credits`. `README.md` is the public introduction and `DEVELOPMENT.md` the developer reference. Unsigned CI builds must work without `.env` or a signing team.

## Proof for a change

Prove every change, at the lowest of these levels that fits it:

1. **None.** Docs, copy, colors, spacing and constants. Reading the diff is the proof.
2. **Compile.** A small code change with nothing to look at. Build it and run the suites around it: `swift test --filter` on the owning package, and `make check`. Infrastructure changes still run `make test-all`.
3. **Before and after.** A reported bug, anything a user can see, motion, performance, and anything a release note or the user manual will claim. Show the broken state and the fixed one: screenshots, a recording, or numbers from the same command run on both (`make benchmark` for memory and speed).

- Never call a bug fixed without running the scenario that showed it. Name the root cause, and add a test that fails on `main` and passes on the branch wherever a test can reach the bug.
- Engine changes (`Packages/engine/Native`, the overlays): `make engine-check` is compile proof for the native bridge only. Behavior needs a built engine and the smoke that covers it (`make app-smoke`, `make headless-smoke` and so on). Memory and speed claims compare `make benchmark` on the old engine and the new one with `make perf-gate ARGS='--compare …'`. Until the engine is built, the change has compile proof and nothing more; say so.
- Smokes that need the screen, focus or a signed build can't always run during the day, because they fight over the screen or need nobody at the Mac. Cover the logic with a test or `make headless-smoke`, and name the smoke still owed, with its exact command, as pending. Attach its result once it has run. A smoke that hasn't run proves nothing.
- The pull request description that finishes a change starts with `Proof: none`, `Proof: compile` or `Proof: before and after`, lists the commands and tests that ran, and attaches the evidence: screenshots and recordings as uploads, numbers inline. Pending smokes are listed there too.
