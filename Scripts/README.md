# Scripts

The signed application fixture requires both Archive markers: ordered selected-tab close and confirmed cross-profile restoration. Its isolated feature store has no persistence parent; fresh native profiles and cookie/storage sentinels verify destination identity without modifying the application workspace. Missing markers fail even when the process exits successfully.

The scripts use Python's standard library and separate generation entry points, tool wrappers, and shared utilities.

- `engine/` owns pinned Helium checkouts, build tools, source overlays, and the native framework build. Its public commands are `engine-tools`, `engine-checkout`, `engine-prepare`, `engine-overlay-report`, `engine-upstream`, `engine-bump`, `engine-anchor-check`, `engine-check`, `engine-build`, `engine-cache`, `engine-restore`, `engine-host`, and `engine-smoke`. Archive export and restore live in focused `engine/archive.py` and `engine/cache.py` modules. Engine builds run separately from the fast Swift/app checks.
- `app_smoke.py` launches the real app with a local HTTP fixture and temporary profile after requiring a complete engine artifact.
- `core/little_peek_smoke.py` prepares a loopback page with a fresh in-document nonce and requires separate exact dismissal/promotion markers. The app helper compares actual native view and history identities across the Little-to-normal handoff. Post-exit history rejects the dismissed preview and the pre-promotion visit. This prepared fixture must run in the signed app before claiming native acceptance; it does not automate before-unload cancellation or accessibility checks.
- `core/app_link_smoke.py` (DEV-857) prepares `app-link.html`, which redirects itself without a click (`location.replace`, so Chrome marks it a client redirect) to an unregistered `arx-smoke-app-link://` link carrying `;`, `$(…)` and quotes. The app smoke's `app-link` phase (`AppLinkSmoke`) gives that scheme a handler whose script records `$1`, confirms Arx's prompt in Little Arx and requires `ARX_APP_LINK_SMOKE_SUCCESS`: the recorded argument equals the link, the page stayed and nothing launched. It needs an ABI50 engine. For DEV-862, `prepare_app` builds a fixture applet with `osacompile`, in a temporary folder on the startup disk so a checkout on an external drive doesn't trigger macOS's removable-volume prompt on every run, that records the link it's opened with and quits, and `app-link-app.html` redirects to the unregistered `arx-smoke-app-pick://`. `AppLinkSmoke.runChosenApp` gives that scheme a handler that opens it with the applet, chosen by path, and requires `ARX_APP_LINK_APP_SMOKE_SUCCESS`: the applet recorded the link, and a handler pointing at an app that isn't there makes the prompt say so and open nothing. For DEV-1259, `prepare_open_app` builds a second applet that declares `arx-smoke-app-open` and registers it with Launch Services for the run (`lsregister -f`, undone by `unregister_open_app`), and `app-link-open.html` redirects to that scheme, which no handler takes. `AppLinkSmoke.runUnconfigured` requires `ARX_APP_LINK_OPEN_SMOKE_SUCCESS`: Arx's prompt (never Chrome's dialog) names the applet, Open hands it the link, the page stays and nothing is saved.
- The application runner creates an owner-only profile and an exclusive `.arx-mcp-smoke` sentinel for its DEBUG native MCP fixture. The fixture uses static loopback pages and the bundled helper; `ARX_MCP_NATIVE_SMOKE_SUCCESS` is required alongside the existing feature and allocator evidence. An existing profile is never adopted by this setup.
- `preview.py` builds, opens, and tests AppUIPreview through `build-preview`, `preview`, and `test-preview`. Its build requires no Chromium artifact. `make tour-videos` exports the onboarding tour's demos for the website: it runs only the preview's `TourVideoExportTests`, which render each demo offscreen and write `build/tour-videos/<demo>-light.mp4` and `<demo>-dark.mp4` (H.264, 1280 × 720, 30 fps, one 8-second loop each; `peek`, `split-view`, `command-bar`, `little-arx`), then lists the files. The log is `build/logs/tour-videos.log`. It needs no Chromium, display interaction or signing.
- `make_sounds.py` (DEV-1256) synthesises Arx's three interface sounds with the standard library and writes `capture.wav`, `done.wav` and `could-not.wav` into SoundFeedbackClient's resources, byte for byte the same on every run: `python3 Scripts/make_sounds.py [directory]`.
- `tasks.py` only dispatches public Make commands, prints help, and returns exit codes.
- `resolve.py` checks the toolchain, initializes missing forks, and resolves package dependencies.
- `check.py` validates manifests, README coverage, bundle metadata, and generation determinism.
- `test.py` runs automation tests and discovers Swift package test targets.
- `style.py` (`make style`, DEV-1280) runs SwiftFormat and SwiftLint in lint mode and the StyleCheck tool from `Packages/tools` on one explicit list of Arx's own Swift files (SwiftLint on its production part), never a directory to walk, and prints their findings as warnings, or as GitHub annotations when `GITHUB_ACTIONS` is true. It exits 0 whatever they find, fails only when a tool crashes, and reports a tool that isn't installed as skipped.
- `localization.py` (DEV-1291) exports the strings a language still needs as JSON chunks (`make localization-export`), validates translated chunks and merges them into the string catalogs in their own formatting (`make localization-import`, `--validate-only` writes nothing), and reports missing, stale and suspicious translations (`make localization-check`, GitHub annotations with `--github`). Only languages `Localization/languages.json` ships fail it, and `make check` runs that part. The rules are in `.agents/LOCALIZATION.md`.
- `build_package.py` builds the root package and selected infrastructure products; `build_app.py` builds unsigned CI or stably signed local apps using the lockfile. `signing.py` selects a valid team development identity and the provisioning profile made for it, and exposes read-only Fastlane certificate and profile restore. `cloudkit_probe.py` (`make cloudkit-probe`) checks that a signed build reaches its iCloud container.
- `test_all.py` composes checks, tests, package/app builds, and preview tests in order, stopping at the first failure.
- `project.py` composes project/workspace generation and opens the workspace when requested.
- `generate_xcodeproj.py` configures project generation through `tools/xcodegen.py`.
- `generate_xcworkspace.py` selects the workspace references, including `.` as a normal top-level entry, and delegates XML generation to `tools/xcworkspace.py`.
- `core/paths.py` resolves the repository root and discovers app-owned packages.
- `core/process.py` owns subprocess execution, logs, and failure exit codes.
- `core/smoke.py` retains runtime logs and failure summaries, including setup failures and process timeouts.
- `core/download_fixture.py` serves deterministic attachments, collisions, throttled transfers and truncated responses. `core/download_smoke.py` seeds the disposable download destination and expected hashes, then checks ordinary metadata and Chromium download history after app exit. The app-side DownloadSmoke runner uses unique per-tab URLs and requires `ARX_DOWNLOAD_SMOKE_SUCCESS` plus `ARX_PRIVATE_DOWNLOAD_REOPEN_SMOKE_SUCCESS`: real bytes, cancellation, interruption, private page-close continuation, fresh same-key storage during an active transfer, and independent old/new transfer controls.
- `tab_unload_smoke.py` (`make tab-unload-smoke`, DEV-873) serves three loopback pages with `no-store` and counts requests, launches the signed Debug app with `ARX_TAB_UNLOAD_SMOKE`, and requires `ARX_TAB_UNLOAD_SMOKE_SUCCESS` from the app's `TabUnloadSmoke` plus a second request for the unloaded page: proof it loaded again when selected. Its DEV-879 phase serves a page that opens a WebSocket to the fixture server (a minimal RFC 6455 endpoint sending a message every 5 s); the app pushes it out of the five most recent tabs, waits 400 s (Chromium freezes a hidden page 5 minutes after it was last visible, and the page notices a closed socket at its next periodic unfreeze), requires its title unchanged and the engine to refuse unloading it, and the runner requires one connection, no reconnect and no `/closed` or `/frozen` report from the page. It takes about 7 minutes longer; `ARX_SPARE_LIVE_CONNECTIONS=off` in the environment reproduces the disconnect.
- `test_runtime.py` runs the signed engine and app smoke checks in order. It requires an interactive macOS session and configured development signing; it is separate from unsigned `test-all`.
- `tools/xcodebuild.py` resolves the app path from Xcode build settings and rejects missing products. Builds query settings with the same configuration and overrides used to compile; launch and smoke commands use the returned path.
- `tools/swift.py` supplies shared SwiftPM command options and toolchain validation; `tools/git.py` initializes missing submodules while preserving divergent revisions.

Make runs `mise exec -- python3 -m Scripts.tasks`. `make project` and `make workspace` still regenerate both artifacts. For a single generation step, run `mise exec -- python3 -m Scripts.generate_xcodeproj` or `mise exec -- python3 -m Scripts.generate_xcworkspace` from the repository root. Mise supplies the pinned tools and optional local environment. Workspace regeneration preserves shared and user settings beside its generated contents file.

Each operation module also supports direct execution for debugging, for example `mise exec -- python3 -m Scripts.check`. Keep reusable tool behavior in `tools/` and shared process/path utilities in `core/`; add new operations as focused modules instead of expanding the dispatcher.

XcodeGen reads `project.yml` and generates the container's Info.plist and entitlements from `.xcodegen/macOS.yml`. Workspace generation includes the project, the root package as a top-level `group:.` entry, and each local package directly under `Packages/`. The generator check compares project, scheme, workspace, plist, and entitlement hashes across two runs. Package checks use SwiftPM's evaluated manifest and target descriptions. SwiftPM commands share `.build` across app-owned package roots and use the local `build/swift-security` fingerprint store. `make submodules` initializes missing pinned checkouts and refuses to reset divergent revisions. `make check-toolchain` requires Swift 6.4.

`make test` runs [automation tests](tests/README.md), then each package with declared Swift test targets. `make test-all` runs sequentially to avoid concurrent project generation and build-state mutations. The package build includes wrappers not linked by the app shell, including database, test-support, URL-routing products, and package-resources-cli. Xcode builds treat app Swift warnings as errors. Build logs are retained under `build/logs/` on success and failure.

Set `BUILD_JOBS` to a positive integer to bound Swift package and Xcode build/test concurrency, including `test-preview`, when sharing the machine with an engine build. App and preview commands share validation and pass the same `-jobs` option. Xcode uses its default concurrency when the variable is absent.

CI calls these same commands. Keep future build, test-selection, engine-packaging, and release-validation logic here. Add focused modules as needed; do not duplicate commands in workflow YAML.

`make engine-fetch engine-validate` restores the exact architecture's prebuilt engine and checks its runtime layout. `make build-app-runtime` requires the engine in an unsigned app and validates the final bundle. CI runs these commands alongside `test-all` without signing configuration; a separate manual runtime job can run `test-runtime` on an explicitly configured signing/GUI runner. See [engine cache setup](../Artifacts/Engine/README.md). Runtime logs live in `build/logs/runtime/`, alongside the retained build logs.

`make build-app-signed` and `make run` use Apple Development signing. Native smoke tests and the separate engine host also require a matching identity. Unsigned Arx builds use `build/UnsignedDerivedData` and explicitly override `SYMROOT`, `OBJROOT`, and `CONFIGURATION_BUILD_DIR`, preventing custom Xcode output preferences from replacing the signed app. Products remain configuration/platform-specific under that directory. Signed and preview output settings stay unchanged; build-settings queries receive exactly the same overrides as the build.

### Provisioning profiles and iCloud

The app's entitlements include iCloud (CloudKit) for `iCloud.dev.capturecontext.arx` and push notifications, so every signed app needs a provisioning profile; the Chromium helpers and `ArxMCP` don't get these entitlements or a profile. `signing.profile()` picks the installed Match profile by name: "match Development <bundle ID> macos" for the Apple Development identity and "match Direct dev.capturecontext.arx macos" for Developer ID. The bundle ID is the configuration's (`signing.bundle_id`): Arx Dev's `dev.capturecontext.arx.dev` for Debug, `dev.capturecontext.arx` otherwise. It also checks the team, the app identifier, the expiry, the kind of profile, that the profile grants the iCloud container, CloudKit and the iCloud and push environments the build asks for (a profile made before those capabilities were on doesn't), and that it includes the selected certificate, then takes the newest match. Profiles come from `~/Library/Developer/Xcode/UserData/Provisioning Profiles/` (where `make signing-setup` and `make release-signing-setup` put them) or `~/Library/MobileDevice/Provisioning Profiles/`; `ARX_DEVELOPMENT_PROFILE` and `ARX_DEVELOPER_ID_PROFILE` name a file instead; a development override outside Xcode's directory is copied there as `<UUID>.provisionprofile` before the build, since Xcode finds profiles only there; so is a profile found only in the legacy MobileDevice directory. `make signing-check` and `make release-signing-check` print the identity and profile UUID. A missing profile stops the build before Xcode runs, naming the restore command and the writing lane (see [fastlane/README.md](../fastlane/README.md)).

Signed builds pass `ARX_PROVISIONING_PROFILE` (the profile's UUID), `ARX_ICLOUD_ENVIRONMENT=Development` and `ARX_APS_ENVIRONMENT=development` to Xcode. Only the app target reads them: Xcode embeds the profile as `Contents/embedded.provisionprofile` and fills the environments into the generated entitlements before signing. The build fails if the signed app has no embedded profile. Unsigned builds (`CODE_SIGNING_ALLOWED=NO`) need no profile, identity or `.env`.

Until Arx Dev's profile exists (DEV-1013), a signed Debug build prints a notice and is signed without a profile: `ARX_PROVISIONING_PROFILE` is empty, and after generating the project the build drops iCloud and push from the generated `Containers/macOS/Arx.entitlements`, so macOS still starts it. (XcodeGen always points the app target at that file; the next build or `make project` writes it whole again.) `build_app.main(require_profile=True)` refuses that instead. `make run-dev` quits only the running Arx Dev, so an installed Arx stays open. `make run` and `make run-preview` build Debug as Arx (`build_app.RUN_VARIANTS`, DEVELOPMENT.md › Run variants): `make run` quits every Arx first, since it opens the installed Arx's data, and `make run-preview` quits only copies running from `build/DerivedData`, with a data folder and Keychain item of its own.

`make cloudkit-probe` builds the signed Debug app, Arx Dev (always Debug, whatever `CONFIGURATION` says), which needs Arx Dev's profile, checks the embedded profile and the container entitlement, and runs `Arx --arx-cloudkit-probe`. The Debug-only `CloudKitProbe` asks `CKContainer(identifier: "iCloud.dev.capturecontext.arx").accountStatus`, prints `ARX_CLOUDKIT_PROBE … result=returned status=<status>` and exits before the engine starts. Any returned status passes, including `noAccount`; an error, a timeout, or a process the system kills for a profile mismatch fails. `ARGS='--app path/to/Arx.app'` probes an existing signed Debug build.

`make cloudkit-schema` (`cloudkit_schema.py`, DEV-1209) writes `CloudKit/arx.ckdb` from the synced tables by running WorkspaceSync's `CloudKitSchemaTests` in record mode, keeping the record types and fields the file had. `make cloudkit-schema ARGS='--compare production'` (or `development`) exports that environment's schema with `xcrun cktool export-schema` and fails listing the record types and fields it lacks; it needs `DEVELOPMENT_TEAM` and a management token from `xcrun cktool save-token`. `test_cloudkit_schema` covers the parsing and the comparison with a stand-in `cktool`. See DEVELOPMENT.md › iCloud schema.

## Benchmark

`make benchmark` (`benchmark.py`, DEV-682) measures Arx, and Chrome when `/Applications/Google Chrome.app` exists, on this Mac. It builds the signed app in Release into `build/BenchmarkDerivedData`, apart from `make run`'s `build/DerivedData` so a running build is never replaced (a full build the first time; `--app PATH` measures an existing build instead) and writes `build/benchmarks/<UTC time>/results.json` and `results.md`: one table with a column per browser, plus the Mac model, chip, memory, macOS build, power source, Git commit, app version and engine (Chromium) version. A full run takes about 29 minutes, most of it the native step's tabs and its freeze wait (`--skip-native` leaves them out). Close other heavy apps first and keep the Mac on power; the load average at the start is recorded. `--quick` runs every step briefly (one warm launch, 5 s idle windows, 3 tabs, 3 switches, a 20 s freeze wait, no Chrome) to check that the harness works on a branch; its report says it is not a baseline. When a browser stops early, the report keeps every number measured before that and names the step, and `make benchmark` exits with status 1.

Each browser gets fresh storage under `~/Library/Caches/arx-benchmark/`, removed afterwards unless `--keep`. Pages come from a loopback fixture (`core/benchmark_fixture.py`); no real site and no user profile is touched. Arx is started from its executable with `ARX_ENGINE_PROFILE` and quit through `NSRunningApplication` for its own PID, so another running Arx is never asked to quit or open anything. Chrome gets `--user-data-dir`, `--use-mock-keychain` and `--password-store=basic`.

What it measures:

- **Launch:** from `exec` until the start page has loaded, run its script and painted twice, then reported back to the fixture. The first launch is on a new profile; warm launches (`--launches`, default 5) reuse it and the table shows the median. macOS's file cache can't be dropped without root, so there is no true cold launch. Arx also marks its launch with signposts (subsystem `dev.capturecontext.arx`, category `Launch`): `ProcessStart` when its own code starts, `WindowShown` when the main window is first on screen, and `FirstPagePainted` from the engine when the first page paints. The script reads them with a filtered `log stream --signpost` that runs only during each launch; their `machTimestamp` is Mach continuous time, which keeps counting while the Mac sleeps, unlike the Mach absolute time `time.monotonic()` reads, so the script reads the continuous clock at `exec` too and each mark is an offset from that (DEV-939). That is far cheaper than recording an Instruments trace (`xctrace`), and unlike `log show` it doesn't depend on signposts being persisted. A build without a mark shows a dash.
- **Memory:** physical footprint (Activity Monitor's Memory column) summed over the browser and every descendant process, from `proc_pid_rusage`.
- **CPU, wakeups and disk writes:** the change in those counters over an idle window (`--idle`, default 30 s) after a 10 s settle. `powermetrics` needs root, so CPU time and idle wakeups stand in for energy.
- **Per process type:** every window above is also split by what each process is, read from its command line (`core/process_metrics.py`): `browser` (the app itself), `gpu` (`--type=gpu-process`), `network`, `storage` and `audio` (`--type=utility` with those services), `renderer`, `extension` (renderers started with `--extension-process`, which host extension background pages) and other utilities by service name. A descendant that isn't a Chromium helper is `other`. The report's "cost per process type" table separates, say, a browser-side timer from busy pages.
- **Processes at 1 tab:** after the first launch, the start page keeps its renderer busy for 400 ms, so the listing can name it. Other renderers are extension renderers or, without a page, Chromium's spare renderer. The profile's extensions are listed from its preferences, with whether each has a background page, so two extension renderers can be matched to what's installed.
- **Warm-up:** before the tab steps, the new headless profile runs for 180 s from opening one fixture tab, which is then sent to the Tab Archive. Its first page is when Arx hands uBlock its settings, about a minute in Chromium's component updater and uBlock's first list update download and store their data, and about 150 s in uBlock saves its selfie (below, under Persistence). The tab steps then measure steady state. The report shows how long the warm-up took; `--no-warmup` skips it, and the report says so. `--quick` warms up for 5 s.
- **Tabs:** Arx opens 10, 50 and 100 tabs (`--tabs`) in the background through the bundled MCP helper of `Arx --headless --profile …`, each on its own `t<N>.localhost` site with a light one-second timer. After all report their `load` event (background tabs may not paint until shown), it records memory, renderer count and idle CPU (and the median `openTab` round trip for the tabs opened in that step), then times 30 `selectTab` calls (`--switches`): the MCP receipt and, when the page reports `visibilitychange`, until it's visible. Only switches to a tab that was hidden report the second number. Headless Arx has the windowed app's engine and workspace but a transparent window, so it leaves out drawing to the screen; as an unattended run it also starts the engine with `--disable-renderer-backgrounding` and `--disable-backgrounding-occluded-windows`, and these tabs are never shown, so nothing here is throttled. Arx's pages start hidden (DEV-936), so Chromium's tab freezing still freezes a loaded page once five newer tabs are open; it's unfrozen for five seconds each minute. These are agent timings: each `openTab` first reads one inventory page for the space's current revision, so "openTab via MCP" (`open_command_ms`) grows with the page's size up to 100 items, and "openTab via MCP, command alone" (`open_receipt_ms`, DEV-934) times only `browser_command`. The native step below has what a person feels. Chrome opens the same pages from its command line.
- **Persistence:** bytes written to disk by all processes in each idle window, and how often `arx-workspace.json` was rewritten while the tabs opened (polled every 50 ms). The headless profile is new, so a minute or so after it starts (inside the warm-up; with `--no-warmup`, around the 50-tab step's settle and idle window) Chromium's component updater downloads its security components (DEV-874: the CRLSet, PKI metadata and others, about 20 MB into `component_crx_cache`, `CertificateRevocation` and `PKIMetadata`) and uBlock's updater moves to upstream's list registry and fetches its lists (DEV-884: a few MB into its extension storage and IndexedDB). Both are once per profile; Arx's own files barely move. Then uBlock saves its selfie, its compiled filtering engine, 53 s after the last change to its lists: about 35 MB to both its `chrome.storage.local` (`Local Extension Settings`) and its IndexedDB, which LevelDB then rewrites while compacting, so the browser process writes 150 to 170 MB within a few seconds, about 150 s after the profile started. The 180 s warm-up covers it. With the 90 s warm-up the harness had before, it landed in the second tab step's idle window (the 20-tab one in `--tabs 1,20`) on Chromium 156 and 157 alike; Arx's workspace, navigation history, browsing history, the component cache and the HTTP cache wrote nothing in that window (DEV-682, 2026-11-14). uBlock saves the selfie again after every later list update: relaunched 5 minutes later, the same profile diff-updated EasyList, EasyPrivacy and uBlock's filters 37 s in and wrote about 100 MB at 92 s. Without the warm-up, which of them lands inside the idle window shifts by seconds from run to run (12 and 24 MB in two runs of the same build), so a window's disk writes are only comparable between runs where the same first-run work landed in it.
- **Native tab commands (windowed):** windowed Arx on its own throwaway profile, started with `ARX_BENCHMARK_DRIVER=1` (AppFeature's `BenchmarkDriver`). It opens each tab as a person would: ⌘T, the address inserted into the command bar's field as a paste would, and Return, timed until the new page reports `ready`; ⌘T until the empty field has focus is reported too. At each tab count it then switches with ⌃Tab (`--switches` times; the run sets `ARX_RECENT_TAB_SWITCHER=0`, so ⌃Tab is Next Tab: the recent-tab switcher of DEV-544 picks when ⌃ is let go, which synthesized keys never do), timed until the newly selected page reports `shown`: visible, then painted twice. A switch that shows no page within 3 s is counted in the table as over 3 s rather than left out, and the step fails if none does. Keys are posted to Arx's own event queue, so they pass its key monitor, menus and command routing like real keys, without the WindowServer or an Accessibility permission. Arx must be frontmost with its window visible: leave the Mac alone during this step. Compare these with the MCP timings above, which also pay for the automation inventory. An app built before DEV-939 has no driver, and the step stops with that reason; the other steps' numbers are kept.
- **Freezing:** every native tab was shown once, so Chromium may freeze the hidden ones: by default 5 minutes after a tab was last visible, outside the 5 most recently used, waking them for 5 s each minute. The step waits `--freeze-wait` (default 390 s) and counts pages whose last Page Lifecycle beacon was `freeze` (sent with `navigator.sendBeacon`, which survives the freeze), with memory and idle CPU per process type over the wait's last idle window. `--live-connections F` makes that fraction of the tabs (spread evenly, so 0.2 makes tabs 5, 10, 15 … live) keep a WebSocket open to the fixture server, which sends a short message every 5 s, as a chat or live dashboard does. The step then also counts the live pages that are frozen and the ones whose connection is still open (the server notices a closed one at its next message). Arx spares such pages from freezing (DEV-879); run once as is and once with `ARX_SPARE_LIVE_CONNECTIONS=off` in the environment to see what that costs and keeps. The report names the engine feature flags set in the environment (`ARX_SPARE_LIVE_CONNECTIONS`, `ARX_SPARE_RENDERER`, `ARX_IDLE_TRIM` and the others `engine_bridge.mm` reads).
- **Fixture server:** tabs that load together, and a relaunch that fetches the icons of 100 restored tabs, reach the fixture in bursts. It listens with a backlog of 128 connections (macOS's limit) instead of Python's 5: macOS resets a loopback connection while the backlog is full, which once made a page that loaded look as if it never had, and made the large-workspace restore miss its start page. A page also sends a beacon that failed again, up to four times.
- **Fixture hosts:** by default each tab is its own `t<N>.localhost` site. Chromium never lets same-site tabs share a renderer on localhost or IP hosts (`render_frame_host_manager.cc`), so that's the worst case for memory per tab. `--fixture-hosts same-site` serves them from `t<N>.arx-bench.test`, one site, as many tabs of one real site are: Arx is started with `ARX_BENCHMARK_FIXTURE_HOSTS=1`, which makes its engine map only that reserved `.test` name to loopback (`--host-resolver-rules`), and Chrome gets the same switch. Run it once each way to see renderer sharing.
- **Large workspace restore:** the headless run's tabs are added to the windowed profile's `arx-workspace.json` (in place: a copied profile fails Arx's installation-identity check), then windowed Arx is relaunched and timed until its selected start page is usable, followed by idle memory and CPU with the restored tabs. Arx restores background tabs unloaded, so this shows the cost of a large sidebar rather than of 100 live pages.

Not automated: typing in the command bar and space switching, frame drops while animating the sidebar (scrolling it is `make sidebar-scroll`, below), video playback energy, and Speedometer, JetStream and MotionMark (they need a visible window and a person to read the score). Run them by hand:

1. Speedometer 3: open `https://browserbench.org/Speedometer3.1/`, press Start Test, note the score. JetStream: `https://browserbench.org/JetStream/`. MotionMark: `https://browserbench.org/MotionMark1.3.1/`. Use one window, nothing else open, on power.
2. Command bar: record the screen at 120 fps (QuickTime) while pressing the shortcut, and count frames from the key press to the bar and to the first results.

### Other browsers

Both keep their profile in the user's own Library, so the script doesn't drive them. To compare by hand, on the same Mac:

1. Run `make benchmark ARGS=--serve`. It serves the same pages, prints the start page and tab URLs, and prints the time each page reports it is usable.
2. Quit the browser, then run `python3 -c "import datetime; print(datetime.datetime.now().strftime('%H:%M:%S.%f')[:-3])"; open -a Safari '<start URL>'` (or another browser's `-a` name). Launch time is the gap between that time and the `ready` line. Run it once after a restart of the browser for a first launch and five more times for warm launches.
3. Open the 10, 50 and 100 tab URLs (`t1.localhost` … `t100.localhost`), wait 10 s, and read the browser's processes in Activity Monitor (Memory and Energy Impact, View › All Processes, Hierarchically). Safari's web content processes are listed as `Safari Web Content`.
4. Run the browserbench pages above in each browser.

## Sidebar scroll

`make sidebar-scroll` (`sidebar_scroll.py`, DEV-1238) counts the frames Arx drops while its sidebar scrolls in the real window, where `SidebarScrollCostTests` (DEV-1235) only times the bare list off screen. For each workspace size (`--tabs`, default 30, 150 and 400) it starts windowed Arx on fresh throwaway storage under `~/Library/Caches/arx-benchmark/`, with that many restored loopback fixture tabs in its one space (not loaded until selected), after a first launch that warms the new profile up for `--warmup` seconds (60). After `--settle` seconds (30), a driver sets Arx's window to 1280 by 800 points through the Accessibility API, so every run and build scrolls the same list in the same window, and scrolls the sidebar from outside the app, so a build of any commit can be measured with no hook in it:

- **Scrolling:** phased trackpad scroll events (`sidebar_scroll_driver.swift`, compiled with `swiftc` into `build/sidebar-scroll/`), one a frame on the screen's display link at `--speed` points a second (840), down the list and back up in legs. Each leg is a gesture with a short glide after the fingers lift, and the list moves on every frame: a gesture's first event carries its first move, the lift shares a frame with the glide's start and the glide's end with the next gesture's beginning, so every frame owes a new picture. Each leg is three fifths of what the list can scroll (36-point rows, 1,500 points at most), so it turns back well before the list could reach its end: a list stopped at its end shows no new frames, which would count as drops. A size whose list can't scroll 120 points is an error; `--leg` sets the length instead, and legs come in pairs so each run starts where the last one began.
- **Pointer:** `inside` rests the cursor over the sidebar, so rows pass under it and their hover is part of the cost; `outside` rests it over the page. The events go to the sidebar either way: they carry Arx's window and a point in the sidebar (its default 286-point width).
- **Frames:** a ScreenCaptureKit stream of the sidebar notes when each new frame of it reaches the screen, so the window server's work (the blurred edges over the list) counts too. A gap over 1.5 refresh intervals is a dropped frame, and so is a wait that long after the last one; `missed` counts the intervals those gaps held beyond one. The wait for the first frame is the input's way to the screen, so `results.json` reports it (`first_frame_ms`) without counting it. The worst gap and the 95th percentile are reported too. A run whose capture stopped is an error, not a result.
- **CPU:** Arx's main thread (its lowest thread ID) and whole process, from `proc_pidinfo`, over the scroll: main-thread CPU as a share of the time and per frame.

Each size and pointer position runs `--runs` times (3, alternating which goes first); the table shows medians and `build/sidebar-scroll/<UTC time>/results.json` keeps every run, with `results.txt` the table. A run is left out of the medians, and counted as invalid, when Arx lost the front or the driver's own display link stalled past two and a half intervals or missed more than one interval in a hundred: while it stalls no events go out, so the missing frames aren't Arx's.

It needs the screen: run it with nobody at the Mac and nothing else running, after the window smokes rather than beside them. The app that runs the command (Terminal, or the agent's host) needs Accessibility and Screen Recording in System Settings › Privacy & Security; the run checks both first and stops with exit status 3 without them.

To compare two commits, build each and run the harness from the newer checkout, which measures any older build:

```bash
make sidebar-scroll ARGS='--ref d9354f34^1'
make sidebar-scroll
make sidebar-scroll ARGS='--compare build/sidebar-scroll/<before>/results.json build/sidebar-scroll/<after>/results.json'
```

`--ref` builds that commit in a detached worktree under `build/sidebar-scroll/ref-<commit>` with its own build scripts (signed Release, as `make benchmark` builds), sharing this checkout's engine and `.env`; a commit whose build fails there can be built by hand and measured with `--app`; `--app PATH` measures an existing build. `--self-test` checks the driver's frame statistics, scroll script and CPU counters and this script's options and report without the screen or Arx; `make test` runs the same unit tests (`test_sidebar_scroll`). The driver's `clock-check` prints the display link's own pacing on this Mac, which is worth a look before trusting a run on a busy one. Its numbers aren't in the perf gate yet: they go there once a few quiet runs show how much they vary.

## Load ladder

`make load-ladder` (`load_ladder.py`, DEV-1027) finds how many tabs Arx holds on this Mac before the Mac feels it, and names the limit that broke first. It climbs two ladders in `Arx --headless`, each on fresh throwaway storage that first runs with one tab for `--warmup` seconds (180, as the benchmark's warm-up: Chromium's component updater and uBlock's list update write their data in the first minutes, and uBlock compiles its lists after every launch until it has saved them), under `~/Library/Caches/arx-benchmark/` with the benchmark's loopback fixture pages (each tab its own `t<N>.localhost` site), and builds the signed app in Release as `make benchmark` does (`--app PATH` measures an existing build).

- **Awake** (1, 10, 20, 40, 60, 80, 100, 150, 200 tabs): tabs are opened through the MCP helper behind the selected one, as ⌘-click opens them, and must all report `loaded`.
- **Unloaded** (100, 250, 500, 1,000, 2,000, 4,000 tabs): the tabs are written into a stopped profile's `arx-workspace.json` and Arx starts again, so they come back as a relaunch restores them, listed but not loaded until selected. The step reports how long Arx took to be ready and how many restored pages loaded anyway, and waits 120 s instead of 10 before measuring (`--restore-settle`; 30 s with `--quick`): uBlock's updater runs 37 s after every launch and diff-updates any list that changed upstream, then saves its selfie about 55 s later, and with the 30 s this ladder had before, a list change landed in the quiet window. a first baseline on a Mac mini broke at 100 restored tabs on 18% CPU in the extension processes and 13 MB written by the browser, while the same rung idles at 0.5% when no list changed (DEV-1180). It times no switches: `selectTab` refuses a tab with no page yet, so this ladder measures what the restored rows themselves cost.

At each step, after 10 s to settle: `--idle` seconds (10) nobody touches Arx, for the CPU and idle wakeups of every process it owns and their memory; then `--probe` seconds (5) of one-item `browser_inventory` requests every 200 ms, whose round trip is how long Arx's main thread takes to answer (headless Arx runs no stall watchdog, so this is the main-thread lag a person would feel); then `--switches` (5) `selectTab` round trips to tabs the ladder opened. Arx allows an MCP client 256 mutations an app session, and every open, close and switch counts, so the awake ladder stops before a step that wouldn't fit and reports where (not a failure, not a broken limit); 200 tabs with 5 switches a step fit. The Mac's memory pressure (`kern.memorystatus_vm_pressure_level`) and how much swap grew since the ladder started are read last.

A ladder stops at the first step past any limit in `LIMITS`: pages that never loaded; idle CPU over 15% of one core; over 1,000 idle wakeups a second (provisional until the first quiet-machine run); more than one probe interval held by a main-thread answer over 100 ms (an answer counts once for each 200 ms interval it took, so one 6 s stall counts 31), or more than one switch over 100 ms (each switch goes to another tab than the one before); memory pressure above normal; swap grown over 512 MB. The step before is its ceiling. Results go to `build/load-ladder/<UTC time>/results.json` and `results.md` with headless Arx's log for each ladder; a ladder that stops on a failure rather than a limit keeps the steps measured before it, records no baseline, and makes `make load-ladder` exit with status 1 once the report is written. `--record` writes both ceilings and the limits that broke to `perf-baselines/load/<model>.json`, a folder of its own because the perf gate reads every `perf-baselines/*.json` as one of its baselines.

Run it on a quiet Mac on power: other builds and apps make every answer slower and every CPU number higher, and the load average at the start is in the report. The full run takes about an hour and opens up to 4,000 restored tabs. `--quick` climbs 5 and 10 tabs on each ladder with 3 s idle windows, 2 s of probes, 3 switches and no warm-up (`--quick --warmup 180` keeps it), to check the harness on a branch; its report says it is not a baseline, and `--record` ignores it. `--ladders awake` or `--ladders unloaded` climbs one, and `--awake-steps` or `--unloaded-steps` sets the counts.

## Agent evals

`make agent-evals` (`agent_evals/`, DEV-1026) measures how an agent gets work done through Arx's MCP server: how many calls a task takes and how much it reads and writes. MCP contract tests (`make test-mcp`, `headless_smoke.py`, the `Automation*` feature tests) say whether each tool works; this says what a task costs, so changes to tools, descriptions and results can show their gain.

- **Tasks** (`scenarios.py`), on loopback pages (`fixtures.py`) dressed like real sites, with a menu, sidebar and footer around the part that matters: `read-article` (one fact from an article), `find-text` (find a name on that article with `browser_find`, a tool outside the core set), `fill-form` (fill in a contact form in one batch, then press Send message, which asks the person every time (DEV-1008): with nobody to ask in an unattended run, the agent leaves the form filled in, says what's waiting, and nothing may be posted), `email-input` (subscribe with an `<input type="email">`), `compare-tabs` (the cheaper of two products, with both prices) and `needs-approval` (asked to send the form in a run that didn't grant page interaction: the agent must stop and say what it needs, and nothing may be posted). Each runs in its own `Arx --headless` run with a disposable profile and only that task's `--allow` classes.
- **Stand-in agents** do each task the way the arx-browser skill teaches: inventory, `browser_wait` after opening a tab, the cheapest read (`browser_read` with `scope: "main"`), one `browser_batch` for steps they know, no replays, and a one-line answer. Where Arx gets in the way, they recover as a careful model would, and each workaround names its ticket: they pair a label with the control beside it because snapshots don't name controls by their labels (DEV-1061); they finish a form one call at a time with `returnSnapshot` when the batch's first step uses up the snapshot, and read a click's own disposition when its result says `staleReference` because the page left (DEV-1011); they type a field `browser_replace_text` refuses; they wait for the inventory's `sessionState: ready` before `browser_wait`, read the inventory again on `staleTarget`, and open the tab they're about to read in front (DEV-1062). Their figures are a floor, not a model's average. A check per task judges the answer and what the fixture received.
- **Known issues.** A task can name an open ticket it fails on and the failure that ticket causes (`email-input`: DEV-1060, nothing fills an email field). That failure shows as `known` and doesn't fail the command; any other failure of the task still does, and a pass shows as `fixed?`, the cue to drop `known_issue` and record the baseline.
- **Figures** (`usage.py`), from the JSON-RPC messages: tool calls by tool and errors, split into **work** (calls that do the task) and **polls** (repeated looks while a new tab commits, which follow the machine's load; the baseline compares work); the UTF-8 bytes of the server's `initialize` instructions, of the tool list (name, description and input schema of each tool), of the arguments sent and of the text results read; and tokens estimated at 4 bytes each, plus image counts. A client sends the instructions and the tool list with every model pass, so each call also records the listing it was made with: **per turn** is that cost averaged over the task's calls, and **all turns** adds it once per call to the arguments and results, what a model that makes one call per pass pays (DEV-1021). They're for comparing runs, not bills.
- **Tool listing.** `ARGS='--tools core'` (the default) has the helper start with the core tools and `browser_more_tools`, as Claude Code gets them; a stand-in agent that needs another tool adds its group and reads the tool list again, as a client does on `list_changed`. `ARGS='--tools all'` lists every granted tool, as other clients get them. Running both shows what the core set saves; the baseline records which one it came from.
- **Output.** A table per task with changes against [agent_evals/baseline.json](agent_evals/baseline.json), and every run's figures in `build/agent-evals/<UTC time>-<model>.json`; the log is `build/logs/runtime/agent-evals.log`. A failed task fails the command; changes against the baseline are only reported, with no CI gate. `ARGS=--record` rewrites the baseline from a scripted run of every task with no unexpected failure: commit it with the change that moved it. `ARGS='--task NAME'` (repeatable) runs some tasks, and `ARGS='--app PATH'` takes an existing build with the engine instead of building.
- **Real-model mode**, run by hand: `ARGS='--model claude'` (with `--claude PATH`, `--claude-model NAME`, `--claude-timeout SECONDS`) gives each task's prompt to Claude Code with only the run's `arx` server, behind a recording relay (`relay.py`), so its calls are measured the same way, plus its own token count and cost from the stream's result. It spends tokens on the signed-in plan and never records the baseline.

The runs need a logged-in macOS session, as every headless run does, but no display.

## Performance gate

`make perf-gate` (`perf_gate.py`, DEV-902) compares a release with the previous one on the same kind of Mac, and the release workflow runs it after `make dmg-verify`. The previous release's numbers are committed per Mac model in [perf-baselines](perf-baselines), one `<model>.json` each (`sysctl hw.model`, such as `Mac16,10`), since numbers from different Macs can't be compared. It runs `make benchmark` on the release for `--sessions` sessions (default 2) of `--launches` warm launches (default 6), with `--skip-chrome --tabs 20 --switches 20`, plus `--freeze-wait 1` when the benchmark takes it, and compares each metric's median over the sessions with the baseline. `--previous <Arx.app>` measures that app too instead, one at a time and alternating which goes first. The metrics:

| Metric | From the benchmark | Threshold |
| --- | --- | --- |
| First launch → first paint | `launch_marks.first.FirstPagePainted`, else `first_launch_s` | +10 % and +0.10 s |
| Warm launch → first paint (median) | `launch_marks.warm.FirstPagePainted.median`, else `warm_launch_s.median` | +10 % and +0.05 s |
| Tab switch → page shown, 20 tabs (median) | the windowed step's `shown_ms`, else MCP `selectTab` → visible | +15 % and +15 ms |
| Memory, 1 tab | `idle_one_tab.footprint_mb` | +10 % and +25 MB |
| Memory, 20 tabs | the 20-tab step's `footprint_mb` | +10 % and +75 MB |
| Idle CPU, 1 tab | `idle_one_tab.cpu_percent` | +50 % and +0.5 points |

A metric regresses only when it's worse by more than both thresholds (`perf-gate.json`), so noise on small numbers doesn't fail a release. A metric the release didn't measure fails; one the previous release didn't measure is shown as having no baseline. Any regression fails the gate unless `--override "<reason>"` is passed; the reason is kept in `gate.json`. `--compare previous.json current.json` compares two existing benchmark results instead of measuring. Results go to `build/benchmarks/gate-<UTC time>/` (`--output` elsewhere): `gate.json` and a `gate.md` table.

A Mac model without a baseline fails the gate unless `--override` says why (its first release); the gate is then recorded as skipped. `--record` writes the release's medians as the model's new baseline once the gate passes, overridden or not, with the release, the Mac's chip, memory and macOS, and any override reason; commit it with the release. A release that didn't measure every metric can't be recorded, and neither can `--compare` results, which may come from another Mac. In the release workflow the gate runs with `--record`, `perf_override` is the reason to ship anyway, and the uploaded `perf-gate` artifact holds `baseline.json`, the file to commit as `Scripts/perf-baselines/<model>.json`. A benchmark run that failed partway, for either app, fails the gate; run it again. A metric any session failed to measure counts as not measured, and so does one whose workload didn't finish: a 20-tab step whose pages didn't all load, or a switch median that misses switches that timed out. The runner has to be a logged-in Mac with nothing else running.

The benchmark has no true cold launch: macOS's file cache can't be dropped without root, so "first launch" is the first launch on a new profile.

## Release disk image

`make dmg` (`release.py`) produces `build/release/Arx-<version>-<build>-arm64.dmg` and a `.sha256` file next to it. The version is the app's `CFBundleShortVersionString` and the build its `CFBundleVersion`. The same command runs locally and in CI. It runs these steps in order:

1. `build`: takes the next build number (see [Versions](#versions)), then a Release, arm64-only build with the engine required, in `build/ReleaseDerivedData`, copied to `build/release/Arx.app`. Release post-processing strips the app executable's symbols; `Arx.app.dSYM` stays beside the built app under `build/ReleaseDerivedData/Build/Products/Release` for crash symbolication. Keep that dSYM with each release.
2. `sign`: Developer ID signing from the inside out with a secure timestamp and no `--deep`. Libraries, loose executables and the eight `Arx Helper*` apps come first, then the engine framework, then the app. Options follow Chromium's own signing scripts: the renderer and GPU helpers get `restrict,kill,runtime` and `com.apple.security.cs.allow-jit` from `Distribution/Entitlements/`; other executables get `restrict,library,runtime,kill`. The app uses the generated `Containers/macOS/Arx.entitlements` with `com.apple.application-identifier` and `com.apple.developer.team-identifier` for the team (codesign doesn't add them the way Xcode does, and iCloud needs them), the iCloud container environment `Production` and push environment `production`, written to `build/release/Arx.entitlements`. Before the app itself is signed, the Developer ID profile is copied into it as `Contents/embedded.provisionprofile`.
3. `check`: `codesign --verify --strict --deep`, then every piece of code must be signed by the team, executables must have the hardened runtime, and entitlements must match the list above with no `get-task-allow`. The app must embed the profile made for the signing identity and carry the team's application and team identifiers and the iCloud container entitlement with the environments that profile allows. Xcode's Debug launcher (`Arx.debug.dylib`, `__preview.dylib`) and the development engine host fail the check. `spctl --assess --type execute` accepts the Developer ID signature before notarization.
4. `notarize-app`: zips the app, runs `xcrun notarytool submit --wait` with the App Store Connect API key from `.env`, staples the ticket and runs Gatekeeper again. A rejected submission prints notarytool's log.
5. `dmg`: `dmgbuild` with `Distribution/dmg_settings.py`: the app on the designed background (`Distribution/dmg-background.png` and `@2x`, exported from the Figma frame; dmgbuild makes the Retina TIFF) at a fixed position, with no Applications shortcut since the artwork says Arx moves itself there, in ULFO (LZFSE) format. `mise install` provides `dmgbuild`.
6. `sign-dmg`, `notarize-dmg`: signs, notarizes and staples the disk image.
7. `checksum`: writes the `.sha256` file.

Options go in `ARGS`. `--skip-notarize` is a local dry run without uploading anything. `--development-identity` signs with the Apple Development identity and embeds the development profile with the `Development` environments instead, and implies `--skip-notarize`. `--only STEP` (repeatable) and `--skip STEP` run single steps for debugging against the staged `build/release/Arx.app`, and `--app PATH` stages an already built app. For example: `make dmg ARGS='--only sign --only check'`.

`make dmg-verify [path.dmg]` checks a finished disk image (the newest in `build/release` by default). First, the `.sha256` next to it must name it and match its contents, and the image must be in ULFO (LZFSE) format. Then it checks the disk image signature, mounts it read-only, and runs the `check` step's per-part checks on the app inside: team, hardened runtime, the JIT entitlement only on the renderer and GPU helpers, no debug entitlements, no development shell, and an embedded provisioning profile. It doesn't compare that profile with an installed one, so it works on a Mac without the signing setup. Last come the stapled tickets with `stapler validate` and Gatekeeper with `spctl --assess --type open --context context:primary-signature` and `--type execute`, then it ejects the image. `ARGS=--allow-unnotarized` skips the notarization checks, for dry-run disk images.

`make appcast ARGS='--previous <folder>' [path.dmg]` (`appcast.py`) prepares a Sparkle release for GitHub Releases and publishes nothing (DEV-859). It refuses a disk image whose build isn't newer than every one in `--previous`, or whose version is already there with another build (a release's tag is its version alone, so the message says to bump the version), an app (`--app`, by default `build/release/Arx.app`) that isn't that version and build, has no `SUPublicEDKey` or doesn't read the feeds of `--repository` (default: the Arx repository, `capturecontext/arx-browser`), a keychain key (`generate_keys --account dev.capturecontext.arx -p`) other than the app's, and a disk image that isn't signed and stapled (`--allow-unnotarized` skips the staple check). It copies the disk images into `build/release/appcast` (`--output`), runs `generate_appcast` with only the new build in the feed, up to five deltas and download URLs under the release's tag, the version alone (`0.2.0`, no `v` and no build number), checks that the feed lists only that build, verifies the disk image's signature with `sign_update --verify`, copies it to `Arx.dmg` beside it (byte for byte, after `generate_appcast`, which would take a second disk image of the same build for another update), and prints the `gh release create … --latest` command for the files, `Arx.dmg` among them on both channels. `Arx.dmg` is the fixed name behind the website's `releases/latest/download/Arx.dmg` link; the feed, the deltas and `--previous` use only the versioned name, and an `Arx.dmg` in `--previous` is ignored. Sparkle's tools come from `make dmg`'s `build/ReleaseDerivedData` or SwiftPM's `.build/artifacts`; they read the private key from the login keychain, and the script never passes, writes or prints it. The `sign` step re-signs Sparkle's `Downloader.xpc` with `--preserve-metadata=entitlements`, as Sparkle's signing guide asks; its other parts get the usual options.

Credentials: the Developer ID Application certificate for `DEVELOPMENT_TEAM` and the Developer ID profile must be installed. `make release-signing-setup` restores both through the read-only Fastlane `developer_id_signing` lane, which never creates or revokes certificates or profiles; `make release-signing-check` shows which identity will be used, and `ARX_RELEASE_IDENTITY` picks one by SHA-1 fingerprint. If the certificate doesn't exist, the command fails and says it has to be created once in the Apple Developer portal. Notarization uses `APP_STORE_CONNECT_API_KEY_KEY_ID`, `_ISSUER_ID` and `_KEY_FILEPATH` or `_KEY_CONTENT`, or a `notarytool` keychain profile named by `ARX_NOTARY_KEYCHAIN_PROFILE`. An inline key is written to a private temporary file for the upload and removed afterwards; none of these values are printed.

### Versions

`.xcodegen/settings.yml` holds both numbers. `MARKETING_VERSION` (for example 0.1.0) changes only by hand: `make version ARGS=0.2.0` sets it, and `make version` shows both. A release's tag is the marketing version alone, so every published release needs a new one; `make appcast` refuses a version already released with another build. `CURRENT_PROJECT_VERSION`, the build number, goes up by one in every `make dmg` that runs the `build` step, starting from 1, and never resets when the marketing version changes. `versioning.py` writes the new number back to the settings file; commit it with the release so the next build continues from it. A CI job can't keep that change, so it passes `ARX_BUILD_NUMBER` instead (DEV-837).

### Release checklist

Before `make dmg` for a release:

1. Refresh the bundled !bang list: run `make bangs`, review the `Bangs.tsv` diff and the printed counts (bangs, keywords, skipped; a large drop or many skipped entries needs a look before shipping), run `make test` for `BangCatalogTests`, and commit the file on its own. Arx never fetches the list at runtime, so this step is the only way new or fixed bangs reach users (DEV-689).
2. Build and check the disk image: `make dmg`, then `make dmg-verify`.

### Install on this Mac

`make install` and `make update` (`install.py`) put a Release build in `/Applications/Arx.app` without a disk image, for testing the real app on a development Mac (DEV-856). They run `make dmg`'s `build`, `sign` and `check` steps with the same Developer ID identity, profile and entitlements, so the installed app has the release bundle ID and team and reaches the same profiles and Keychain items. The build goes to `build/install/Arx.app`, separate from `build/release`, and uses the current build number without bumping it; only `make dmg` does that. Nothing is notarized, so `spctl` accepts it as an unnotarized Developer ID app.

The signed app is copied with `ditto` to `/Applications/.Arx.app.new` and checked with `codesign --verify --deep --strict`. Only then is the Arx running from `/Applications/Arx.app` asked to quit, as Command-Q would, so it saves its session; Arx builds running from anywhere else are left alone. If it doesn't quit within 20 seconds, for example because it's asking to confirm, the command stops and the installed app stays as it was. It's never force-quit. The new bundle then trades places with the installed one in a single `renamex_np(RENAME_SWAP)` rename, and the old one is removed. Arx is opened again if it was running, or when `ARGS=--open` is given.

`ARGS=--no-timestamp` signs without Apple's secure timestamp, for when its timestamp service is down or out of reach and `codesign` stops with "The timestamp service is not available". Only notarization needs the timestamp, and these commands notarize nothing, so the installed app is the same to use. `make dmg` always timestamps.

`make install` also works when no Arx is installed. `make update` refuses then and says to run `make install`. Both need the Developer ID signing setup from `.env` described under Credentials above; signing values are never printed.

### Release on CI

`.github/workflows/release.yml` runs the same pipeline when it's dispatched by hand. It runs on GitHub's hosted `xcode-27` image in the `release` GitHub environment, whose secrets supply the signing material, and uploads the disk image and its `.sha256` as a workflow artifact, kept for 30 days. It publishes nothing: no tag, no GitHub release, no update feed. Clear the `notarize` input for a dry run with `--skip-notarize` and `--allow-unnotarized`.

The certificate never goes into the runner's login keychain. `make release-signing-setup` sees `ARX_RELEASE_KEYCHAIN` and `ARX_RELEASE_KEYCHAIN_PASSWORD`, so the read-only match lane imports into a throwaway keychain named after the run, with a random password. `make release-signing-cleanup` deletes that keychain at the end of the job, even after a failure. It does nothing when `ARX_RELEASE_KEYCHAIN` isn't set.

Configure the `release` environment once:

- Variables: `ARX_DEVELOPMENT_TEAM` (the team ID); optionally `ARX_RELEASE_IDENTITY`, `MATCH_GIT_BRANCH` and `APP_STORE_CONNECT_API_KEY_IS_KEY_CONTENT_BASE64`.
- Secrets: `MATCH_GIT_URL`, `MATCH_PASSWORD`, `APP_STORE_CONNECT_API_KEY_KEY_ID`, `APP_STORE_CONNECT_API_KEY_ISSUER_ID`, `APP_STORE_CONNECT_API_KEY_KEY_CONTENT`; `MATCH_GIT_BASIC_AUTHORIZATION` only for an HTTPS match repository (base64 of `user:token`). With an SSH URL, the runner's user needs read access to the match repository.
- Restrict the environment to trusted branches, and add required reviewers if a release should need approval.

`make test-mcp` builds the native helper and runs official Swift/Python SDK protocol clients against temporary authenticated local IPC. Set `MCP_PYTHON` to Python 3.10+ when the system Python is older. See [fixtures](mcp/README.md).

The controlled capture fixtures in `core/capture_fixture.py` cover exact CSS color patches, canvas, an iframe, frozen animated content, long/horizontally overflowing layout with fixed and sticky elements, a loading resource and lazy content. They expose only loopback test pages; their HTTP test verifies availability, while pixel, layout-preservation and cancellation acceptance belongs to the real Chromium capture smoke. `PATCHES` uses CSS coordinates for native tests to map with actual bitmap/viewport ratios, including fractional display scales.

`core/capture_smoke.py` passes those exact fixture expectations to the DEBUG app helper and requires separate pixel, layout and invalidation markers as complete output lines. The app-smoke runner fails if any assertion phase is missing, even if the app exits successfully. These ABI5 capture smoke assertions are prepared and unit-tested; the real native run is pending a compiled, signed ABI5 framework. They do not constitute native rendering validation before that run succeeds.

The standalone engine smoke explicitly requests the ABI5 mock-Keychain path with its own fresh disposable profile and requires the native `ARX_ENGINE_SMOKE_MOCK_KEYCHAIN` marker as well as successful load/shutdown. The host validates the bounded local fixture before enabling it. This isolates OS authorization prompts; it does not validate production Keychain persistence or security. Signed `app-smoke` retains real Keychain behavior. Native ABI5 smoke has not yet run.

Application smoke samples only its disposable app's direct child processes. `core/process_smoke.py` requires renderer, GPU and network helpers from the embedded framework and positive Seatbelt evidence using the same read-only `sandbox_check(pid, NULL, 0)` query as pinned Chromium.
